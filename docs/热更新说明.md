# 前端热更新使用说明

改 HTML / CSS / JS 不用打 APK，也不用发 Release。流程：

```text
本地改 assets → publish-hot.sh 打包+签名 → 写进仓库 hot/ → git push
→ App 检查 → 下载验签 → 下次冷启动切换
```

APK 只在动 Java / 原生资源 / 需要新桥指令时才重打。

> **2026-10-18 起不再用自己的服务器。** 以前清单和包都 scp 到香港那台，
> 那是单点 —— 机器欠费、被封、磁盘满、Caddy 写错，全世界的前端热更就断了。
> 而热更恰恰是出问题时唯一能救场的通道，做成单点等于没有这个东西。
> 现在全在 GitHub 仓库的 `hot/` 目录里。

## 1. 东西放哪

```text
hot/hot-update.json            签名信封，约 600 字节
hot/resources-r<rev>.zip       前端包，约 350KB
```

客户端从三个候选拉清单（`Endpoints.hotIndexUrls()`）：

```text
https://gh.dpik.top/<raw>/hot/hot-update.json?t=<时间戳>
https://gh-proxy.com/<raw>/hot/hot-update.json?t=<时间戳>
https://raw.githubusercontent.com/zhaoruizhe81/AIIvideo/main/hot/hot-update.json?t=<时间戳>
```

其中 `<raw>` = `https://raw.githubusercontent.com/zhaoruizhe81/AIIvideo/main`。

**为什么带时间戳查询串**：raw 和几个 gh 镜像前面都有 CDN（约 5 分钟）。
2026-10-18 实测：推上去之后三个候选全在吐旧的那份，客户端 check 一遍得出
「没有更新」—— 表现是「发布了，但没人收得到」。清单 600 字节，绕过 CDN 的
代价可以忽略；340KB 的包照常吃缓存。**清单要新鲜，包要缓存。**

**为什么四个候选全拉一遍取 revision 最大的**（`fetchBestEnvelope`）：不同
边缘节点收敛时间不一样。按顺序取第一个会一直读到旧的那份。

## 2. 怎么发一版

```bash
cd work/shells

# 只写到仓库的 hot/ 目录
./publish-hot.sh

# 生成后自动 commit + push
HOT_PUSH=1 ./publish-hot.sh

# 指定版本号（revision 必须比上一版大；version 只用于显示）
REVISION=20261018103000 VERSION=2026.10.18.2 HOT_PUSH=1 ./publish-hot.sh
```

`publish-hot.sh` 会：

1. 从 `work/android/app/src/main/assets/` 复制前端到临时目录；
2. 排除 `hot-update-public.pem`、`site-default.json`、`dexopt/` 这类不能热更新的文件；
3. 用 `work/android/scripts/gen-web-config.py` 现算一份 `site-web.js`
   （不能直接用 assets 里那份：Gradle 的 `genWebConfig` 按内容哈希判 UP-TO-DATE，
   内容没变就不重写，磁盘上那份的 mtime 可能比 `site-default.json` 还旧）；
4. 打 `ui/` + 根 `site.json` / `theme.json` 的 zip；
5. 用 `.build/brandkey/aiivideo-hotupdate-private.pem` 签 ECDSA；
6. 校验签名、包路径、sha256；
7. 删掉旧的包，只留最近 2 个（仓库里堆 350KB 的 zip 会被 git 历史永久记住）；
8. `HOT_PUSH=1` 时 `git add hot && commit && push`。

发布后大约 5 分钟 CDN 才收敛。客户端最长 30 分钟才会自己检查一次。

## 3. 客户端什么时候生效

- 启动时检查一次，30 分钟内不重复；设置页「检查更新」强制检查。
- 下载、验签、解包成功后进入 `pending`，不会立刻打断当前页面。
- **下次冷启动**自动把 `pending` 作为 trial 加载；设置页也可以点「立即应用并重启」马上切。
- 新界面在首页真正渲染出来后调用 `hot-ready`，trial 才算健康（`state.active`）。
- 如果新界面启动失败/超时没 ready，下一次启动会自动回退到上一版，并把该 revision
  记为 `blocked`（设置页显示「rX 没能正常启动，已回退」）。发一个更高 revision 覆盖即可。

**发完要两次冷启动才看得到效果**：第一次只把包拉下来写进 `pending`，第二次启动
才当 trial 加载。在页面上核对 `window.HotRuntime`：

```js
// Chrome DevTools 里执行
window.HotRuntime   // {revision: 20261018103000, version: "2026.10.18.2"}
```

`revision` 是 0 / `version` 是「内置」就说明还在跑 APK 自带那份。

`logcat` 里搜 `[hot]` 能看到每次会话的判定：

```text
[hot] session state={"pending":20261018103000,"blocked":...}
[hot] session state={"active":20261018103000,"trial":0}
```

## 4. 包结构

```text
site.json          {}                  ← 只保留 APK 内置站点配置，不覆盖用户源
theme.json         {"enabled":false}   ← 不启用远端主题
ui/
  app.html
  app.css
  app.js
  card-transition.js
  runtime.js
  site-web.js
  setup.js
  feed-player.js
  cover.js
  adapters.js
  vendor/
  hxm/
  *.svg
```

`HotUpdateManager.resource()` 会把 `appassets.androidplatform.net/assets/<path>` 优先映射到
`<session>/ui/<path>`，找不到才回落到 APK 内置 assets。因此整包前端都在 `ui/` 下。

阶段限制（`stage()` 里写死的）：

- 最多 512 个文件、解压后 26 MB；
- 只收 `ui/`、`theme/`、根 `site.json` / `theme.json`；
- 只收 `.html .css .js .svg .png .jpg .jpeg .webp .gif .json .woff .woff2 .txt`。

解包后 `envelope.json` 存的是**签名信封原文**。别改成存资源包 —— 见第 6 节。

## 5. 密钥

- APK 里只有公钥：`work/android/app/src/main/assets/hot-update-public.pem`。
- 私钥在本地：`work/shells/.build/brandkey/aiivideo-hotupdate-private.pem`，
  **不要提交、不要上传**（`.gitignore` 已包含 `work/shells/.build/`）。
- 换私钥 = 换公钥 = 必须重新打 APK；旧包会全部验签失败。

### 2026-10-18 换过一次密钥

旧私钥在本机、香港服务器、git 历史里都找不到，只剩公钥 —— 等于热更通道已经签不动了。
所以换了一对新密钥，新公钥打进 **1.0.24**。

**后果：这条通道只对 1.0.24 及以后生效。** 装旧版的用户收不到热更包，但也不会出错 ——
验签不过就当作没有更新。所以 `HOT_MIN_VERSION_CODE` 默认是 `10024`，更旧的应用版本
根本不会接收这一批包。

## 6. 踩过的坑

**`envelope.json` 写错了对象（2026-10-18 修）**

`unpack()` 把资源包（zip 字节）写进了 `envelope.json`，而 `metadata()` 又拿这个文件去
`verifyEnvelope()` —— 对一堆 zip 字节做 JSON 解析，必然抛异常。

后果不是「热更失败」，而是 `beginSession` 每次都走 catch：新版本被标成 `blocked`，
`active` 也被清掉，最后 `load(0)` 回内置。表现是**下载了、提示了「下次启动生效」、
重启之后永远是内置版本**，而且一条错误日志都不打。

这条链从 Gradle 源码树重建之后就没工作过，磁盘上那个 `active` revision 是旧 apktool
版留下的。修完之后加了四行 `[hot]` 日志，不然下次还是只能靠猜。

## 7. 边界

这条通道只能改前端资源。下面这些仍然必须重打 APK：

- Java 逻辑、Manifest、原生资源；
- 新增/修改打包进 APK 的权限、Activity、Service；
- 新增桥指令（旧 APK 不认识，点了没反应）。

另外，`site.json` / `theme.json` 在包里留空是刻意的：这个 App 的内容源由用户自带，
热更新不应该覆盖用户当前选的源。站点规则确实要下发时再单独设计。
