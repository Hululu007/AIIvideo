# 用户自带源与适配层

**日期**：2026-10-16
**产物**：`work/shells/cz-final.apk` / `AIIvideo.apk`（8057458 字节，sha256 `406ea791dc8faeff…`）
**补丁集**：`patches/` 23 个文件 696K
**Java 层**：362 个方法（上一轮结束时是 217）

这一轮把 App 从「一个写死了黄果站的壳」改成了**通用客户端**：装完是空的，用户填一个源地址才有内容。同时把网络层、缓存、源管理补齐，并移除了红果源。

> **配置文件的字段表在 [`站点配置参考.md`](站点配置参考.md)** —— 这一篇讲的是「为什么这么做、踩了什么坑」，那一篇讲的是「照着什么写」。

## 一、这一轮改了什么

| 原状 | 现在 |
|---|---|
| 只认黄果一个站，地址编译在包里 | **用户自带源**。设置页填地址，支持两种协议 |
| 抓 HTML + 正则解析（`SiteRepository` 3959 行） | 抓 HTML 那套**整块删除**（共 3055 行），改走 `/api/` REST |
| 双源：黄果（私密）+ 红果（公开） | **红果整块移除**（723KB smali） |
| `HttpURLConnection`，域名被污染就连不上 | **OkHttp 4.10** + DoH 解析 + 可配代理 |
| 缓存全局一份，换源后画的是上一个源的内容 | 缓存**按源分作用域** |
| 没有源管理，换源要清数据 | 设置页「内容源」列表，切换 / 删除 / 添加 |

## 二、用户自带源：三层

```text
用户填的地址
    │
    ├── {origin, web}        我们自己的 JSON（REST）
    ├── {code, list, class}  苹果CMS JSON 接口
    ├── {……XML……}           苹果CMS XML 接口（/at/xml/）
    ├── {urls[]}             TVBox 多仓        → 二期
    └── {sites[]}            TVBox 单仓        → 二期
```

**识别是自动的**，用户不需要知道「适配器」是什么。认不出来时给一句人话，不让他对着沉默的输入框猜。

配置存两处：

```text
files/user-source.json    当前生效的那份配置（SiteProfile 读它）
files/user-sources.json   地址清单 {active, saved:[{url,name,at}]}
```

**清单存地址不存内容。** 切换 = 重新拉那个地址 + 覆盖 `user-source.json`，走**跟第一次填完全一样的校验**。这样切到一个已经失效的源会被当场拒绝，而不是留一份坏配置在盘上等下次启动闪退。

## 三、苹果CMS 适配器

`CmsAdapter.java`（约 340 行）+ `CmsXml.java`（约 190 行）。

### 接口形状（2026-10-16 实测）

```text
取分类  GET ?ac=list
        → {code, class:[{type_id:1, type_name:"电影"}, …]}
取列表  GET ?ac=detail&t=<type_id>&pg=<page>
        → {code, page, pagecount, list:[{vod_id, vod_name, vod_pic, vod_remarks, …}]}
取详情  GET ?ac=detail&ids=<vod_id>
        → {code, list:[{…, vod_play_url, vod_play_from, vod_content}]}
```

**探测要拉两次，结果是互补的：**

```text
裸地址 / ?ac=list      list=20  class=49  封面域名=0
?ac=detail&pg=1        list=20  class= 0  封面域名=1
```

`class[]`（分类表）只在 list 那侧，`vod_pic`（封面）只在 detail 那侧。少任何一边都不行——没有 `class` 建不出分类表，没有 `vod_pic` 提取不出封面域名，而空的 `allowedHosts` 会让 `SiteProfile` 构造时抛异常（见坑 1）。

### XML 是另一套，但只差一层

`CmsXml` 只做一件事：**把 XML 翻译成 JSON 那套形状**，然后丢给 `CmsAdapter`。映射、分集拆解、播放地址提取全部复用，不写第二遍。

```text
JSON                          XML
list[].vod_id                 <video><id>
list[].vod_name               <video><name><![CDATA[…]]>
list[].vod_pic                <video><pic>          ← **只在详情里有**
list[].vod_content            <video><des><![CDATA[…]]>
list[].vod_play_url           <dl><dd> 的内容（多条）
class[].type_id/type_name     <class><ty id="…">…</ty>
```

两个 XML 特有的坑：

- **列表里没有封面。** 旧版接口的 list 只有 `id/tid/name/type/dt/note`。所以提取封面域名时得**单独探一次详情**。
- **CDATA 必须剥。** 不剥界面上显示的就是 `<![CDATA[你却爱着一个他]]>`。简介里还常有大段全角空格，一并压掉。

### 架构决策：适配器在 Java 侧，规范化成**我们那套 JSON 形状**

```text
JS 发 /api/...  →  SiteRepository.detail(path)  →  AiiHttp.get  →  JSON  →  JS 的 adapters.js
```

适配器负责让外部源的响应「看起来像我们的站」。于是：

- 前端那层字段别名（16 个角色）**一行不用改**——复用它是最大的收益
- `/api/home`、`/api/videos/{id}` 这些路径从「黄果站的真实路径」升级成**我们内部的动作词汇表**
- 代价是语义上绕一点（CMS 站没有 `/api/videos/123`）

**分流只接 `/api/` 开头的路径。** 封面是绝对 URL 也会走到 `AiiHttp.get`，全路由给适配器的话会被以「不认识的路径」拒掉，表现是封面全挂（见坑 4）。

### 播放地址的多线路选择

实测某 XML 源：

```text
<dd flag="liangzi">第01集$https://v.lzcdn27.com/share/47fa1e27…   ← 分享页，要第三方解析
<dd flag="lzm3u8">第01集$https://v.lzcdn27.com/20261009/…/index.m3u8 ← 直链
```

**取第一条 = 「点了播放没反应」。** 所以 `pickLine()` 优先挑含 `.m3u8` 的线路，其次 `.mp4`，都没有才退回第一条（那种情况下面会明确报错）。

## 四、红果源整块移除

```text
smali/com/hongguotv/**      47 个类    642 KB    （Kotlin SDK：Signer / AesV3 / MediaCrypto …）
Hongguo*.smali               8 个文件    81 KB    （Repository / Genres / Search / Playback）
SequelMatcher*                         孤儿，顺带删
```

**723 KB smali → classes.dex 少 117 KB → APK 少 53 KB。**（smali 一行一条指令，压缩比很高，别拿 723 KB 直接对 APK。）

`DualContentRepository` 整个重写成纯转发，**类没删**——MainActivity 的 dispatch 里有 13 处指向它，而那是按编号跳的 packed-switch（索引和 sparse-switch 哈希表耦合），改那两张表是本工程最容易出事的地方，留层薄壳一行都不用动。

**为什么删得掉**：红果没坏（站点 HTTP 200、字段形状实测还对得上、那 47 个类也都在），但它是**没接线**——前端改造后所有动作都算成 `/api/` 路径，而红果要的是「动作名 + series id」，两套调用约定对不上。而它那套实现（SSR 抓 HTML + Signer 签名 + AesV3 解密）恰好是我们前几轮从 `SiteRepository` 里整块删掉的架构。

## 四之二、底部导航也归配置

原来那排按钮是写死的四格：`首页 / 剧场 / AI / 我的`，两格中间的颜色、图标、文案全在 `app.html` 里。换到苹果CMS 之后就露馅了 —— **`剧场` 和 `AI` 点进去是同一份数据**（CMS 的分类是一维的，上一版就把同一张表填给了两个 key），名字还跟内容没关系，源里根本没有「AI」这种东西。

现在由配置出：

```json
"ui": {
  "tabs": [
    { "key": "1",  "label": "电影",   "icon": "film" },
    { "key": "2",  "label": "连续剧", "icon": "tv" },
    { "key": "4",  "label": "动漫",   "icon": "sparkle" },
    { "key": "3",  "label": "综艺",   "icon": "star" },
    { "key": "more", "label": "其他", "icon": "grid" }
  ]
}
```

- `key` 是 `data-nav` 的值，同时是 `categoryIds` / `categoryLabels` / `categoryTitles` / `categoryLeads` 的键 —— 四处必须一字不差，漏了哪张那张就退回内置文案
- 数量由配置定，1~5 个；页面按长度算 `grid-template-columns`，不再写死 4 列
- 图标名认不出来退回 `grid`，不报错

内置那份（黄果）在 `site-default.json` 里，还是 `剧场 / AI` 两个，同时把以前硬编码在 `app.js` 里的 `categoryLabels` / `categoryTitles` / `categoryLeads` 也搬进了配置 —— 前端那三个函数现在只剩兜底分支。

**苹果CMS 怎么生成这排按钮**（`UserSource.wrapCms`）：

```text
class[] 里按 type_pid 建树
  ├─ 有子分类的顶层 = 频道，按子分类数量排序，取前 4 个当入口
  │    （实测「取前几个」会挑错：量子那个源第 5 个是「体育」，
  │      和「综艺片」一样是 4 个子分类 —— 按内容量排才稳定）
  ├─ 剩下的频道 + 没有子分类的顶层 → 合成一个「其他」入口
  └─ 整棵树都没有 pid（一维分类）→ 一个「影视库」入口，全部类型排在子分类条里
```

实测 `cj.lziapi.com`（8 个顶层）：**首页 / 电影 / 连续剧 / 动漫 / 综艺 / 其他 / 我的**，7 格，每格 ~52dp 放得下。点「动漫」→ 子分类条 `国产动漫/日韩动漫/欧美动漫/港台动漫/海外动漫`，第一条请求 `cate_id=29`，出来的就是国产动漫。

打包时 `build.sh` 会拦这几类配置错：`tabs` 的 key 在 `categoryIds` 里没有、`categoryIds` 有 key 却没人能进、key 重复、四张表少了一张。

## 四之三、首页那排标签

换成 CMS 源之后「全部类型 >」旁边**一个胶囊都没有**了 —— 因为上一版把 `popularTags` / `tagGroups` 全清成了空数组。当时的理由是「怕黄果的都市/校园/古风漏过来，点了拿那些词去搜」——防漏是对的，**但清空等于把这个入口整个删掉**，还连带把「全部类型」页也变成空白（那一页按 `tagGroups` 分区渲染）。

CMS 没有独立的标签体系，它的 `type` 分类表就是标签表（`CmsAdapter.tags` 把每个 type 打上 `group="cms"` 交上来）。三处对齐起来就活了：

```text
tagGroups   [["cms", "全部分类"]]           ← 不留这一组，「全部类型」页是空的
popularTags [[cateId, 名字], …]             ← 首页那排胶囊
tag-list    /api/videos?cate_id={slug}…     ← 点胶囊去哪
```

**`tag-list` 不能是搜索。** CMS 的搜是标题匹配（`wd=`），拿「动作片」去搜一个都搜不到 —— 上一版就是 `/api/search?q={keyword}`，点标签等于白点。而标签的 slug 在 CMS 那边本来就是 `type_id`，直接当 `cate_id` 用一次到位。为此给路径模板加了个 `{slug}` 占位符（`adapters.js` 的 `fillTemplate` + `build.sh` 的 `FILLED` 各加一处）—— `keyword` 那条路走不通，它会被 `label`（显示名）顶掉。

**首页挑哪 8 个**：每个频道轮流取一个，不是从头截。`class[]` 是按 `type_id` 排的，从头截 8 个大概率全属于电影片（动作/喜剧/爱情/科幻/恐怖/剧情/战争/纪录片），首页那排看着像只有电影。轮流取出来是：

```text
动作片 / 国产剧 / 国产动漫 / 大陆综艺 / 足球 / 喜剧片 / 香港剧 / 日韩动漫
```

另外**标签不能挂顶层频道**：苹果CMS 查父类返回 0 条（坑 19），点进去会是空列表。

## 五、网络层

```text
java-src/com/huangguo/mobile/AiiHttp.java    HTTP + DoH + 代理
```

### OkHttp 而不是 HttpURLConnection

两个原因，都是实测逼出来的：

**① SNI。** 直接连 `103.41.125.229` 会 `sslv3 alert handshake failure`——服务端靠 SNI 选证书，`HttpURLConnection` 做不到「连 IP 但用域名握手」。

**② 多 IP 轮询。** DoH 一次返回 5 个地址，`HttpURLConnection` 只用第一个，第一个不通就整个失败；OkHttp 会依次试。

### DoH

```json
"doh": {
  "enabled": true,
  "servers": [
    { "name": "阿里DNS", "url": "https://dns.alidns.com/resolve", "ips": ["223.5.5.5","223.6.6.6"] },
    { "name": "腾讯DNS", "url": "https://doh.pub/dns-query",      "ips": ["120.53.53.53","1.12.12.12"] }
  ]
}
```

**`url` 写域名、`ips` 单独给**——域名让 SNI 和证书校验成立，`ips` 让解析不依赖系统（否则「解析 DoH 服务器本身」又要先解析，递归）。

**实测的边界**：DoH 能绕开运营商那一跳，但绕不开服务商自己的递归。阿里和腾讯对 `huangguoai.com` 同样给毒答案（Dropbox/Twitter 段），只是换成加密通道递过来。墙外的 `8.8.8.8` / `1.1.1.1` 这台设备根本连不上（6 秒超时）。

**它的真实作用不是「救黑名单域名」，是拿到某个域名的全部 IP 交给 OkHttp 轮询。**

**一个现场结论**：`huangguoai.com` 从手机直接 15 秒超时（系统 DNS 被污染），**只有走 DoH 才通**。所以入口域选 `cab3f.nt17g20k.cc`——两个域名实测返回同样的 19916 字节。

### 代理（新）

设置页「网络代理」，支持三种写法：

```text
127.0.0.1:7890                         HTTP 代理，不认证
socks5://127.0.0.1:1080                SOCKS5
user:pass@1.2.3.4:1080                 带账号密码（不写 scheme 默认 HTTP）
socks5://user:pass@1.2.3.4:1080        带账号密码的 SOCKS5
http://user:pass@1.2.3.4:8080
```

留空表示直连。**改代理会强制重建 OkHttp 客户端**（`proxy` 是构造期定下来的，改不了）。

**认证是怎么挂的**：HTTP 走 OkHttp 的 `proxyAuthenticator`（407 回来带一次凭据重试），SOCKS 那条路 OkHttp 没有口子——它走 `java.net.Socket` 内部，认证只能挂全局的 `java.net.Authenticator`。设之前先看 `getRequestorType()`，只回代理那一路的凭据，不接管别的认证。

**日志里不打印账号密码**——那行会进 logcat，而凭据是明文的。`describe(route)` 只输出类型和地址。

**为什么值得做**：实测直连那条链六次里四次 9~18 秒，而**换路由是客户端唯一能真正改变延迟的手段**。DoH、连接复用、预热都只是把已经确定的那段延迟挪个位置。

#### 怎么填（这里最容易填错）

**核心：`127.0.0.1` 在这个 App 里指的是「手机自己」，不是你的电脑。**

| 代理跑在哪 | 该填什么 |
|---|---|
| **手机上**（Clash for Android / Stash / Surfboard / Shadowrocket 之类） | `127.0.0.1:7890`——客户端自己监听的端口，直连没问题 |
| **电脑上**（Clash Verge / ClashX / v2rayN），手机和电脑同一个 WiFi | `电脑的局域网 IP:端口`，例如 `192.168.1.132:7897` |
| 远程代理服务器 | `服务器IP:端口`，格式同上 |

**电脑上那台必须打开「允许局域网连接」（Allow LAN）。** 默认是关的，而且关着的时候客户端只绑 `127.0.0.1`——手机连过去的包根本没进程接。

Clash Verge 的开关在「设置 → 局域网连接」，对应配置文件里的：

```yaml
# ~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/clash-verge.yaml
allow-lan: false      # ← 改成 true，或者直接在界面里勾
mixed-port: 7897      # ← 这个就是「端口」，HTTP 和 SOCKS 共用
```

**端口别猜。** Clash Verge 默认 `7897` 是混合端口（HTTP + SOCKS 都吃），`7890` 是 Clash 系的传统 HTTP 端口。填之前确认一下：

```bash
# macOS 上看谁在监听
netstat -an | grep -i listen | grep -E "789[0-9]"

# 从另一台机器验证代理真的通了（这一步最关键）
curl -s -o /dev/null -w "%{http_code}\n" -x http://192.168.1.132:7897 https://www.google.com/generate_204
# 期望 204。连不上就是 Allow LAN 没开，或者防火墙拦了
```

#### 手机侧怎么确认

```bash
# 1. 手机和电脑在同一网段吗
adb shell ip -4 addr show wlan0 | grep inet      # 例如 192.168.1.138/24
ipconfig getifaddr en0                            # Mac 侧，例如 192.168.1.132

# 2. 手机能 ping 到电脑吗
adb shell ping -c 2 192.168.1.132

# 3. 手机能连到那个端口吗（这一步过了，App 里填就一定能用）
adb shell "curl -s -o /dev/null -w '%{http_code}' -x http://192.168.1.132:7897 --max-time 8 https://www.google.com/generate_204"
```

第 3 步返回 `204` 就对了。返回 `000` 就是没通。

#### 填错了会怎样

**App 里不会提示。** 代理是在发请求那一刻才用的，生效与否要等下一次请求：

```text
设了代理但代理不可达 → 请求抛 Failed to connect to /192.168.1.132:7897
```

设置页只校验格式（`host:port` 看不看得懂），**不主动发请求验证**——代理没起来的时候给一个吓人的报错，比什么都不说更糟。

#### 自己搭的怎么用（推荐）

如果你有自建节点（xray / v2ray / sing-box / trojan / ss 都行），**在服务器上再开一个带认证的 HTTP 或 SOCKS5 入站**，App 直接填它即可——不需要在手机上装任何客户端。

Xray 的例子，在现有配置的 `inbounds` 里加一段：

```json
{
  "listen": "0.0.0.0",
  "port": 1080,
  "protocol": "socks",
  "settings": { "auth": "password", "accounts": [{ "user": "你的用户名", "pass": "你的密码" }], "udp": false }
}
```

或者用 `gost` 一行起一个：

```bash
gost -L http://用户名:密码:0.0.0.0:8080
gost -L socks5://用户名:密码:0.0.0.0:1080
```

然后 App 里填：

```text
socks5://用户名:密码@你的服务器IP:1080
```

**一定要带认证。** 公网上裸奔一个无认证的 SOCKS5，几小时内就会被扫到当开放代理用。

**这条路的好处**：不用装客户端、不用内置 30MB 的内核、手机在哪都能用（不像局域网方案要连同一个 WiFi）。

#### 手机上装客户端（另一条路）

```text
装 FlClash 或 Clash for Android  →  导入订阅  →  开起来
App 里填 127.0.0.1:7890（或它显示的端口）
```

**这是全球同类 App 的通行做法**——TVBox、影视仓、各种播放器都是让你自己开客户端填端口。不是偷懒，是内置内核的代价远超收益。

#### 实测：自建 SOCKS5 的效果（2026-10-16）

在自建节点（VPS `64.64.224.121`，AlmaLinux 9.7，Xray）上加了一个带认证的 SOCKS5 入站：

```json
{
  "tag": "socks5-in", "listen": "0.0.0.0", "port": 19108, "protocol": "socks",
  "settings": { "auth": "password",
    "accounts": [{ "user": "aii", "pass": "<随机 24 位>" }], "udp": false },
  "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"] }
}
```

App 里填 `socks5://aii:<密码>@64.64.224.121:19108`。

**效果（同一个搜索接口，连测 5 次）：**

```text
走代理     281  219  274  286  257  ms     方差 1.3 倍
直连      1623 1958 1046 1715 2581 ms     方差 2.5 倍
```

**6~8 倍，而且抖动明显变小。**

首页接口（`/api/home`）从手机量的对比更夸张：

```text
直连            15.54  12.98  13.39   1.92   1.92   7.15 秒
走 VPS SOCKS5    1.42   1.35   1.33   1.27   1.35   1.40 秒
```

**最慢那次差 11 倍。** 直连的最好成绩（1.92s）跟代理持平，但会随机崩到 15 秒。

**推测原因**：`socks5h` 让**服务器端做 DNS 解析**——手机本地解析拿到的 IP 时好时坏（本地 DNS 被污染，或者就近路由不准），而服务器在美国解析同一个域名，拿到的是近的 Cloudflare 边缘。也可能运营商对那个域名的 SNI 做了 QoS。

**这是客户端优化治不了的**——DoH、连接复用、预热改的都是「拿到 IP 之后怎么用」，改不了「手机到 Cloudflare 那一跳走哪条路」。

#### 为什么不「填个订阅链接就行」

**订阅链接和 HTTP 代理不是一回事。**

```text
订阅链接                       vmess:// vless:// trojan:// ss://
HTTP 代理                      http://127.0.0.1:7890
```

HTTP 代理是**一根管道**，App 把原始请求交给它，它负责转发。订阅是**一份节点清单**，vmess/vless/trojan/ss 各有自己的加密握手、混淆、传输层——要连它们必须有实现了那些协议的客户端。

App 自己实现 = **内置一个 Clash**。代价实测过：

```text
cmfa-2.11.35-meta-arm64-v8a-release.apk      46.5 MB
cmfa-2.11.35-meta-universal-release.apk     118.5 MB     ← 4 个 ABI，约 30MB/ABI
```

我们的 APK 现在 **8MB**。加进去是 **40~70MB**，而且构建链要加 Go 工具链 + NDK + CMake（ClashMetaForAndroid 是用 `com.github.kr328.golang` 的 Gradle 插件**在构建时编译 Go** 的，不是拿现成的库）。

**唯一的好消息**：不需要 `VpnService`、不需要 VPN 权限——我们只要自己的请求走代理，不要全局接管。

#### 一个要注意的地方

**代理不一定是「加速」。** 这条链路的瓶颈是「中国到 Cloudflare 洛杉矶边缘」，换一个落地在别处的代理可能更快也可能更慢。**填完实测一下**：首页加载那种九秒十几秒的情况有没有变。

设置页「网络代理」，支持三种写法：

```text
127.0.0.1:7890
http://127.0.0.1:7890
socks5://127.0.0.1:7891
```

## 六、缓存：四层

### ① 首页内容缓存（前端 localStorage）

```js
const CACHE_PREFIX = 'hgcache:';
function cacheKeyOf(key) { return CACHE_PREFIX + (scope ? scope + ':' : '') + key; }
```

三级兜底：**内存 → localStorage → 骨架屏**。localStorage 是同步读的，冷启动第一帧就有内容，不用等网络也不用等桥。

拿到新数据后按 `homeSignature` 比对，变了才重画。

### ② 缓存作用域（这一轮补的）

**原来分键只按 key，不按源。** 从苹果CMS 切回黄果时实测撞到：31 条封面失败，DOM 里挂的还是上一个源的 `img.lzipic.com`，拿它去核对新源的白名单自然全挂。

修法：`setup.js` 在放行启动之前写 `window.HG_CACHE_SCOPE = state.url`，`cacheKeyOf` 把它散列成短标识当键前缀。

**顺序是硬要求**：`ensure()` → 写作用域 → `startHome()` → `goHome()`。因为 `goHome()` 是**同步**读 localStorage 的。

用配置地址当标识而不是 `origin`——CMS 源的 origin 是空的，只有那个地址能区分。

淘汰改成**跨作用域按时间**。原来豁免 `home`（「首页那条不参与淘汰」），那是在全局只有一个 home 的前提下写的；现在每个源各一条，再豁免就是换几次源永久留几份。

### ③ 首屏预热（Java 侧）

`AiiHttp.warmup()` 在 `__source:get` 里触发——那是最早能同时拿到 context 和 profile 的地方（WebView 还在载入、闸门还没过完）。

前端来要同一条时**等那次在飞的预热**，而不是另开一次。实测：

```text
预热完成 /api/home 19916 字节 1182ms
等到预热结果 /api/home 19916 字节，等了 1164ms
[api] /api/home ok 1167ms
```

**收益要说实话**：目前只有「只发一次请求」的效果，延迟基本没变——因为 `__source:get` 和 `goHome()` 之间只隔 20 毫秒。要拿到真正的提前量，预热得挂到 `MainActivity.onCreate`（WebView 载入之前），那是 smali 改动。

### ④ DoH 结果的磁盘缓存

内存那份 TTL 十分钟，**冷启动就没了**。落到 SharedPreferences（TTL 30 分钟）之后冷启动直接拿上次的地址开连。

**同时后台重问一次**——磁盘那份是「省一次 DoH」，不是「永远信它」。地址真变了下次启动就是新的。

### TVBox 的 `type 3`（不做）

实测那份真实配置 86 个源里 **79 个是 `type 3`**，指向要下载执行的 JAR。

拉了一个下来看：

**加固过的。** 真实代码加密、解密在原生库里。

- 要装两份 **ARM-only、stripped、看不出做什么**的原生库
- **53 个 Guard 类全是这样**，代码不可审计
- 定位不同：一份配置一个站 vs 86 个源同时在线

实测工作量其实**不大**（约 460 行 Java），但代价不在代码量。

**不做的话 TVBox 兼容覆盖 7/86 = 8%**，而那 7 个恰好是苹果CMS——纯数据接口，正好是这套定位能覆盖的部分。

## 九、这一轮踩的坑

### 坑 1：坏配置能把 App 永久锁死

`SiteProfile` 在 `MainActivity.onCreate` 里构造，它自己那堆校验（origin 是不是 https、封面 AES 密钥够不够长、`allowedHosts` 空不空）抛异常的表现是**一装完就闪退**。而配置存在 `files/` 下，App 起不来就进不了设置页 —— **用户被一份填错的配置锁在外面，只能清数据。**

实测撞到过：`allowedHosts` 写成空数组 → `缺少封面域名` → 闪退 → `pm clear`（会清掉本地观看历史）。

**修法**：`__source:set` / `use` 存盘前先 `new SiteProfile(context, config)` **干跑一次**。它跟启动时读的是同一个文件、同一条合并逻辑，抛异常就拒绝落盘。

### 坑 2：封面要显式覆盖两块

内置模板里 `cover.mode` 是 `aes-cbc`（黄果的封面是加密图），而 CMS 返回的是**普通 JPEG**。照内置那套解密会把图毁掉。

`allowedHosts` 也要覆盖——`SiteProfile.coverUrl()` 会拿它**逐个精确比对** host，不匹配直接抛「无效封面域名」。它是防 SSRF 的，但 CMS 的封面域名事先不知道，只能从探测响应里现取（实测每个源只用**一个**封面域名）。

### 坑 3：换源之后 `location.reload()` 不够

`SiteProfile` 只在 `MainActivity.onCreate` 里构造一次。**`location.reload()` 只重载 WebView 页面，Activity 不重建** —— Java 侧那份 profile 还是旧的。

表现：源表已经切了、缓存作用域也换了，但 `__source:web` 返回的还是上一个源的 web 块，首页也还是上一个源的内容。

**修法**：给 `MainActivity` 加静态引用 + `restart()`（调现成的 `recreate()`），Java 侧换源后调它。

第一版试的是 `startActivity(launch)` + `Runtime.exit(0)`——**实测把 App 直接弄没了**：同一进程里的任务被一起干掉，`startActivity` 排的队也跟着没，用户得自己再点一次图标。

这条路**当时没走通**，真正的两个拦路虎在坑 14、坑 15 —— 修完才「点一下就换」。

### 坑 4：适配器分流不能全接

`AiiHttp.get` 按 `adapter == "cms"` 分流时，**只接 `/api/` 开头的路径**。封面是绝对 URL 也会走这里，全路由给适配器会被以「不认识的路径」拒掉，表现是封面全挂。

### 坑 5：键对不上，逻辑一次都没走到

预热存的是 `/api/home`（内部路径），而前端来要的是 `https://cab3f.nt17g20k.cc/api/home`（拼过 origin 的完整地址）。`WARMING.get()` 永远返回 null，**等预热的逻辑一次都没执行**——表现是两路并发，日志里两条 GET，预热白跑。

修法：加 `prefetchKey()` 归一化。

### 坑 6：界面常量的 key 必须是 `adult` / `ai`

那是前端 `state.tab` 的取值。CMS 配置里写成 `main` 前端读不到，**静默退回黄果那套硬编码文案**「成人剧场 / 成人短剧 / 成人漫剧」。

> **已过时（10-16 下午）**：key 不再有这个名字约束了 —— 底部导航由 `web.ui.tabs` 定，key 是配置自己起的（苹果CMS 那边直接用 `"1"`/`"2"`）。见「四之二、底部导航也归配置」。真正还成立的那半句是：**四张按 key 索引的表必须和 `tabs` 对齐**，对不上同样静默退回内置文案 —— 现在 `build.sh` 会在打包时拦下来。

### 坑 7：`categoryTitles` 是字符串不是数组

它是页面大标题。塞数组进去被插值成「电影片,连续剧,综艺片,…」四十个名字连成一串的巨标题。前端加了类型检查兜底。

### 坑 8：`open(p,'w')` 会立刻截断文件

编辑 `MainActivity.smali` 时写的：

```python
open(p,'w',encoding='utf-8').write('\n'.join(L))
```

Python 先求值参数再调用——**`open(p,'w')` 已经截断了文件**，然后 `'\n'.join(L)` 抛异常，`write` 从没执行。**4941 行的文件变成 0 字节。**

从 `patches/` 恢复了（那个目录就是干这个的）。**以后改 smali 一律先写 `.tmp` 再 `os.replace()`。**

**补一刀**：`os.replace()` 会连**权限位**一起换掉 —— 新写的 `.tmp` 是 `644`，替换之后 `build.sh` 就没有执行位了，报的是 `bash: ./build.sh: Permission denied`。用这套写法改可执行文件，改完记得 `chmod +x`。（实测踩到。）

### 坑 9：缓存层会遮住网络层的问题

测「设代理后请求应该失败」时成功了——因为 `/api/home` 被预热缓存挡住，`get()` 在预热命中的分支就返回了，压根没碰网络。换 `/api/videos/12` 才测到。

### 坑 10：CMS 源的请求完全绕过代理

`CmsAdapter` 走的是 `AiiHttp.getRaw()`，而那个方法第一版是这样的：

```java
public static byte[] getRaw(String url, int timeoutSeconds) {
    OkHttpClient plain = new OkHttpClient.Builder()...build();   // 每次新建
    ...
}
```

三个问题一次踩全：

- **用户的代理设置在这里被完全忽略**（CMS 源的请求根本没走代理）
- **每次 `new` 一个 `OkHttpClient` 等于每条请求都重来一遍连接池和 TLS 握手**
- **没有日志**——`[http] GET …` 那行在 `get()` 里，`getRaw` 不经过它

排查时被这个绕了很久：设了代理、请求也「成功」，但代理服务端一条连接都没有。**日志里什么都没打，是因为那条路本来就不打日志。**

修法：`getRaw` 改用缓存客户端（`plainClient()`），照挂代理，补上日志。

**教训**：分流出来的第二条路要跟主路走同一套基础设施，不然「用户设置」和「可观测性」会在那条路上同时失效。

### 坑 11：SOCKS 的 `RequestorType` 是 `SERVER`，不是 `PROXY`

给代理加认证时，SOCKS5 那条路是这么写的：

```java
protected PasswordAuthentication getPasswordAuthentication() {
    if (getRequestorType() != RequestorType.PROXY) return null;   // ← 永远返回 null
    return new PasswordAuthentication(route.user, route.pass.toCharArray());
}
```

**Java 的 SOCKS 实现用的是 `RequestorType.SERVER`。** 所以凭据永远回不去，服务端只收到空认证。

现象很有迷惑性：

```text
App 报      SOCKS : authentication failed
服务端报    rejected proxy/socks: invalid username or password
curl 用同一套密码 -x socks5h://… → 完全通
```

**很容易怀疑到密码头上**——去查密码、去重设密码、去比对 URL 编码。实际是那个 `RequestorType` 判断写错了。

加一行日志就定死了：

```text
Authenticator 被调用：type=SERVER proto=SOCKS5 host=64.64.224.121:19108
  不是 PROXY，返回 null
```

**修法**：判断条件换成「协议 + 目标地址」，比 `RequestorType` 可靠，也不会顺手接管别的认证请求。

```java
if (!"SOCKS5".equalsIgnoreCase(String.valueOf(getRequestingProtocol()))) return null;
SocketAddress raw = route.proxy.address();
if (!(raw instanceof InetSocketAddress)) return null;
InetSocketAddress address = (InetSocketAddress) raw;
if (!String.valueOf(getRequestingHost()).equals(address.getHostString())) return null;
if (getRequestingPort() != address.getPort()) return null;
return new PasswordAuthentication(route.user, route.pass.toCharArray());
```

**教训**：`RequestorType` 这个名字会诱导你按字面理解。**先打日志确认实际值，再写判断。**

### 坑 12：测试脚本读错了返回值

`bridgeCall` 返回的是**对象**不是字符串，我一直用 `String(r)` 判断结果——拿到的是 `[object Object]`（15 个字符）。**这个 15 字节的「成功响应」骗了我好几轮**，还让我一度以为请求根本没发出去。

看返回值要 `typeof r === 'string' ? JSON.parse(r) : r`，或者直接看 `Object.keys(d)`。

### 坑 13：切换源的残留不是渲染问题，是缓存问题

从 XML 源切到黄果时 31 条封面失败、报「无效封面域名」。我当时判成「切换源的残留渲染」——**现象描述对了，归因错了**。实际是缓存没按源分键，把旧源的首页端了出来。

### 坑 14：`Activity.recreate()` 不在主线程就抛

用户报的是「选完源不生效，必须退出 App 再进」。

`UserSource.handle` 是从 OkHttp 的线程进来的（前端 `bridgeCall` → 桥 → `handle`），我就在那个线程里直接调了 `host.restart()` → `MainActivity.recreate()`。从 API 28 起 `recreate()` 自己查线程：

```java
if (Looper.myLooper() != mMainThread.getLooper())
    throw new IllegalStateException("Must be called from main thread");
```

抛了被 `catch (Throwable)` 吞掉，接着走「叫起 launcher intent」的退路。而那条退路只加了 `FLAG_ACTIVITY_NEW_TASK` —— **任务本来就在前台，系统只是把原任务拎到前面**，没有新 Activity，配置也不会重读。两头都空，表现就是「什么都没发生」。

改法：`recreate()` 用 `Handler(Looper.getMainLooper()).postDelayed(...)` 挪到主线程（留 200ms 让 `{ok:true}` 先回到前端，界面才画得出「正在切换…」），退路补上 `FLAG_ACTIVITY_CLEAR_TASK`。

前端那边也改了：**不能再 `await` 这条重启指令**。Java 是异步重建，页面会在响应回来之前就被销毁，promise 永远不 resolve，界面卡在「正在切换…」——用户在截图上看到的就是这个状态。现在发出去就不管，只留一个 2.5 秒的兜底定时器。

### 坑 15：注入的 smali 落到了错的方法里

接坑 14。修好线程问题后，日志说的是另一句：`拿不到 MainActivity 实例`——**`MainActivity.host` 恒为 null**，冷启动之后立刻查也是 null。

是我自己加的「onDestroy 里把 host 置空」那三行：

```
const/4 v0, 0x0
sput-object v0, Lcom/huangguo/mobile/MainActivity;->host:...
```

插到了 **`onCreate` 的末尾**（`checkHotUpdates()` 那一句前面），不是 `onDestroy`。于是每次 onCreate 先把 host 设上，执行到函数末尾又清掉，别人读的时候永远是 null。日志看着像「时机不对」，其实是位置错了。

顺手把置空加上条件：

```
sget-object v0, ...->host
if-ne v0, p0, :cond_2    # 只有当前实例确实是自己时才清
const/4 v0, 0x0
sput-object v0, ...->host
:cond_2
```

无条件清的话，**后建的实例会被先建实例的 onDestroy 抹掉**——`recreate()`、双实例、切换重合都能撞上。这个已经实测到过：一次 `am start` 起出第二个实例之后，`host` 就再也不是活的那个了。

**教训**：往 smali 里插指令，「插在某个方法末尾」这种锚点太弱——`sput-object`、`checkHotUpdates` 这类片段在同一文件里到处都是。插完必须回头确认它落在哪个方法里：

```bash
awk 'NR<=目标行 && /^\.method/ {m=$0; n=NR} NR==目标行 {print n": "m}' MainActivity.smali
```

### 坑 16：换源重建了 Activity，没重建网络层

紧接着用户又报：「点完直接首页显示 内容更新失败，展示缓存」。

日志里只有一行可疑的：

```text
[http] 等到预热结果 /api/home 5164 字节，等了 0ms
```

那个 0ms 是破案点 —— 重建刚发生 71ms，新的预热不可能已经跑完，所以这 5164 字节**是上一个源的首页**。黄果的首页是 19916 字节，大小也对不上。

根子在 `AiiHttp` 的两个 static map：

| 量 | 作用 | 问题 |
|---|---|---|
| `PREFETCH` | 预热拿回来的字节，60 秒内有效 | 键是**路径**（`/api/home`），不带来源 |
| `WARMING` | 在飞的预热，前端来要同一条时等它 | 条目**完成之后从来不删**，而它带着 `body` |

`get()` 是先查 `WARMING`、再查 `PREFETCH` 的。于是 `WARMING` 那个「完成信号」事实上变成了一层**没有 TTL、也不区分来源的缓存**——第一次预热完之后，`/api/home` 永远从它取，永远不碰网络。

更糟的是 CMS 源：`get()` 里 CMS 的分流在最前面，**直接 return，压根走不到预热那段**。所以给 CMS 源预热是白跑（还多打一次接口），而存进去的字节就烂在 `PREFETCH` 里没人取；下次换回普通源，正好把它捞出来用。

修法三条：

1. `AiiHttp.resetForSourceChange()` —— 换源/清源时清掉 `WARMING`、`PREFETCH`、连接池。**换源走的是 `recreate()`，进程活着，不清就是带着上一个源的痕迹往下跑。**
2. `Warmup` 加 `fresh()`，跟 `Prefetch` 一个 TTL；`warmup()` 遇到过期的条目先腾位子。
3. 预热线程开工时记下 `GENERATION`，回来对不上就把字节丢掉 —— 否则换源那一瞬间在飞的预热会在几百毫秒后落进 `PREFETCH`，把刚清干净的表又污染一次。

还有一处同类的：`client(profile)` 里 `new SmartDns(profile)` 把 profile 捕获进去了，而客户端是缓存的 —— 换源之后连接池也得一起作废。

**教训**：`recreate()` 看起来像「重启」，其实只是一次 Activity 重来。**进程里那些 static 的东西一样没动。** 换源要清的清单得照着「所有跨 Activity 存活、又和源有关的东西」写一遍，别信感觉。

### 坑 17：变量遮蔽 —— 局部 `cover` 盖住了封面模块

修完坑 16，那个提示还在。这次日志帮忙了（`toast()` 现在会把每条提示打进 logcat）：

```text
10:04:04.284  [api] /api/home ok 2076ms
10:04:04.287  [toast] 内容更新失败，正在显示缓存      ← 成功之后 3ms
```

**接口 200，然后立刻说它挂了。** 所以根本不是网络的事。

在 `goHome` 的 catch 里把 `error.stack` 打出来：

```text
[home] 失败：TypeError: cover.loadInto is not a function
```

`refreshMissingImages` 里：

```js
const cover = byId.get(button.dataset.openId);  // ← 一个 URL 字符串
...
cover.loadInto(image);                          // ← 想调的是模块级的 cover 对象
```

模块级那个 `const cover = window.HGCover.create(...)`（第 80 行）被函数内的同名局部变量遮住了。`字符串.loadInto` → `undefined` → TypeError。

触发条件有两个，所以它是间歇的：首页数据**没变化**（才走 `else` 分支）+ 页面上**有封面没加载出来**（`naturalWidth === 0` 才继续往下走）。CMS 源封面偶尔失败时正好两条都满足。

改成 `const url = ...` 就好了。

**教训**：`cover`、`api`、`state` 这种模块级单字名，函数内别用同名的局部变量。这个错误本来跑一次就现形，可惜它被下面那条 catch 伪装成了网络故障。

### 坑 18：`try` 里网络和渲染混在一起，错误提示会撒谎

坑 17 之所以查了半天，是因为 `goHome` 长这样：

```js
try {
  const fresh = await refreshing;      // 网络
  ...
  renderHome();                        // 渲染
  refreshMissingImages([...]);         // 渲染
} catch (error) {
  toast('内容更新失败，正在显示缓存', true);   // ← 渲染炸了也报这句
}
```

后面那几句抛出来，走到同一个 catch，用户看到的是「内容更新失败」。**顺着这个提示查网络，方向从头就是歪的。**

拆成两个 `try`：拿不到数据才叫接口失败（保留原来的错误页 / 提示 / 退避重试）；拿到了数据就说明接口是好的，渲染出问题只打日志、不弹提示，并且把已经拿到的好数据存下来。

顺手加了一条：`toast()` 里 `console.log('[toast] ' + message)`。真机上提示三秒就没了，光看 DOM 分不清是这次弹的还是上次留在那儿的（我就被这个骗过一轮：页面上挂着失败提示，日志里首页却是成功的）。`MainActivity` 的 `onConsoleMessage` 会把 console 原文转进 logcat，所以所有提示现在都能回溯。

**教训**：**错误提示的措辞会把排查带偏。** catch 的范围划多大，就等于撒谎的范围有多大。

### 坑 19：苹果CMS 查父类不出内容

做导航分组时本来想偷懒：顶层频道当入口，点进去用父类的 `type_id` 查。**实测不行**：

```text
cj.lziapi.com  ?ac=detail&t=1&pg=1   →  total=0
cj.lziapi.com  ?ac=detail&t=6&pg=1   →  total=4974     （6 是 1 的子类）
bfzyapi.com    ?ac=detail&t=1&pg=1   →  total=0
```

`t=<父id>` 返回空 —— 苹果CMS 的 `t` 是精确匹配 `type_id`，不会把子类一起捞上来。所以**一个入口要能用，必须把它下面的叶子分类列全**，不能只挂一个父 id 上去。这条决定了整个分组算法的形状。

### 坑 20：XML 接口没有分类层级

苹果CMS 那套 `/at/xml/` 的 `<class>` 长这样：

```xml
<class><ty id="1">电影片</ty><ty id="6">动作片</ty>…</class>
```

**只有 id 和名字，没有 `type_pid`** —— 分类树读不出来，底部导航只能退化成一个「影视库」入口。同一台机器的 JSON 接口有：

```text
GET /api.php/provide/vod?ac=list   →  class[] 44 条，type_pid 齐全
GET /api.php/provide/vod/at/xml/   →  40 条，只有 id + 名字
```

两者地址只差一个 `/at/xml/`。所以 `load()` 里补了一次探测：**只在「URL 含 `/at/xml/` 且拿到的 class 一条 pid 都没有」时才问**，而且只把层级关系补进去，id 和名字还是用 XML 那份（本来就是同一张 type 表）。失败就按一维处理，不影响能用。

顺带发现两个接口的条数还不一样（XML 40 / JSON 44），所以是按 `type_id` 对齐后**补**、不是整份替换 —— 直接换会把 XML 有而 JSON 没有的那几条弄丢。

### 坑 22：发布包带着临时改动发出去了（2026-10-16）

**症状**：所有源的首页全空。日志显示 `[api] /api/home ok 2176ms`，接口是通的，
`state.home.featured` 却是 `[]`。探到 `window.HG_SITE.shapes` 是一组**测试用的形状映射**
（`envelope: ""`），而这个源根本没配 `shapes`。

**原因链**：

1. 验 `shapes` 自检能不能拦住错配置时，往 `cz_repack/assets/site-default.json` 里塞了一组临时的
   `web.shapes`，跑 `./build.sh fast`
2. 验完把 `site-default.json` 还原了
3. 接着跑 `sync-patches` + `verify`（都说「完全一致」），然后
   `cp cz-final.apk ../../AIIvideo.apk`
4. 但 `cz-final.apk` **还是第 1 步那次打的**——第 2 步之后没有再 `fast` 过

关键在 `site-web.js` 是**生成**的（每次 pack 从 `site-default.json` 现生成），
而且它在 `IGNORE` 里、**不参与补丁集比对**。所以「改 JSON → 打包 → 改回来」这个顺序
会留下一份内容对不上源的 APK，而 `verify` 照样报「完全一致」。

**修法**：加了 `./build.sh release`，把顺序钉死在一个命令里 ——
`verify → pack → sync-patches → verify → pack → 报 sha256`。
发版一律走它，别手动 cp。改配置这件事本身没有错，错的是「打包」和「发布」之间
隔着一步手工操作。

**顺带记下这个站的两个反直觉点**（写适配器时踩到的）：

- `/v2/search` **只有它带 `data` 信封**，`/v2/home-list` 和 `/v2/catalog` 都是裸的。
  同一个站内部都不统一。
- 首页列表和目录列表**两套命名**：`{AID, Title, PicSmall, NewTitle}` vs
  `{id, name, cover, uptodate}`。按一套写，另一套全 `null`。

## 坑 21：不认识的 group 一律折进 `other`

首页那排胶囊回来了，点「全部类型」还是**整页空白**，但表头写着「40 个标签」—— 数据拿到了，一个都没渲染。

`adaptTags` 里：

```js
group: TAG_GROUP_BY_CODE[code] || 'other'
```

CMS 那边给的 `code` 是 `"cms"`，不在那张映射表里，于是 40 个标签全被折进 `other`；而 CMS 的配置只声明了 `"cms"` 一组 —— `renderTags` 按 `tag.group === id` 过滤，两边对不上，全丢。

改法是给映射表显式加一条 `cms: 'cms'`，同时在 `site-default.json` 的 `tagGroups` 里补上 `["cms","全部分类"]`（内置源不会产出这个 code，那一组永远是空的，`renderTags` 对空组直接跳过，不显示）。

**这里是 `build.sh` 那个检查救场的地方**：它本来就有一条「`adapters.js` 会产出 group=X，但 `ui.tagGroups` 里没有这个分组」的校验，加完映射表之后立刻报了出来 —— 提示我两个文件要一起改。这类错的共同点是**不崩、不报错、只是页面上少了一片东西**。

**教训**：`X || '默认值'` 这种兜底，在「另一个文件里还有一张表声明了合法值」的时候会把错误藏起来。要么显式列全，要么让兜底值也进那张表。
