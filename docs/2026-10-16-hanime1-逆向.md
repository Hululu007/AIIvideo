# hanime1.me 逆向

**日期**：2026-10-16
**目标**：`https://hanime1.me/`
**手段**：本机 Chrome + chrome-devtools MCP，真浏览器上下文内 `fetch` + DOMParser 离线解析，未落任何第三方抓包代理
**产物**：`docs/2026-10-16-hanime1-逆向.md`、`work/shells/java-src/com/huangguo/mobile/Hanime1Adapter.java`、`work/shells/hanime1.json`
**结论**：**元数据层可以直接接，播放层能拿到直链但要运行时现取。**
**用途**：本地测试沙箱内的单站适配器实验，不外发。

---

## 一、先把结论摆出来

| 项 | 状态 | 依据 |
|---|---|---|
| 首页 / 分类 / 搜索 / 分页 | ✅ 服务端渲染 HTML，无登录、无鉴权 | 裸 `fetch` 首页 144 张卡、分类页 41 张、`sort=最新上傳` 页 59 张 |
| 详情 | ✅ OG meta + DOM 全给 | `og:title` / `og:image` / `og:video:duration` / `og:description` 四条齐 |
| 播放直链 | ⚠️ **能拿，但不能缓存** | `<video><source>` 内联三档 mp4，带 `?secure=` 签名，TTL 约 12 小时 |
| 签名能不能自己算 | ❌ 不能 | 改一位、换时间戳、去参数三种改法全部 403 |
| 封面图 | ✅ 长效签名（约 97 年，等价于不校验过期） | 卡片封面 ts 比当前时间大约 31 亿秒 |
| 接口有没有 JSON | ❌ 没有 | `/api/*`、`/sitemap.xml` 全部 404 且返回 `{"message":""}` |
| **页面域能不能从安卓直连** | ⚠️ **未实测，且有一道 TLS 指纹闸** | curl 全 403，六种浏览器指纹全 200 —— 见第二节 |

**一句话**：这是个**纯 SSR 的 Laravel 站**。没有 API，数据只能从 HTML 里抠；播放地址有签名，必须在用户点播放的那一刻去详情页现取，不能进缓存、不能预取。**另外它在 Cloudflare 后面，闸门卡在 TLS 指纹上而不是 Cookie 上**——这是落地前必须先验的一项。

## 二、Cloudflare 那道闸（落地前必读）

这一节是本轮最重要的发现，也是**唯一没验证完的一项**。

### 2.1 现象

同一个 URL、同一组请求头，换客户端结果完全不同：

```text
curl（OpenSSL，即使伪装成完整浏览器头）        → 403  Attention Required | Cloudflare
curl_cffi impersonate=chrome131                → 200  218825 字节，144 张卡
curl_cffi impersonate=chrome99 / 110 / safari  → 200  144 张卡
curl_cffi impersonate=firefox133 / edge101     → 200  144 张卡
```

**六种浏览器指纹全放行，只有 OpenSSL 那一族被拦。** 请求头怎么补都没用（补全 `sec-ch-ua*`、`Sec-Fetch-*`、`Accept-Language`、`Upgrade-Insecure-Requests` 之后仍然 403）。

### 2.2 判据不是 Cookie

浏览器里那份完好的会话，`document.cookie` 只有三个：

```text
_ga, _ga_2JNTSFQYRQ      Google Analytics
XSRF-TOKEN               Laravel 自己的 CSRF
```

**没有任何 `cf_clearance` 之类的 Cloudflare 令牌。** 也就是说浏览器之所以通，不是因为攒了 Cookie 通行证，而是因为它是浏览器。这反过来支持「闸门在 TLS/HTTP2 指纹」这个判断。

实测的 JA3 差异：

```text
curl (OpenSSL)     ja3_hash 375c6162a492dfbf2795909110ce8424   ← 被拦
Chrome 131         ja3_hash 7e0c5f8498c43574d76173e7871417c0   ← 放行
```

### 2.3 媒体域**没有**这道闸

好消息：`vdownload.hembed.com` 是 **CDN77 的对象存储**，裸 curl 就能拿：

```text
$ curl -H 'Range: bytes=0-10' 'https://vdownload.hembed.com/408706-480p.mp4?secure=…'
HTTP/2 206
content-type: video/mp4
x-rgw-object-type: Normal            ← Ceph RGW，对象存储
access-control-allow-origin: *       ← 还开了 CORS
x-77-cache: HIT                      ← CDN77
```

**没有 `cf-ray`，没有 `server: cloudflare`。** 而且响应里连 `cf-ray` 都没有——媒体这一层完全是另一条链路。

### 2.4 对安卓端意味着什么（**未验证**）

```text
页面域  → 过 Cloudflare，卡 TLS 指纹   ← 风险点
媒体域  → 裸客户端直接 206             ← 没问题
```

安卓侧走 OkHttp，它的 TLS 是**平台实现**：Android 上 OkHttp 用 Conscrypt（就是 BoringSSL，Chrome 那一族），不是 OpenSSL。**所以它大概率不会像 curl 那样被拦——但这是推断，不是实测。**

不能直接假定的原因：Conscrypt 的扩展顺序、支持的曲线、HTTP/2 SETTINGS 帧参数与桌面 Chrome **并不完全相同**（Conscrypt 不实现 GREASE、某些扩展默认关）。CF 的判定是多种信号的加权，同族不等于同指纹。

本机没有连安卓设备，这一项**本轮没做**。验法：

```bash
# 1) 手机连上、装好 APK 后，走适配器拉一次首页
adb logcat -s AiiHttp | grep 'GET hanime1.me'
# 2) 若首页空白，先在设备上直接验 TLS 指纹是不是元凶：
adb shell 'printf "GET / HTTP/1.1\r\nHost: hanime1.me\r\n\r\n" | openssl s_client -connect hanime1.me:443 -servername hanime1.me 2>/dev/null | head -5'
# 3) 判据：拿到 "Attention Required" 就是指纹闸；拿到 <html lang="zht"> 就是通了
```

**如果实测被拦**，三条备选（按代价排序）：

```text
① 换 HTTP 客户端 —— OkHttp 换成自带 BoringSSL 且能配 GREASE 的实现
   （Chrome 的指纹靠的就是 GREASE + 特定扩展顺序，Conscrypt 默认不 GREASE）
② 走 WebView 发请求 —— 这本来就是浏览器栈，指纹天然对。代价是慢、
   要解析回调，但项目里已经有 MediaProxy 那套接管 WebView 请求的先例
③ 换域 —— 站点有镜像，但**适配器不认镜像**（DOM 形状没验证过），
   等于从零重做一遍逆向
```

**现阶段不要因为「逆向都通了」就把它当成可用源交付** —— 元数据和播放地址解析都已验证，卡的是「安卓端能不能把请求发出去」这一跳。

## 三、数据层：HTML 选择器表

### 3.1 首页 `/`

分区容器是 `.video-item-container`，里面套 `.horizontal-card`：

```html
<div title="…" class="video-item-container">
  <div class="horizontal-card">
    <a href="https://hanime1.me/watch?v=408707" class="video-link">
      <div class="thumb-container">
        <img class="main-thumb" src="https://vdownload.hembed.com/image/thumbnail/408707l.jpg?secure=…">
        <div class="duration">02:00</div>
        <div class="stats-container">
          <div class="stat-item"><i class="material-icons">thumb_up</i> 98%</div>
          <div class="stat-item">4549次</div>
        </div>
      </div>
      <div class="title">うごイラ(Full)：ラブリーチカちゃんと戦ってみた♡</div>
    </a>
    <div class="subtitle">
      <a href="https://hanime1.me/search?query=ぽるせりん">ぽるせりん</a>
      <span class="subtitle-time">&nbsp;• 26分鐘前</span>
    </div>
  </div>
</div>
```

| 我们要的 | 从哪来 |
|---|---|
| id | `a.video-link[href*="/watch?v="]` 的 `v=` 参数 |
| title | `.title` |
| cover | `img.main-thumb[src]`（`l.jpg` = 列表图，`h.jpg` = 大图） |
| duration | `.duration`（`mm:ss` 文本） |
| likes | `.stat-item` 首个（`98%`） |
| views | `.stat-item` 次个（`4549次`） |
| uploader | `.subtitle > a` |
| uploadedAt | `.subtitle-time` |

### 3.2 分类 / 搜索页 `/search`

**形状和首页不一样**——这是第一个坑：

```html
<div class="home-rows-videos-wrapper">
  <!-- 广告卡：同样是 <a> + .home-rows-videos-div，但 href 指向 l.erodalabs.com -->
  <a style="text-decoration:none" href="https://l.erodalabs.com/s/7duYXu" target="_blank">
    <div class="home-rows-videos-div search-videos hover-lighter">
      <div class="video-card-inner"><img loading="lazy" src="…/image/icon/erolabs_search_268x394.jpg?secure=…"></div>
    </div>
  </a>

  <a style="text-decoration:none" href="https://hanime1.me/watch?v=406534">
    <div class="home-rows-videos-div search-videos hover-lighter">
      <div class="video-card-inner" style="position:relative">
        <img loading="lazy" src="https://vdownload.hembed.com/image/cover/406534.jpg?secure=…">
        <div class="home-rows-videos-title">少女彈珠汽水 8</div>
      </div>
    </div>
  </a>
```

**广告卡必须过滤**。判据有两条，用第一条就够：

```text
① href 必须匹配 watch?v=(\d+)          ← l.erodalabs.com 那条立刻掉队
② 封面 src 必须在 vdownload.hembed.com  ← erolabs_search_268x394.jpg 是 /image/icon/ 路径
```

第二条是兜底：广告位图集叫 `/image/icon/`，正片封面叫 `/image/cover/` 或 `/image/thumbnail/`。

### 3.3 分页

```html
<ul class="pagination" role="navigation">
  <li class="page-item disabled"><span class="page-link">‹</span></li>
  <li class="page-item active" aria-current="page"><span class="page-link">1</span></li>
  <li class="page-item"><a class="page-link" href="?genre=%E8%A3%8F%E7%95%AA&page=2">2</a></li>
```

`?page=N`。**越界不是 404，是 0 张卡**——`page=9999` 返回 200、列表为空、DOM 里没有 `a[href*="/watch?v="]`。

所以假分页的判据是「这一页能抠出 0 个条目」，不是 HTTP 状态码。

### 3.4 排序与筛选

搜索页年份下拉是**纯年份**，不是内容排序：

```text
全部 / 2026 年 / 2025 年 / … / 2003 年
```

真正的内容排序在 URL 上：`?sort=最新上傳`、`?sort=最新上市`。`genre=` 是内容分类（裏番 / 泡麵番 / Motion Anime / 3DCG / 2.5D / 2D動畫 / AI生成 / MMD / Cosplay / 新番預告）。

### 3.5 详情 `/watch?v=ID`

元数据几乎全在 OG meta 里，**这是最省事的一层**：

```http
og:title            [RD] Anastasya - Hanime1.me
og:description      Title / タイトル: Anastasya\nBrand: RD\nRelease: 2026/10/15\nFile size: 5.2 GB\n…
og:image            https://vdownload.hembed.com/image/thumbnail/408706h.jpg?secure=…
og:video:duration   484
twitter:description [RD] Anastasya - 原神, 安娜絲塔夏…, POV, 1080p, 乳交, 妖精, 巨乳, … - Hanime1
```

`twitter:description` 是**标签串**：标题 + ` - ` + 逗号分隔的 tag 列表 + ` - Hanime1`。剥两头就是 tags 数组，其中 `1080p` 这类画质词也混在里面（要过滤）。

标签锚点：`# 原神` → `/search?query=原神`（**注意带 `#` 前缀和空格**，要 trim）。

未登录状态下**点赞数拿得到、观看数拿不到**（列表页有 `4549次`，详情页那个位置是空的）。

## 四、播放层：签名机制

### 4.1 直链长什么样

```html
<video id="player" data-poster="…">
  <source src="https://vdownload.hembed.com/408706-720p.mp4?secure=k55MpA1GNS6yC_CEOCsuMg==,1792206059" type="video/mp4">
  <source src="https://vdownload.hembed.com/408706-480p.mp4?secure=hQDas-Taez9NJROp5lDzVQ==,1792206059" type="video/mp4">
  <source src="https://vdownload.hembed.com/408706-1080p.mp4?secure=anr6uIPoTtyCTvWtbAg1Pg==,1792206059" type="video/mp4">
</video>
```

**三档固定：480p / 720p / 1080p。** 五个不同 id（408706 / 408704 / 408316 / 408315 / 406534）全是这三档，一个不多一个不少。缺档的情况没见到——但按 id-画质 拼 URL 时不要假设，从 DOM 里读。

**不是 HLS**。站点引了 hls.js，但这几个 id 全是 mp4 直链，`.m3u8` 在整个页面里 0 命中。hls.js 是给别的片源留的后路。

### 4.2 `secure` 参数

```text
?secure=<base64 22 字符>=,<unix 秒>
         └─ 尾部 == 是 Java Base64 风格
```

实测的四种改法：

```text
原始签名（从 DOM 抠下来，原样重放）              → 206 video/mp4   ✅
去掉 ?secure 整条                               → 403 text/html   ❌
secure=AAAAAAAAAAAAAAAAAAAAAA==（保留时间戳）    → 403             ❌
真实签名 + 把时间戳往前挪 100000 秒              → 403             ❌
```

结论两条：

1. **签名绑路径**（换 id 段或不带 ts 都过不去）
2. **签名绑时间戳**——签名本身对 ts 做了绑定，改 ts 等于验证失败

`secure` 是服务端签发的，客户端算不出来。**不要试图去逆向签名算法**——没有意义，因为签发的那个值就在页面里白给。

### 4.3 有效期：两种签名，两个量级

同一次会话里量到的：

```text
播放 mp4 的 ts     1792206059   -  now 1792163976  =  +42083 秒   ≈ 11.7 小时
封面图的 ts        1794786728   -  now 1792163984  =  +2622744 秒 ≈ 30 天
首页卡片封面 ts    4855471889   -  now 1792163984  =  +3063307905 ≈ 97 年
```

三点读法：

- **播放链接 ≈ 12 小时**。够一次会话，不够当持久化源用
- **封面 30 天 ~ 97 年**。列表页的封面签名长效，**可以安全进缓存**
- 三个量级并存说明**签名策略是按资源类型分档的**，不是全局 TTL

### 4.4 工程结论

```text
封面  → 抠下来直接存缓存，30 天不用管
播放  → 每次播放现抓详情页，不能缓存、不能预取、不能批量
```

这决定了适配器的形状：`/api/videos/{id}/play` 必须是**一次实时 HTTP**，不能走任何缓存。项目里 `AgedmAdapter` 有 `DETAIL_CACHE`（12 条 LRU）——**hanime1 不能照搬那个缓存去做播放**，详情元数据可以缓存（比如 10 分钟），播放地址必须穿透。

### 4.5 播放器参数（Plyr）

```js
new Plyr('video', {
  speed: { selected: 1, options: [0.5, 0.75, 1, 1.25, 1.5, 2] },
  quality: { default: 720 },
  seekTime: 5,
  i18n: { caption: '字幕', quality: '畫質', speed: '速度' }
})
```

对着我们 App 的播放能力看：倍速 0.5–2 ✅、画质三档 ✅、seek 5 秒 ✅。**字幕那条线它有我们没有**（`captions: '字幕'`），如果后面要做字幕，这个站可以作为第一个样本。

## 五、坑清单

1. **列表页形状 ≠ 首页形状**。首页是 `.video-item-container > .horizontal-card > a.video-link`，列表页是 `.home-rows-videos-div > .video-card-inner`。写一个选择器搞定两边的想法行不通，要么两条腿，要么统一按「`a[href*="watch?v="]` 往上找最近的图文容器」这个形状无关的做法。
2. **广告卡混在列表里**，且长得和真卡一模一样。`href` 必须校验 `watch?v=(\d+)`，光看 `class` 会中招。
3. **翻页越界返回 200 + 空列表**，不是 404。判空页要看条目数。
4. **`?sort=` 是排序，年份下拉不是**。把年份当排序做，界面会变成一堆「2026 年」的胶囊。
5. **标签串要从 `twitter:description` 里剥**，两头有标题和 `- Hanime1`，且画质词（`1080p`）混在里面。
6. **播放签名约 12 小时过期**。缓存播放地址 = 用户明天点开 403。
7. **签名不可自算、不可重放变体**。四种改法全 403，只能原样透传页面里那串。
8. **媒体和封面同域** `vdownload.hembed.com`，`allowedHosts` 只填一条即可——但**端口不能写进去**，这是 `SiteProfile.coverUrl()` 的硬闸。
9. **详情页那个 `data-poster` 是 `null` 属性的坑**：`<video id="player" data-poster="…">` 在部分页面上 `video.poster` 读出来是空，得读 `data-poster` 属性或直接落回 `og:image`。
10. **`referrer: no-referrer`** 是站点自己声明的。我们转发请求时**不要加 Referer**，虽然实测加了也不拦，但跟站点声明反着来没必要。
11. **Cloudflare 卡 TLS 指纹，不卡 Cookie。** curl 补全所有浏览器头也是 403；换成任意一种浏览器指纹立刻 200。所以「拿 curl 试了一下不行」**不能**得出「这个站封了」的结论——反过来，「浏览器里能跑」也不能得出「安卓能连」。这是两套 TLS 栈的差别，见第二节。
12. **媒体域和页面域是两条完全不同的链路。** 页面过 CF、媒体不走 CF（CDN77 的对象存储，裸客户端 206，还带 `access-control-allow-origin: *`）。所以「页面拉不到」和「片子能不能播」是两个独立问题，别把前者的失败当成后者的结论。
13. **列表页和首页的字段量不一样**（实测）：首页横向卡有 duration / 点赞率 / 上传者，列表页的竖卡**只有封面和标题**。这是站点的形状，不是解析失败——前端拿到空串应当是「不画那个角标」。
14. **`let allIds = [...]` 有 96 个 id，不是 12 个。** 站点把「全部影片」的滑动列表塞进了同一个变量，前 12 个才是真·相关推荐（和 DOM 里那 12 个链接对得上）。不截断的话前端会画一条 96 张的空卡长龙。

## 六、和我们现有架构的接口

### 6.1 适配器归属

按项目里「**一个适配器覆盖一个族**」的规矩（`CmsAdapter` 是苹果CMS族、`AgedmAdapter` 是AGE动漫），hanime1 是**单站适配器**，因为：

```text
数据源        HTML（不是 JSON）
播放          内联 <source> + 服务端签名
元数据        OG meta
```

这三条没有第二条同族站能共享。写法参照 `AgedmAdapter`：`adapter: "hanime1"`，在 `AiiHttp.get()` 里分流。

### 6.2 路径词汇表该怎么落

| 我们的路径 | 落到 hanime1 的 |
|---|---|
| `/api/home` | `GET /` → 抠卡片，取前 N 个区 |
| `/api/videos?cate_id={cateId}&page={page}` | `GET /search?genre={cateId}&page={page}` |
| `/api/videos/{id}` | `GET /watch?v={id}` → OG meta + tags |
| `/api/videos/{id}/play?ep={episode}` | **实时** `GET /watch?v={id}` → 抠 `<source>`，按 ep 选档 |
| `/api/search?q={keyword}&page={page}` | `GET /search?query={keyword}&page={page}` |
| `/api/tags` | 固定表（10 个 genre） |

`ep={episode}` 在这里不是「第几集」（这是个单集站），而是**画质档位**：`ep=480/720/1080`。这点要在适配器头上写清楚，不然下一个人会以为是分集。

### 6.3 三个必须守住的边界

```text
① 播放地址零缓存 —— 这是签名的要求，不是性能取舍
② 请求不带 Referer —— 站点声明了 no-referrer
③ 分页判空看条目数 —— 越界是 200 不是 404
```

### 7.5 真机抓出来的四个 bug（都已修，代码在仓库里）

真机测试的价值就在这儿 —— 这四个静态分析和离线回归**一个都发现不了**。

**① 详情 404：`HTTP 404 @ https://hanime1.me/api/videos/408707`**

首页好的、详情挂。原因在 `SiteRepository.detail()` 那段 smali：它会把**相对路径拼上 origin** 再交给 `AiiHttp.get()`，于是适配器分流的 `startsWith("/api/")` 全部落空，请求真的发到了 `hanime1.me/api/videos/408707`。

对 cms / agedm 没暴露，是因为那两家的 `origin` 是空的（拼完还是 `/api/...`），而 hanime1 的 origin 是 `https://hanime1.me`，正好踩中。

修法：`AiiHttp` 里加 `stripOrigin()`，把同 origin 的绝对地址还原成内部动作路径再分流。没选「把 origin 留空」，因为配置是自动生成的、用户改不了，而且 origin 还有别的用处。

**② 分类页 403：`HTTP 403 @ https://hanime1.me/watch?v=`**

注意**等号后面是空的** —— id 丢了。

`Hanime1Adapter.fetch()` 原来是「有 `/play` 就播放，否则一律详情」，于是 `/api/videos?cate_id=X&page=1` 这条**分类列表**掉进了 `detail()`，`videoId()` 从一个没有 id 段的路径里解出空串。

修法：加 `cate_id` 分支，且它必须排在详情之前（三个动作共用 `/api/videos` 前缀）。

**③ 播放 `MediaError 4`（SRC_NOT_SUPPORTED）**

地址和签名都对、手机上裸 curl 也是 `206 video/mp4`、编码是 `ftyp isom` + `avc1`（H.264）、`moov` 在文件头（faststart）—— 服务器侧挑不出毛病。挂的是 **WebView 自己发的那个请求**。

修法：把 `hembed.com` 加进 `MediaProxy.HOSTS`，让媒体请求被接管、走 OkHttp 强制 HTTP/1.1。修完日志里出现 `[media] 媒体代理 206 http/1.1`。

⚠️ 这条和 bilibili 那族**成因不同**：bilibili 是 CDN 的 h2 后端不认签名（服务端 403），hembed 是服务端全对、只有 WebView 发出去才挂。注释里写清楚了，别合并成一条。

**④ 详情页「正在加载…」不消失**

实际上 `/api/videos/408297` 早在 561ms 就 `ok` 了，是前端没更新状态。这个和上面三个不同 —— 它**不影响功能**（画面照常出来），是渲染时序问题。留给下一轮，见 TODO。

### 8.1 站点侧：240 个标签，7 个分区

| 人物關係 | 9 | 近親 / 姐 / 妹 / 母 / 女兒 / 師生 / 青梅竹馬 |

DOM 结构：

```html

<label class="hentai-tags-wrapper">
  <input name="tags[]" type="checkbox" value="無碼"/>
  <span class="checkmark">無碼</span>

```

**它不是一个「标签 → URL」的表，而是一个多选表单**（`<form id="hentai-form" method="get" action="/search">`）。

### 8.2 标签查询的正确姿势（两个坑）

```text
GET /search?genre=裏番&tags%5B%5D=巨乳&page=2
     └─ 必须有    └─ 方括号必须编码   └─ 页码
```

**坑一：`tags[]` 的方括号要编码成 `%5B%5D`。** 直接写 `tags[]=` 有时会被
中间层吃掉，表现是「点了标签出来的还是默认列表」。

**坑二：不能只给 `tags[]`、不给 `genre`。** 实测 `/search?tags[]=巨乳`（无 genre）
返回默认全站列表，标签像没生效。带上 `genre` 才对 —— 对照实验：

```text
裏番（无标签）          41 张   checked=[]
裏番 + tags[]=巨乳      41 张   checked=['巨乳']   ← 巨乳覆盖面广，数量没变
裏番 + tags[]=拳交      35 张   checked=['拳交']   ← 从 41 掉到 35，过滤生效的铁证
```

所以 `listingByTag()` 里默认挂一个 `GENRES[0]`（裏番）当 seed —— 那是**兜底
不是筛选意图**，站点要求有 genre 才认真过滤标签。

### 8.3 接进 App 时踩的两个坑（都是静默失败）

**坑三：`adaptTags` 只认 code → 映射表这一条路。**

`adapters.js` 原代码：

```js
group: TAG_GROUP_BY_CODE[code] || 'other'      // ← 标签自带的 group 被完全忽略
```

走适配器的源（cms / agedm / hanime1）已经在 Java 侧把最终组名算好了，只要
code 不在那张表里，**240 个标签全部折进 other**，页面一片空白。

修法：`const own = tag.group`（**直接读属性，不用 `pick()`** —— pick 走
`web.fields` 别名表，而 group 是算好的最终值不是候选名；往 fields 里塞会被
`build.sh` 的字段自检当场拦下）。

**坑四：`renderTags()` 在非 private 模式下不看配置。**

```js
// 原代码
const sections = privateMode() ? (siteUi().tagGroups || []) : [['short','短剧类型'],['comic','漫剧类型']];
```

而 `privateMode() === (contentSource === 'huangguo')` —— **只对内置黄果源为 true**。
所以**所有用户自带源**都被按死在那一对短剧/漫剧分组上，配置里写什么 tagGroups
都没用。症状极具误导性：接口明明拿到 240 个标签（右上角就写着「240 个标签」），
页面却是空的，而且不报错。

修法：配置优先，没配才退回内置。

```js
const configured = siteUi().tagGroups || [];
const sections = configured.length ? configured
  : (privateMode() ? [] : [['short','短剧类型'],['comic','漫剧类型']]);
```

### 8.4 配置层怎么接

`wrapHanime1()` 生成的 `ui`：

```json
"popularTags": [["中文字幕","中文字幕"],["巨乳","巨乳"],["JK","JK"],["純愛","純愛"],
                 ["NTR","NTR"],["校園","校園"],["後宮","後宮"],["3P","3P"]],
"tagGroups":   [["hanime-attr","影片属性"],["relationship","人物关系"],
                 ["hanime-role","角色设定"],["style","外貌身材"],
                 ["setting","情境场所"],["plot","故事剧情"],
                 ["hanime-act","性交体位"],["other","其他"]]
```

两处要点：

- **`tagGroups` 的 code 必须和适配器交上来的 `tag.group` 一字不差**。对不上的组
  会被前端整组丢掉 —— 不报错，页面上少一块。所以 `TAG_SECTIONS` 是唯一来源：
  适配器的 `groupCodeOf()` 和 `wrapHanime1()` 的 tagGroups 都从它生成。
- **`other` 一定要留着**。站点改字形（繁→简、改名）时认不出的分区会折进
  `other`，没这一组就等于整批标签人间蒸发。
- **首页胶囊不从头截**。前 9 个标签全是「無碼 / AI解碼 / 中文字幕」这种规格词，
  一眼看去像一排设置项。每个分区轮着挑一个。

### 8.5 标签的路径

```json
"tag-list": "/api/videos?tag={slug}&page={page}&size={size}"
```

**用 `tag=` 不是 `cate_id=`。** 站点那边 `genre=` 和 `tags[]=` 是两套东西：
`cate_id` 走 10 个大方向，`tag` 走 240 个细标签。走错了不报错，只是「点标签
出来的还是默认列表」。`Hanime1Adapter.fetch()` 按参数名分流，两条路共用
`/api/videos` 前缀，所以**判断顺序是 tag → cate_id → play → detail**，不能换。
