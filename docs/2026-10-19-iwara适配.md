# Iwara 适配（2026-10-19）

`https://www.iwara.tv/` 逆向 + spider 接入。交付一个 json + 一个 js，跑通离线回归，
市场清单已更新。

## 一、先定形态：盾后站，而且是「含 api 一起在盾后」

`curl` 打三个地址（带完整安卓 Chrome UA）：

| 地址 | 结果 |
|---|---|
| `https://www.iwara.tv/` | 403，5456 字节，`Just a moment...` |
| `https://api.iwara.tv/videos?page=0` | 403，5531 字节，同一个挑战页 |
| `https://i.iwara.tv/image/thumbnail/…/thumbnail-03.jpg` | **200，7266 字节，image/jpeg** |
| `https://files.iwara.tv/` | 404，29 字节 `{"message":"errors.notFound"}`（应用层，不是盾） |

所以配置分成两半：

- `web.shield` 罩住 `iwara.tv`（一条后缀就把 www / api / filesq / 三十来个 CDN 别名全包住）；
- 封面域名 `i.iwara.tv` **不进** shield —— 它没盾，走普通 okhttp 就行。塞进去只会让首屏
  每张封面都去排队抢 WebView。

判断依据还是那条：能不能用 `curl` 拿到内容。封面能，页面和接口不能。

## 二、接口面

全部在 `api.iwara.tv`，都是 JSON。五个能用，两个是坑。

| 用途 | 请求 | 返回 |
|---|---|---|
| 列表 | `GET /videos?sort=<date\|trending\|popularity\|views\|likes\|recent>&rating=all&page=N&limit=M` | `{count, limit, page, results[]}` |
| 搜索 | `GET /search?type=videos&page=N&query=Q&limit=M` | `{page, count, limit, results[], type:"videos"}` |
| 详情 | `GET /video/{id}` | video 对象 + `fileUrl` |
| 播放清单 | `GET <fileUrl>` | `[{name, src:{view,download}, type}]` |
| 标签过滤 | `GET /videos?tags=<tagId>` | 同列表 |

实测数字（2026-10-19 23:00 前后）：

- `limit` 上限 **50**（给 100 也只回 50），默认 32；
- 搜索 `hatsune miku` → `count: 1566`，`limit: 32`；
- `page` **从 0 开始**；
- 排序六个值都真的生效（`sort=date` 和 `sort=recent` 是**两套不同结果**；
  `sort=zzzz` 这类无效值会静默退回默认，不报错）。

## 三、四个坑（每个都真踩了）

### 3.1 盾后回填给的是 `outerHTML`，不是响应体

这条最要命。`ctx.net` 打到盾后域时，主进程用真浏览器**导航**过去，把
`document.documentElement.outerHTML` 交回来（`SiteFetchWebView.doFetchByNav`）。
对 HTML 页正好是页面；对 JSON 接口，Chromium 会把它渲染进 `<pre>`：

```
<html><body><pre>{"count":33,"limit":32,"page":0,"results":[…]}</pre></body></html>
```

实测那个文档：`body` 的第一个子节点是 `PRE`，`textContent.length` 正好 1560 =
JSON 长度，一个字不多。所以 `JSON.parse(r.body)` 必炸。

`iwara.js` 里 `unwrap()` 按三种形态兜：

1. 首字符是 `{`/`[` → 裸 JSON，直接用；
2. 有 `<pre>` → 取里面再解 HTML 实体（顺序：`&amp;` 必须最后解）；
3. 都没有 → 首个 `{` 到末个 `}` 硬切，切出来先 `JSON.parse` 验一遍再返回。

第 3 条是兜底，不是主路：真机上见过一次 `pre` 因为标题里带 `</pre>` 被截断，
那条走的就是硬切。

### 3.2 `/videos` 的 `count` 是假的

```
page=0 limit=10 → count 11, results 10
page=1 limit=10 → count 21, results 10
page=2 limit=10 → count 31, results 10
```

恒等于 `page*limit + n + 1`。拿它算「还有没有下一页」会让用户永远滑不到底。
真正能用的判据是 **`results.length === limit`**。

而 `/search` 的 `count` 是真的（1566、325702）。两个接口语义不一样，所以
`listResult()` 按 `type === "videos"` 分流：搜索用 count 算，列表按满页算。

### 3.3 `/videos?search=` 是无效的

参数被忽略，原样回默认列表 —— 连 `?search=zzzzqqqxy` 都回一模一样的 16597 字节。
真正的检索端点是 `/search?type=videos&query=`。这个坑很隐蔽：不比对响应体的话，
会以为「搜索功能正常，只是这个关键词没结果」。

### 3.4 标签过滤能用，但 `tags=mmd` 是站方的数据坏了

`GET /videos?tags=<tagId>` 确实过滤（`tags=koikatsu` 和 `tags=genshin_impact`
返回的是两套不同结果）。但 `tags=mmd` 直接 **HTTP 500 `errors.serverError`** ——
站点自己点标签页也 500（网络面板里那条 `?rating=all&tags=mmd&sort=date` 就是 500）。
所以源里对「分类页解析不到卡片」给的错误信息专门提了这句，免得下一个人以为是参数拼错。

## 四、播放：两跳，而且第二跳的主机名每次都不一样

```
GET /video/{id}          → fileUrl: https://filesq.iwara.tv/file/{fileId}?expires=…&hash=…
GET fileUrl              → [{name:"360",   src:{view:"//bailu.iwara.tv/view?hash=…"}},
                            {name:"preview", src:{view:"//blade.iwara.tv/view?hash=…"}}]
```

**`fileUrl` 不是视频**，是一份清晰度清单。把 `fileUrl` 直接交给播放器，表现是
「播放器一闪就报格式不支持」，因为它拿到的是 JSON。真正能播的是 `src.view`
（协议相对，要补 `https:`）。

`src.view` 的主机名是站点从固定池里**随机**挑的 —— 同一条视频连打两次，一次
`asta/blade`，一次 `phoebe/clara`。抽了 120 条视频的清单，共出现 13 个不同主机：

```
acheron aiko asta bailu blade bronya camellya clara firefly hanya herta hime
himeko hook jade kafka lumi mikoto naja pela phoebe robin silverwolf sparkle
topaz welt youhu yukong zani
```

全是星铁 / 绝区零 / 原神的角色名。DNS 是 wildcard（`198.18.0.x`，代理的假 IP），
所以「名字存不存在」只能靠 HTTPS 探：真主机回 403，假名字 TLS 直接失败。

这引出两条硬约束：

- `__spiderSite.hosts` 和 `http.hosts` 都是**精确匹配**（`host.equals`），
  所以两个池子得列全。漏一个的表现是「能看详情、点播放报主机不在白名单」；
- `web.shield.hosts` 是**后缀匹配**（`host.equals(h) || host.endsWith("." + h)`），
  所以写一条裸域 `iwara.tv` 就罩住了全部，包括将来新出现的 CDN 别名。这是这个源
  能扛住随机主机名的唯一原因。

单独验过：从 `www.iwara.tv` 页面里用 `XMLHttpRequest`（`withCredentials = true`）
打 `acheron.iwara.tv/view?hash=…`，回 **200 / video/mp4 / 14.7MB**，响应头里
只有 CORS 安全列表那几个（`cache-control` / `content-length` / `content-type` /
`expires` / `last-modified`）—— 这正是「跨源请求成功、但没 expose 额外头」的指纹。
也就是说 `SiteFetchWebView.fetchBytes` 那条路（页面内 XHR 取流）对这个 CDN 是通的。

## 五、配置要点

`iwara.json`：

| 项 | 值 | 为什么 |
|---|---|---|
| `origin` | `https://www.iwara.tv` | 裸域，无路径无 query |
| `cover.allowedHosts` | `["i.iwara.tv"]` | 封面和原图都在这个域，它没盾 |
| `web.shield.hosts` | `["iwara.tv"]` | 后缀匹配，一条罩全 |
| `web.shield.warmup` | `https://www.iwara.tv/videos` | 最轻的列表页 |
| `http.hosts` | 31 条（filesq + files + 29 个 CDN） | 精确匹配，必须列全 |
| `net` | 不写 | 跟随全局代理开关。这个站在墙外，用户要开代理 |

`iwara.js` 的 `hosts` 只列两个：`api.iwara.tv` 和 `filesq.iwara.tv`。
封面不经 `net`（由 App 的封面通路取），CDN 也不经 `net`（播放地址是**交出去**的，
不是源自己拉的），所以没必要列。

## 六、验证

离线回归（`node scripts/spider-check.js …/iwara.js`）：**25 条断言全绿**。

```
✓ home 8 条   ✓ category 3 条   ✓ search 3 条   ✓ detail 6 条   ✓ play 5 条
```

其中 `home` 的夹具**故意做成盾后回填形态**（JSON 包在 `<pre>` 里、外面还有
`<html><body>`），因为真机上拿到的就是这个形状 —— 不做成那样，`unwrap()`
那半边永远没人验。`search` / `detail` 用裸 JSON，两条路都覆盖。

断言盯的是几个容易悄悄坏掉的点：

- 首条 id 是 `0bmwbE50acZY4B`（比对真实首条，不是「长度大于 0」）；
- 32 张卡满页 + `hasMore === true`；
- 自定义封面走 `/image/original/`（`FqzgOSpbK2hwsY` 那条有 customThumbnail）；
- 缩略图序号两位零填充（`thumbnail-\d{2}\.jpg`，实测有 `thumbnail-00`）；
- 时长 494 秒 → `8:14`；
- 播放两档、默认是 `360` 不是 `preview`、`url` 落在 `alts` 里、
  **没把 `filesq…/file/` 那个清单地址当播放地址**。

全量回归 `node scripts/spider-all-check.js`：**10 个源，10 个配了回归，10 个全过**。

## 八、还没验的：真机

这台机器上的设备 `7f8f5254` 停在锁屏（需要 PIN），装源那一步走的是设置页 UI，
所以**真机链路一次都还没跑**。离线沙箱证明的是「解析对不对」，没证明的是这三件：

1. 主进程 WebView 过 `api.iwara.tv` 的挑战要多久（missav 实测 0.5~3 秒，
   但这个站 api 是独立子域，clearance 可能不共享，得现过）；
2. 盾回填的 JSON 页会不会被 `looksLikeChallenge` 误判 —— 从代码看不会
   （只认 `Just a moment` 和 `_cf_chl_opt`），但没在真机上看过；
3. `fetchBytes` 走页面 XHR 拉 CDN 分片，对 100~300MB 的整文件是什么表现。
   这是真风险：这个站是**渐进式 MP4**，不是 missav 那种几百 KB 的 HLS 分片，
   而 `serveFromWebView` 是一次性把整个文件读进 `byte[]` 再 base64 过桥。
   100MB 的视频 = 100MB 字节数组 + 133MB base64 字符串，低端机会 OOM。

第 3 条如果真机上报内存或黑屏，方向是把 `VlcRelay.serveFromWebView` 改成带
`Range` 分段取，而不是整块吞。那属于播放层改动，不在这次的源里。

装好之后看这三行日志就够定位：

```bash
adb logcat -s HG.Spider
# cap=__meta ok … caps=["home","category","search","detail","play"]
# op=net 命中过盾回填（api.iwara.tv，52xxx 字节），跳过网络
# cap=home ok ms=…
```

如果首页出卡、详情能开、点播放黑屏，先看 `adb logcat -s HG.Spider | grep relay`：
分片有 200 说明链通了，问题在解码或 key 那一跳；分片直接 403/超时才是域名没放行。

顺带纠正一个我自己先写错的说法：`http.hosts` **不参与 VLC 播放**。
全仓只有 `hxm/http.js` 会走 `AndroidHost.http` 那条桥（`PlaybackHttpBridge`），
那是 App 自己 JS 播放器用的；spider 源把地址交给 VLC 之后走的是 `VlcRelay`，
而 `VlcRelay` 里对 `PlaybackHttpBridge` 的引用数是 **0**。所以这张表目前是
「声明了但不生效」——仍然该写（将来接回去就对了），但它不会成为播放失败的原因。
