# Pornhub 适配（2026-10-19）

`https://cn.pornhub.com/` 逆向 + spider 接入。和服务端渲染的那一类站同一个形状：
没有盾、没有 JSON 接口，全靠字符串解析。

## 一、形态：不是盾后站

裸 curl，带安卓 Chrome UA：

| 地址 | 结果 |
|---|---|
| `https://cn.pornhub.com/` | 200，1,014,179 字节，2.07 秒 |
| `https://cn.pornhub.com/video` | 200，1,081,624 字节 |
| `https://www.pornhub.com/` | 200，1,007,029 字节 |

所以配置里**没有 `web.shield`**，也不需要真浏览器内核。顺手把它的 `/api/v1/*`
系列全试了一遍：

```
/api/v1/video/search?search=test&page=1   404（643,910 字节的「没发现页面」HTML）
/api/v1/videos?page=1                     404
/api/v1/video/test                        404
```

公开面没有 JSON 接口。这个站的 HTML 里塞了大量 `<script>` 块，但列表数据本身
是服务端渲染进 DOM 的，不是 JSON 再水合 —— 所以还是得解析标记。

## 二、列表：三处结构不一样

同一张卡在三个入口下的标记**不完全一致**，这是这个源最容易踩空的地方。

列表页（`/video`、`/video?c=<分类>`）：

```html
<li ... data-video-id="492669475" data-video-vkey="6acb28161c796">
  <a href="/view_video.php?viewkey=6acb28161c796" data-poster="https://pix-fl.phncdn.com/…">
    <img class="videoThumb js-videoThumb" src="https://pix-fl.phncdn.com/…">
    <div class="duration thumbOverlay hideInUserStream"><span class="time">15:10</span></div>
  </a>
  <div class="title"><a href="…">标题</a></div>
</li>
```

搜索页（`/video/search?search=`）只差两处，但两处都足以让正则全部落空：

| | 列表页 | 搜索页 |
|---|---|---|
| 时长 span | `<span class="time">` | `<span class="bgEffect time">` |
| 标题 `<a>` | 无额外 class | `class="thumbnailTitle"` |
| 播放量 | 无 | `<div class="videoViews">1.9M</div>` |

所以源码里所有正则都写成「class 里含这个词」（`class="[^"]*\btime\b[^"]*"`），
不写死整串。按整串匹配的话搜索页一张卡都解析不出来，而表象是「搜索没有结果」——
这种最难查。

**卡片 id 取 `data-video-vkey`，不是 `data-video-id`。** 详情和播放都走
`/view_video.php?viewkey=<vkey>`，用数字 id 还得再查一次映射。vkey 是 13 位十六进制。

## 三、切卡片：右边界必须取 `</li>`

`split('data-video-vkey="')` 之后，每段开头是本卡 vkey、后面一直延伸到文档末尾。
如果把整段拿去跑正则，**某张卡缺标题时正则会一路吃到下一张卡的标题** ——
卡片会「串位」，而字节数一切正常，肉眼看不出。

所以每段再用 `</li>` 截断。实测 9 个页面 297 张卡，切出来和 `data-video-vkey`
计数完全一致（297 / 297）。

## 四、分页：只认 `rel="next"`

`?page=N`，从 1 开始。判据不能数卡片：

| 页 | 卡片数 |
|---|---|
| `/video` 第 1 页 | 31 |
| `/video?page=3` | 43 |
| `/video/search?search=asian` | 29 |
| `/video?page=9999`（越界） | 25（推荐位） |

张数不固定，越界页还照样有 25 张推荐卡。真正可靠的是 head 里那一行：

```html
<link rel="next" href="https://cn.pornhub.com/video?page=2" />
```

非末页一定有，末页没有。这个判据必须准 —— 越界翻页站点回的是 **HTTP 404**，
而 `net` 对非 2xx 直接抛错，判错一次用户看到的就是错误块而不是「到底了」。

## 五、封面：签名地址 + 图床轮换

封面是**带签名的临时地址**：

```
https://pix-fl.phncdn.com/c6531/videos/202610/15/65910485/original_65910485.mp4/plain/ex:1:no/bg:0:0:0/rs:fit:480:270/vts:644?hdnea=st=1792425023~exp=1792511423~hdl=-1~hmac=…
```

`exp` 比 `st` 晚 **86400 秒**（24 小时），过期后这张图就 403。列表每次拉都是新签名，
所以不影响使用 —— 但如果哪天做了卡片缓存，超过一天的那批会全灰。

主机在图床之间轮换，抽了 9 个页面 + 详情页，出现过的：

```
pix-fl  pix-cdn77  pix-egi  ei  ew  ev  kw  ss  cdn1-smallimg   （都是 .phncdn.com）
```

`cover.allowedHosts` 是**精确匹配**（`SiteProfile.coverUrl` 逐条 `equals`，没有后缀
匹配），所以配置里 9 个全列了。漏一个的表现是那张卡灰块 —— 不会报错，也不会崩。

## 六、播放：详情页里的 `flashvars`

详情页有一段 `var flashvars_<数字> = {…}`，是个**合法 JSON**（实测 16 条视频全部
能 `JSON.parse`），里面有：

```
video_title       "Japanese sexy Yume Hoshino is sucking a hard cock before having sex."
video_duration    910                                    ← 秒
image_url         https://pix-cdn77.phncdn.com/…         ← 封面（签名）
mediaDefinitions  [{quality:"1080", format:"hls", videoUrl:"…/1080P_4000K_….mp4/master.m3u8?…"}, …]
```

四档 HLS：**1080 / 720 / 480 / 240**。地址主机在 `XX-h.phncdn.com` 这个形状里轮换 ——
16 条视频抽到 `em-h` / `hm-h` / `im-h` / `km-h` 四个。

master m3u8 只有 240 字节、一条 `#EXT-X-STREAM-INF`：

```
#EXTM3U
#EXT-X-STREAM-INF:…,RESOLUTION=1920x1080,…
index-v1-a1.m3u8?validfrom=…&validto=…&hash=…
```

子列表 14,051 字节、分片是 `seg-1-v1-a1.ts?…` 这种**相对路径**，跟 master 同目录
同主机。VlcRelay 里那套「相对路径改写成绝对地址再包一层中继」的逻辑正好用得上，
不用改播放层。

**`mediaDefinitions` 里那条 mp4 别用。** 它长这样：

```json
{"quality": [], "format": "mp4", "videoUrl": "https://cn.pornhub.com/video/get_media?s=<base64>"}
```

实测直接 GET 回来是 `[]`（两个字节）。它要配合会话里的一次性 token 才给东西，
而 HLS 那四档是现成可播的。源码里 `altsOf()` 只收 `format === "hls"` 的项。

## 七、搜索：关键词必须编码

`/video/search?search=大奶` 裸传中文 → **HTTP 400**（2,942 字节的错误页）。
`encodeURIComponent` 之后就正常。这种失败在真机上表现为「搜一次报错，搜英文就没事」，
很容易被当成站点抽风。

## 八、分类

`/categories` 页面里 96 个分类，形如 `<a href="/video?c=111">日本人 75,650 Videos</a>`。
配置里 key 用数字 id、名字去掉尾巴上的计数。另外加了一个约定 slug `new` =
「不带分类的全站最新」，这样类型页也能有「最新」这一格。

注意 `/categories/asian` 是 404，`/video?category=asian` 会 301 回 `/video` ——
分类只有一个入口：`?c=<数字>`。

## 九、验证

离线回归 `node scripts/spider-check.js …/pornhub.js`：**24 条断言全绿**。

```
✓ home 7 条   ✓ category 3 条   ✓ search 4 条   ✓ detail 5 条   ✓ play 5 条
```

夹具是从真实页面**裁**出来的，不是造的：1MB 的页面塞仓库太重，所以只留两段 ——
前 100KB（含 `<link rel="next">`）和头 12 张卡的原始标记。卡片标记一字节没改，
等价于跑整页。

断言盯的是几个会悄悄坏掉的点：

- 首条 id 是 `6ad1206973670`（vkey，不是数字 id），且全部符合 `^[0-9a-f]{13}$`；
- 时长 `15:10`；
- 搜索页首条是中文标题「整张床…」+ 播放量 `1.9M` —— 这两个都只在搜索页那套标记里，
  能读出来就说明 `bgEffect time` 那条分支没漏；
- 播放四档、默认 1080P、`url` 落在 `alts` 里、**给的是 m3u8 不是 `/video/get_media`**。

全量 `node scripts/spider-all-check.js`：**11 个源，11 个配了回归，11 个全过**。

## 十一、还没验的

真机一次没跑（设备停在锁屏，装源要过设置页 UI）。离线沙箱证明的是解析对，
没证明的是这些：

1. 首屏 30 张卡片的封面会不会因为签名地址或图床白名单漏项而半数灰块；
2. 43 张/页的列表在真机上解析耗时（纯字符串，应该几十毫秒，但没量过）；
3. HLS 这条链在播放层是不是顺 —— 子列表和分片都是相对路径，missav 那条已经
   证明能改写，但这个站的 URL 带 `validfrom/validto/hash` 三个 query，改写时
   要保证 query 不丢。

装好后看这几行就够定位：

```bash
adb logcat -s HG.Spider
# cap=__meta ok … caps=["home","category","search","detail","play"]
# cap=home ok ms=…
```

封面灰块补 `cover.allowedHosts`。播放黑屏先看 `adb logcat -s HG.Spider | grep relay`
的分片状态码 —— `http.hosts` 只在 App 自己的 JS 播放器（`hxm/http.js` → `PlaybackHttpBridge`）
那条路上生效，VLC 这条（`VlcRelay`）根本不读它，所以它不会成为播放失败的原因。
