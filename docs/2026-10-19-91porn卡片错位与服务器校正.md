# 91porn：卡片货不对版，以及为什么校正必须放到服务器（2026-10-19 下午）

用户报「点进去，标题、描述、封面、视频内容全变了」。这不是随机换片（那个 2026-10-18
就用游客标记修过），是**列表卡片的标题和封面被站点挂到了别的 viewkey 上**。

---

## 一、取证：错的是列表，不是详情

对同一个 viewkey 连取三次详情，结果稳定：

```
viewkey=1536834169  标题「怪兽酒馆之超级可爱的奈奈美！」  封面 thumb/1252788.jpg
                    ×3 次完全一致
```

再看列表页里这张卡：

```html
<a href=".../view_video.php?viewkey=1536834169&page=1&c=auyklk&viewtype=basic&category=ori">
  <div class="thumb-overlay" id="playvthumb_1253049">
    <img class="img-responsive" src="https://1729130453.rsc.cdn77.org/thumb/1252773.jpg" />
    <span class="video-title">[原创] 调教07母狗之sp抽屁股之惩罚，完整版主页</span>
```

三个值指向三部不同的片：容器 id 是 `1253049`（另一条卡片的封面号）、封面是 `1252773`、
标题是「调教07」—— 而「调教07」的真身是 `viewkey=1514471335`（封面 `1252737`）。

**再抓一次同一个分类页，23 条里有 4 条标题变了。** 也就是说错位是每次渲染重新洗牌的，
不是固定映射，没有任何「照表恢复」的余地。

真机复现 5 条错 2 条；用 `tagList(hot)` 原始输出和详情真值对齐量了一遍：**24 条错 5 条**
（20.8%）。

## 二、为什么不能在手机侧做校正

Java 时代的做法是在手机里开 4 个线程并发拉详情（`/api/reconcile`）。搬到 spider 之后
照着写，直接踩死：

```js
var WORKERS = 8;
async function worker() { while (cursor < ids.length) { await fetchDetailPage(...) } }
await Promise.all(workers.map(worker));
```

看着是 8 并发，实际全串行 —— `ctx.call('net')` 是**同步桥**，JS 在渲染线程上等 Java
回包，`await` 只是把等待点挪了个位置。真机实测：

```
cap=reconcile id=porn91 src=user bytes=29318      17:24:11
[reconcile] porn91 本轮没校正：请求超时（spider） 17:24:41   ← 前端桥 30 秒先炸
cap=reconcile ok ms=42917                          17:24:56   ← 服务端 45 秒才收尾
```

45 秒，一条结果都没回来。24 条 × 单条 2.5-6 秒，串行至少 60 秒。加预算截断也只是
「每次校 6 条」，剩下的永远是错的。

所以这件事只能离开手机。

## 三、服务器侧：`/p91/reconcile`

`server/p91/reconcile.py`，纯标准库，systemd 常驻 `127.0.0.1:8092`，Caddy 路由
`/p91/*` 反代。手机只发一个请求：

```
GET https://149.104.21.177.sslip.io/p91/reconcile?ids=<24 个 viewkey>
{"ok":true,"items":[{"id","title","cover"}]}
```

三个要点：

- **并发是真的**：`ThreadPoolExecutor(8)`，冷缓存 24 条 **1.8-1.9 秒**，命中缓存 0.00 秒。
- **缓存全局共享**：12 小时，最多 5000 条。所有用户分享同一份真值，第二个人零成本。
- **单条失败只是不出现**：源那边保留原值，一张坏卡不能拖住整页。

部署：

```
/srv/p91/reconcile.py
/etc/systemd/system/p91-reconcile.service   （enable --now）
/srv/cfg/Caddyfile                          （handle /p91/* → 127.0.0.1:8092，备份 Caddyfile.bak-p91）
```

## 四、源与前端怎么配合

**源**：`porn91.js` 的 `reconcile` cap 只做「拼参数 + 请求 + 整形」，不再自己拉详情。
`hosts` 里加了 `149.104.21.177.sslip.io`（net 白名单不认就一条都发不出去）。

**前端**：`app.js` 的 `reconcileCards()` 原来对 spider 源有一句 `if (spiderIdOf()) return;`，
理由写着「spider 的卡片一上来就是真的」—— 那句话是错的，parseCards 抠的就是网格页。
现在改成看配置声明：

```json
"web": { "reconcile": true }
```

只有声明的源才问，其它源零开销。另有三处细节：

- **失败不记成「源不支持」**：超时是网络问题，记住它等于这一会话再也不校正。
  只有「spider 没有实现 xxx」才进 `reconcileUnsupported`。
- **结果落 localStorage**（`hgreconcile:<源id>`，7 天过期，最多 400 条）。校正一次，
  重启、换页、再进都不再请求 —— 否则每次开 App 都得等那 2 秒。
- **超时口径**：前端桥 30 秒，服务器 1.9 秒，余量足够。

## 六、降级

服务器不在线时 `reconcile` 返回空数组，列表回到站点原样（错几条看运气），
点进去仍然能看到真身。不会比修之前更差，也不会卡住页面。

`journalctl -u p91-reconcile -f` 能看到每次请求的行，格式
`reconcile ids=24 items=24 1.77s`。
