## 一、这五个 bug 的共同点

接一个纯 SSR 的新站，按理说最费时的是「页面结构长什么样」。实际不是：

| # | 症状 | 出错的那一层 | 我在哪儿改的 |
|---|---|---|---|
| 1 | 「这个适配器不支持按地址识别」 | `SiteAdapter.probe(String)` 的默认实现 | `YhdmSite` |
| 2 | 选集格子全部 `undefined` | `web.fields` 别名表漏 `episodeNumber` | 配置文件 |
| 3 | 上游 200，VLC `cannot peek` | `VlcRelay` 只改写 WebView 那条路的 m3u8 | `VlcRelay` |
| 4 | 选集点第 3 集，请求打到 `ep1` | 前端只传序号，站点的 ep 是字符串 | `YhdmAdapter` |
| 5 | 线路全 403 / TLS 被掐 | 全局代理把国内 CDN 也拖走了 | `DirectHosts` |

五个都不报错，全是「接口 200、日志干净、界面空着」。它们的共同点：

> **站点知识（或者说一次播放需要的信息）散落在多个互不知情的层里，
> 每层各有一份自己的假设。任何一份跟不上，症状都长成同一个样子。**

这已经不是「解析站点」的问题，是**适配器和运行环境之间的契约没有单一真相**。

## 二、契约其实有四份，只有两份有守门的

```text
           ┌──────────────────────────────────────────────┐
   站点 ──► │ ① 解析：HTML/JSON → 我们的内部键名            │  ← 有测试
           ├──────────────────────────────────────────────┤
           │ ② 别名表 web.fields                          │  ← 无测试
           ├──────────────────────────────────────────────┤
           │ ③ 路径模板 web.paths + 参数填充              │  ← 无测试
           ├──────────────────────────────────────────────┤
           │ ④ 网络路由：谁走代理、谁直连、谁绕中继         │  ← 无测试，全局静态
           └──────────────────────────────────────────────┘
```

① 每接一个站都写回归（`YhdmAdapterTest` 等）。②③④ 从来没被单独测过 ——
它们只在「真机上点一遍」时被发现，而那时候症状已经被 ① 的正常输出盖住了。

## 三、四条根治方向

### 方向 A：网络路由跟着源走，缺省直连（本次已做）

**问题**：代理三档是全局的。为了一个站开代理，所有源的 CDN 都被拖走。
`DirectHosts` 是手写白名单，只能追着域名跑 —— 樱花动漫一家就有 16 个采集站域名，
而且天天换。

**改法**：源的配置里声明「哪些域名必须走代理」，其余一律直连。

```json
"net": { "proxy": ["yhdm.one"] }
```

- 有 `net.proxy` → 只有列表里的域走代理，别的全直连（包括封面、分片、新出现的 CDN）
- 没有 `net.proxy` → 维持老行为（`DirectHosts` 白名单 + 全局开关）

这样 16 个 CDN 域名一个都不用登记。墙只挡入口域，播放 CDN 九成在境内直连最快 ——
这条经验对所有源都成立，不是樱花动漫的特例。

### 方向 B：播放失败要能自愈（本次已做）

**问题**：`VlcPlayerActivity` 拿到 `source` 就一次性交给 libVLC，`EncounteredError`
只弹一行字。中继那边明明知道是 403 还是 TLS 被掐，但只写日志，不回传。

任何探测、任何缓存、任何名单都可能错，但「播不动就换下一条」永远成立。
这是唯一能兜住「静态判断全错」的机制。

**改法**：播放 payload 带上备选线路 `alts`，`EncounteredError` 时依次换线重试
（最多 3 条，只在前 30 秒内）。

### 方向 C：缓存要带环境指纹（本次部分做）

**问题**：`urlRemember` 把 URL 缓存 8 分钟，键是 `videoId:ep`。换源、换代理、
换网络之后缓存照样命中 —— 我调试时被它骗了两次（点了播放，日志里根本没有
`/api/play` 请求）。

**改法**：TTL 降到 2 分钟；播放器报错时主动 `urlForget`。

### 方向 D：别名表和路径模板也要有守门（**已做** 2026-10-18 晚）

`AdaptersTest` 守的是「只有一份名单」。缺的两条现在补上了：

- **别名表自检**（`FieldsContractTest`）：拿真实 fixture 跑**真实解析代码**，
  再按前端 `pick()` 的规则走一遍 `web.fields`。两个方向都查：
  1. 前端会读的每个角色，声明了没有、在真实响应上取不取得到值
  2. 适配器往响应里塞的每个键，有没有哪个角色认它（防「新加字段忘了配」）

- **路径模板自检**（`NetRouteTest.路径模板的占位符都能填上`）：`web.paths` 里每个
  `{占位符}` 都要在前端的参数表里。`{episode}` 这种「模板有、前端只给数字」
  的错配，测试能当场发现。

为了能离线测响应形状，把两个方法从「取字节 + 解析」里拆了出来：

```java
static JSONObject detailFrom(id, html, base)              // 详情响应形状
static JSONObject playFrom(id, ep, videoPlays, prober)    // 播放响应形状
```

拆之前这两个方法的网络和解析是缠在一起的，测试只能测到「解析出几个字符串」，
测不到「返回的键名和别名表对不对得上」——而后者正是那个 undefined 的 bug。

**验证过它真的能拦住**：把 `fields.put("episodeNumber", …)` 删掉，三条用例同时红：

```text
详情第 1 个选集：web.fields 里没有声明角色 'episodeNumber'
播放响应：web.fields 里没有声明角色 'episodeNumber'
选集条目里的键 'episodeNumber' 在 web.fields 里没有任何角色认它
```

## 四点五、改的过程中又发现一条（比前面四条都隐蔽）

**存下来的配置是快照，适配器后来加的东西不会自己出现在里面。**

`net.proxy` 明明写进了 `YhdmSite.buildConfig`，真机上 CDN 却还在走代理。
排查了半小时才发现：那份配置是 22:42 存的，那会儿还没有 `net` 这一段。
`SiteProfile` 读的是 prefs 里的旧快照，适配器的新代码根本没被用上。

这条的症状是「新逻辑完全没生效，日志里还一切正常」——和「代码写错了」长得
一模一样，但改代码永远修不好。

修法是 `SiteAdapter.patch(config)`：`SiteProfile` 构造时调一次，适配器把
**能离线推导出来的**键补上（需要联网探的东西不能放这儿）。

```java
default void patch(JSONObject config) {}   // 默认空实现
```

这条对所有适配器都成立：以后往配置里加新块（`net`、`fields`、新的 `paths`），
老用户不用重新加源。

## 六、AiiHttp 的代理层：从字符串到值对象

**日期**：2026-10-18 晚

### 问题

代理在系统里有两种表达，翻译散在七八处：

```text
prefs 里          "socks5://u:p@1.2.3.4:1080"      字符串，UserSource 管
AiiHttp 内部       Route{Proxy, user, pass}          临时拼出来，只用一次
```

`parseProxy` / `attachAuth` / `describe` / `effectiveJavaProxy` 都在 AiiHttp 里，
四个建客户端的地方各自调一遍「解析 → 挂代理 → 挂认证」。边界靠约定：
谁知道该在哪一步校验、哪一步挂认证，全看调用方记不记得。漏了就是
「填了代理却直连」或「SOCKS authentication failed」——两种都难归因。

### 改法

新增 `ProxyRoute`（226 行），代理从「字符串」变成不可变值对象。
之后没有任何地方再碰字符串：

```java
ProxyRoute.Parsed p = ProxyRoute.parse(raw);   // 三态：直连 / 路由 / 认不出来
p.direct(); p.route; p.error;

route.javaProxy();      // 给 OkHttp 和 WebView 的 ProxyController
route.applyTo(builder); // 挂代理 + 挂认证（HTTP 走 proxyAuthenticator，SOCKS 走全局 Authenticator）
route.key();            // 缓存键，不含密码
route.describe();       // 日志，不含密码
```

`AiiHttp` 只剩 `effectiveRoute()` 一个出口。三态是必要的：`setProxy("")` 是
合法的（清空变直连），`setProxy("乱写")` 必须报错 —— 只返回 null 两者分不开，
用户填错了会静默变直连，然后「明明填了代理还是连不上」。

### 顺带：四个客户端工厂合成一个

```text
改前：client / http1Client / plainClient / plainHttp1Client / proxiedClient
      五个方法，四组 volatile 字段 + appliedXxx 记录「上次按什么参数建的」
改后：clientFor(http1, connectSec, readSec, dns, route)
      一个 ConcurrentHashMap，key 里带齐所有影响行为的参数
```

四份代码干同一件事，各自漏过不同的边：`plainClient` 忘了比超时（不同超时的
请求复用同一实例，传进来的 timeoutSeconds 等于没生效），`http1Client` 忘了比
DNS。改成「参数算 key」之后，这类漏判在结构上不存在 —— 参数不同 key 就不同。

`invalidateClients()` 从「置空八个字段」变成 `CLIENTS.clear()`。

### 数字

| | 改前 | 改后 |
|---|---|---|
| AiiHttp | 1470 | 1301 |
| ProxyRoute | — | 226 |
| 客户端工厂 | 5 个方法 / 4 组缓存字段 | 1 个方法 / 1 张表 |

净行数 +57（注释占大头），但**接口面从「字符串 + 约定」变成「一个类型」**。
新增 `ProxyRouteTest` 8 条，钉住三态语义、边界值、以及「日志和缓存键不许带密码」。

# 附：detail 桥不该是万能隧道（2026-10-18 晚）

## 问题

`MainActivity` 有 40 条指令的注册表，但前端 `sourceCommand()` 把一切都包成
`__source:xxx` 塞进 `detail`：

```js
bridgeCall('detail', { id: '__source:' + command })    // 源配置
bridgeCall('detail', { id: '__player:' + command })    // 亮度/清晰度
bridgeCall('detail', { id: '__proxy:' + command })     // 代理核心
bridgeCall('detail', { id: '__progress:' + ... })      // 播放进度
bridgeCall('detail', { id: '__http:' + ... })          // 播放层 HTTP 出口
```

一条 action 承载两类语义完全不同的东西：真正的详情页请求，和五个子系统的控制面。
加一个功能要在 `app.js` 包一层、再去 `UserSource` 的 `startsWith` 链上插一段 ——
**两个文件都得动，而且两处都不在「你要加的功能」附近**。

顺带提一句：`app.js` 那段注释说「MainActivity 的 dispatch 是按编号跳的
packed-switch，加动作要同时改两张表」—— 这句**已经过时了**。现在的 dispatch 是
`Map<String, Command>`，加一条就是一行 `commands.put(...)`。注释不更新，
后来的人会照着它绕路。

## 改法

控制面按前缀拆成五条独立 action，前缀由 Java 侧补，前端只传裸指令：

| action | 前缀 | 管什么 |
|---|---|---|
| `detail` | — | 只留详情页 |
| `source` | `__source:` | 源配置、换源、fetch、web 配置、reset |
| `player` | `__player:` | 亮度、清晰度、外置播放器 |
| `proxy` | `__proxy:` | 代理核心启停、节点、订阅 |
| `progress` | `__progress:` | 播放进度上报 |
| `http` | `__http:` | 播放层的 HTTP 出口 |

前端：

```js
bridgeCall('source', { id: command })      // 以前是 detail + '__source:' + command
```

Java：

```java
this.commands.put("source", args -> control(UserSource.PREFIX, args));
// control() 补前缀后交给 UserSource.handle —— 实现仍然共用一条链，
// 拆的是桥上的入口，不是实现
```

## 兼容

`SiteRepository.detail()` 里那段「`__` 开头就转控制面」的分支**保留**：
热更新的旧版 JS 还在用旧写法。删了就是「升级完页面全废」，而这段代码的
唯一成本是一个 `startsWith`。

## 收益

- 加一个控制面功能：`registerCommands` 一行 + 前端一行，**语义写在 action 名上**
- `detail` 的语义回到「取一个详情」，不再需要读调用方的字符串来判断
- 出问题时看日志就知道是哪条链路：`[api] /api/detail/...` 还是 `source` 桥

真机验证：首页正常加载（`source` 桥的 `web` 指令生效）、设置页「网络代理：已连接」
（`proxy` 桥的 `status` 生效）、播放与进度落盘正常。

# 附：UserSource 拆成五个子系统（2026-10-18 晚）

## 问题

`UserSource` 2492 行，一个类装了七个东西：

```text
handle()                   280 → 534   单个方法，用 startsWith 串起 5 个前缀
progress()                 播放进度上报
http()                     播放层的 HTTP 出口
player() → 亮度/清晰度/播放器
proxyCore() → 25 个方法     内置 Xray：订阅解析、测速、开机自启、模式迁移（638 行）
源配置本身                  get/set/clear/applySource/verify/清单/缓存
factoryReset()              恢复出厂（135 行）
```

它们之间**没有一个共享字段**。挤在一起唯一的原因是历史上都借同一座 detail 桥 ——
而桥早就拆成独立 action 了（上一节），这个类只是一直没人动。

## 拆完

| 文件 | 行数 | 管什么 |
|---|---|---|
| `UserSource` | 2492 → **560** | 只剩一张前缀路由表 + 几个共用小工具 |
| `SourceConfig` | **1102** | 源配置：读写、校验、缓存、清单、恢复出厂 |
| `ProxyConsole` | **678** | 内置代理核心：订阅、节点、测速、自启、模式迁移 |
| `PlayerControl` | **332** | 亮度、清晰度变体、外置/内置播放器 |
| `PlaybackHttpBridge` | **75** | 播放层 HTTP 出口（https + 域名白名单） |
| `ProgressSink` | **63** | 播放进度上报 |

`handle()` 从 280 行变成一张 Map：

```java
private interface Route {
    JSONObject run(Context c, SiteProfile p, String body, JSONObject out) throws Exception;
}

static {
    ROUTES.put(PROGRESS_PREFIX, (c, p, b, o) -> ProgressSink.report(b, o));
    ROUTES.put(HTTP_PREFIX,     (c, p, b, o) -> PlaybackHttpBridge.handle(b, o));
    ROUTES.put(PLAYER_PREFIX,   (c, p, b, o) -> PlayerControl.handle(c, b, o));
    ROUTES.put(PROXY_PREFIX,    (c, p, b, o) -> ProxyConsole.handle(c, b, o));
    ROUTES.put(PREFIX,          (c, p, b, o) -> SourceConfig.dispatch(c, p, b, o));
}
```

原来的 if-chain 有个隐性约束：**顺序不能错**（`__source:` 必须放最后，否则会吃掉
别的前缀）。现在这个约束消失了 —— 五条前缀互不为前缀，顺序无关。

## 重构时踩的坑

**① 字段声明的 `;` 不在花括号里。** 用花括号配对的 `take()` 摘
`private static final String[] HTTP_HOSTS = { ... }` 时，只摘到 `}`，
**丢掉了后面的 `;`** —— 编译报「需要';'」，而报错行在十几行之后。
以后摘字段初始化要单独处理。

**② 静态初始化块有「非法前向引用」。** `ROUTES` 的 static 块引用
`PROXY_PREFIX`，而那个常量声明在它下面 —— Java 不允许。把常量声明提到
`ROUTES` 之前即可。这条只在 static 初始化里出现，方法体里没有这个限制。

**③ 摘方法时把 `context` 参数弄丢了。** `proxyCore(Context, String, JSONObject)`
被我改成 `handle(String, JSONObject)`，方法体里还在用 `context`，
于是编译出一串「找不到符号」，而报错行指向的是每一个**调用** `proxyXxx(context, out)`
的地方 —— 看起来像那一堆方法丢了，其实只是参数没传进来。

## 顺带修掉的一个老洞

真机日志里一直刷：

```text
detail failed: yhdm 适配器不认识的路径：/api/reconcile?ids=…
```

前端进每个网格页都会调 `/api/reconcile`，而 yhdm 适配器没实现它。
已经补上（零网络的空壳应答，和 missav 那次同一个做法）。这个错误之前
比正常请求还密，会把真正的问题淹掉。

## 怎么拆的

没手抄。写了个扫描器按**顶层声明**切块，再按名字分派：

1. 用 `^(async function|function|const|let|var|class)\s+名字` 找出所有顶层声明的起始行；
2. 每块的**注释块也属于它** —— 从声明行往上走，连续 `//` 和 `/** */` 一起收进来。

3. 分派后逐块断言「原文里这一块，在新文件里恰好出现一次」。

结果：270 块、0 块丢失、0 块重复。剩下 1 行没被任何块覆盖 —— 文件头那句 `'use strict';`。

# 附：那堵墙搬进了配置，那八个桩删了（2026-10-18 深夜）

两件都是同一类问题：**代码里还留着「站点知识在 Java 里」的证据**。
一处是硬编码的域名，一处是只会抛异常的方法。

## 一、HTTP_HOSTS：搬了家，没改性质

`__http:` 这条桥是给 AGE动漫 的播放层用的（解析接口要带
`Video-Parse-Sign`，对面预检没回 `allow-headers`，浏览器发不出去）。
它有一张白名单，原来是：

```java
private static final String[] HTTP_HOSTS = {
    "jx.wuzhoupai.com",     // AGE动漫 的播放解析
    "xcdn.khfed.com",       // 它的播放器资源
};
```

2026-10-18 白天这段从 `UserSource`（2492 行）搬进 `PlaybackHttpBridge`
（75 行）时，只搬了位置 —— 它还是**一条写死在 Java 里的站点知识**：换源、
或者同一个源换了播放线路，都得改代码重新发版。

### 改法：和封面那条路对齐

App 里早就有一份「这个源允许访问哪些域名」的配置：

```json
"cover": { "allowedHosts": ["gimg0.baidu.com", ...] }
```

精确匹配、不支持通配符。播放层出口没有任何理由长得不一样。于是变成：

```json
"http": { "hosts": ["jx.wuzhoupai.com", "xcdn.khfed.com"] }
```

- `AgedmSite.buildConfig()` 声明这两台；`AgedmSite.patch()` 给老配置补上
  （配置是加源那天的快照，不会自己长出新块）。
- `SiteProfile` 构造时 `PlaybackHttpBridge.configure(...)`，就在
  `NetRoute.configure(...)` 旁边 —— 两个都是「这个源能碰哪些域名」，
  读一处就够。这也是全 App 唯一一处「当前源长什么样」的组装点。
- **没声明 = 空表 = 全拒**，报错里直说缺 `http.hosts`。这一条是重点：
  空表被当成「不限」的话，这面墙就形同不存在，而它挡的是「页面上的任意脚本
  借 Java 的网络能力访问任意 https 站点」。
- 装载时打一行日志：`播放层出口：这个源没有声明 http.hosts，一律拒绝`。
  这面墙最容易出的问题不是拦错，是**悄悄拦了** —— 用户看到播放层取不到地址，
  日志里什么都没有。

`hostsOf()` 是纯函数，`PlaybackHttpBridgeTest` 钉了五条：声明什么就是什么、
大小写不敏感、空白条目丢掉、没声明就是空表、装载后按当前源判断。

## 二、SiteRepository 的八个桩：不是「以后要实现的接口」

```java
JSONObject home() throws Exception {
    throw new UnsupportedOperationException("home 已改为纯 REST，抓 HTML 的分支已移除");
}
```

`home` / `category` / `search` / `tags` / `tagListing` / `episode` /
`recommend` 七个方法都是这样，外加 `MainActivity` 里七条对应的桥指令
（`home` / `category` / `search` / `tags` / `tag-list` / `episode` /
`newest`+`recommend`）。

它们不是未完成的接口，是**已经死掉的分支**：前端的内容请求统一走
`web.paths` 拼出来的路径（→ `detail` 桥 → `SiteRepository.detail` →
`AiiHttp`），永远到不了这几条命令。

留着它们的代价不是几十行代码，而是误导：任何读代码的人都会以为
「内容语义在 Java 里还有一半」，于是新加一个源时先去 `SiteRepository`
找该覆盖哪个方法 —— 而正确答案是「去配置里写 `paths`」。

所以全删了。`DualContentRepository` 那七个转发方法一起删。

删完之后，`api()` 在拿不到路径时的回退就没有落点了。以前它会
`bridgeCall('home')`，撞上的是一个抛异常的方法；现在那条路不存在了，
所以前端把话说清楚：

```js
const CONTENT_ACTIONS = new Set(['home','category','search','tags','tag-list','episode','recommend','newest']);
if (CONTENT_ACTIONS.has(action)) {
  throw new Error('这个源没有可用的 ' + action + ' 接口路径：检查 web.paths.' + action
                  + '，或这次请求的参数是否齐全');
}
```

注意 `apiPathFor` 返回 null 有**两种**原因：源没声明这条路径，或者参数不全
（分类 slug 查不到 `cate_id`、搜索没关键词）。报错文案两种都覆盖，否则
用户会被指向错误的开关。
