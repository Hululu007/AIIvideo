# 水果派（pie 2.5.4）：接口逆向 + spider 适配

包名 `com.fruit.goodgood`，应用名「水果派」，APK `pie_V2.5.4_release_07311155_zmt_s.apk`，
versionCode 17，`build_time 2026-07-31 11:53`，渠道码 `zmt_s`，targetSdk 35。

结论先放这儿：接口是 `POST /v2_0/<name>`，请求体和响应体都套一层 RSA+AES 信封，
私钥在 APK 的 assets 里，所以离线就能解全部响应。已经写成 `pie.js`（含纯 JS 的
RSA/AES 实现），五个能力实测通，`play` 因为站点用私有加密 HLS 只能降级。

## 一、这个包是什么

`lib/arm64-v8a/` 里五个 so，`classes.dex` 有 5.5MB 但业务不在 Java 层：

| 文件 | 看到的东西 |
|---|---|
| `libapp.so` | Dart AOT 快照，13.6MB，所有页面、网络、加密逻辑都在这儿 |
| `libflutter.so` | Flutter 引擎，符号被剥得只剩 57 个导出，`SSL_write` 之类全没了 |
| `libkiwi.so` | 6.8MB，`strings` 全是乱码 —— 加壳/加密的 so，没啃 |
| `libtoolChecker.so` | 5.5KB，环境检测 |
| `libumeng-spy.so` | 友盟统计 |

## 三、信封协议（这条是全部接口的钥匙）

第一次裸 POST `/v2_0/getSingleItem` 回的是：

```json
{"code":41000,"msg":"请使用正确的参数","data":{},"time":1792426741}
```

看到 `41000` 别急着调参数 —— **它是「解不开请求体」的通用话术**。真实协议是双向信封：

```
请求：{ "encrypt_key": b64(RSA_PKCS1v15( service_public.key, {"key":b64(16B),"iv":b64(16B)} )),
        "encrypt_data": b64( AES-128-CBC/PKCS7( 明文 JSON, key, iv ) ) }

响应：同一个形状，只是 encrypt_key 用 client_private.key 才能开
明文：{"code":1,"msg":"请求成功","data":…,"time":<秒>}
```

- RSA 填充是 **PKCS#1 v1.5**，不是 OAEP（试过 OAEP-SHA1/SHA256，`ValueError`）。
- AES 是 **AES-128-CBC + PKCS#7**，key/iv 各 16 字节，放在 RSA 密文里那段 JSON。
- 请求方向用 `service_public.key` 加密；响应方向服务器拿「client 公钥」加密，
  所以只有 APK 里那把私钥能开 —— 这也是为什么直接 `curl` 永远是 41000。

`/v2_0/getSingleItem` 带上正确信封、body 是 `{}` 时：

```json
{"code":41000,"msg":"请使用正确的参数","data":{},"time":…}
```

带上 `{"libraryId":1}` 就变 `code:1` + 一条完整 item。也就是说：**信封对了，
参数才轮得到被校验**。

`/domain/check`（GET，`?url=`）是唯一不走信封的，回纯文本 `success`。

路径都在 `/v2_0/` 下。名字不存在回 404，存在但参数不对回 400/41000 带中文 msg ——
拿这两条差异就能把整张表爆破出来（`work/re/pie` 那轮跑的是 1148 个候选名）。

| `searchV21List` | `{word,page}` | `{type,currentPage,totalPage,hasNextPage,censorship_type,list}`，`word` 少于 2 字回 41000 |

| `filmDetails` | `{film_id:"<id>"}` | `[{id,title,img_url,url,encryption_url,slice_video_id,price_configs,tags[],…}]`，注意回的是**数组** |
| `filmInfo` | 同上 | `filmDetails` 的别名，字段一致 |

社区侧（顺手记的）：`anchorsList`、`columnList`、`columnistList`、`recommendedDetailsList`、
`weekRecommend`、`homeExplanationPage`、`find`、`universalAdvert`、`getNewVersion` 都能无 token 拿到；
`getUserInfo`、`favorites` 这类要 `userToken`（放 body 里，名字就叫 `userToken`，放 header 无效 —— 试过
`token`/`Token`/`userToken`/`Authorization`/`Bearer …` 全被判「缺少token」）。

### 三个必须记住的坑

**① `library_id` 要字符串。** `{"library_id":1414}` 回 `{"item":[]}`，`{"library_id":"1414"}`
才回真数据。传 `libraryId`（驼峰）会被忽略并回一条固定的 5566 —— 那是个默认值，别当成功。

**② library 和 film 是两张表。** `library_id=1414` 的标题是「长清大学门事件…」，
`film_id=1414` 是「被每晚与老公做爱的绝伦叔母榨精…」。数字撞上了而已。
所以从首页卡片（library）点进去，拿不到 film 的播放地址 —— App 自己也得靠别的接口
（`libraryDetail` 要 `library_id`+`type`，`type` 我扫了 0~40 全是「type 错误」，没摸出来）。

**③ 付费内容给空 `url`。** `filmDetails` 里 `url` 基本都是空串，`is_buy_0/is_buy_1`
才是能不能看；能看的给 `encryption_url`。

## 五、播放：加密解开了

上一版这里写的是「解不开」。解开了，往下看。

### 5.1 密文长什么样

老片（比如 `film_id=10451`）的 `encryption_url`：

```
https://lvacm.fruit.tjfuxinjia.com/encry/vd/20250630/ZTllZTBhNTczY/142523/1080_608/aac/h264/hls/decrypt/index.m3u8
```

`curl` 回来 200、8336 字节、`Content-Type: application/octet-stream` —— 二进制，不是 `#EXTM3U`。
同目录的 `.ts` 也是密文。去掉 `encry/` 或去掉 `decrypt/` 那层全是 `NoSuchKey`，只有这一条路。

### 5.2 怎么确定是「块密码 + 固定密钥」

拿两个不同视频的 m3u8 密文逐字节比：**前 128 字节完全一样，从第 128 字节（正好第 8 个
16 字节块）开始全都不一样**。这正是分组密码 + 固定 IV/密钥的指纹：明文前 128 字节
（那段固定的 HLS 头）相同，密文就相同；一旦某一块的明文不同，后面所有块都跟着变。

反过来，如果是流密码（固定 keystream），差异会出现在明文第一次分叉的那个字节上，
而且 `C_A ⊕ C_B ⊕ P_B` 应该能还原出 **完整** 的 A 的明文 —— 实测只有前 128 字节能读，
后面全乱码，直接排掉流密码。

### 5.3 密钥从内存里挖出来

字符串派生的候选（libapp.so 里 20920 段可打印串，配合 md5/sha1/sha256、hex、base64 共
12.7 万个候选 key）全不中 —— 说明 key 不是字面量，是运行时算的或者藏在别处。

转内存：frida 把进程的 `r--` + `rw-` 全读下来（1083 个区间、634MB），然后拿已知明文
反推。关键是**别依赖明文的具体字节**：服务端吐出来的播放列表可能是重新序列化过的
（换行风格可能被改），所以判据用「`D(C1) ⊕ C0` 是 16 个可打印字符」而不是逐字节相等。

第一次扫（CBC 判据、要求逐字节等于已知明文）0 命中，换成可打印判据立刻出来：

```
ECB 00798.bin@952528/16 key=7361495a586334794d767130497a3536
```

`7361495a…3536` 转 ASCII 就是 **`saIZXc4yMvq0Iz56`**，16 字节，正好一把 AES-128 key。

判据说的是 ECB 命中（`D(C0) == P0`，C0 是第一块、P0 是 `#EXTM3U\n#EXT-X-V`），
也就是**整文件 AES-128-ECB + PKCS#7**。这也解释了两份密文前 128 字节相同：
ECB 没有链，相同明文块在任何文件里都出相同密文块。

### 5.4 验证

```
m3u8   8336 字节密文 → AES-128-ECB → 明文含 248 段，末尾 '\x10'*16 补齐（PKCS#7 pad=16）
.ts    240832 字节   → AES-128-ECB → 首包 47 40 11 10，0x47 严格落在 188 字节的整数倍上
```

两段不同视频的 m3u8、两段不同视频的 ts 都能解。明文播放列表里的段名是相对路径
（`TFkN-00000.ts`），拼在 `encryption_url` 的目录后面就是段地址，每一段同样用这把 key 解。

### 5.5 对 spider 意味着什么

解密本身很简单（ECB 就是 IV 全 0 的 CBC，`HGCrypto.aesCbcDecrypt(key, zeros16, data)`
直接能解），但**播放器不会替你解**：`play` 给的地址是播放器自己去拉的，拉回来的 m3u8
是密文，播放器没有这条解密链路，照样起不来。所以 `play` 仍然降级：

```js
{ reason: 'encrypted', note: '…AES-128-ECB，密钥已知，但播放器侧没有解密链路…' }
```

要让这个源真能播，得在 App 的播放层加一段「整文件 AES-ECB 解密 + 本地重发」的代理
（跟 `MediaProxy` 一个位置），源配置里再声明一条 `decrypt: {mode:'aes-ecb', key:'…'}` 之类。
这一步是 App 的活，不是 spider 的活，已经记在第八节。

离线要拿片源用 `work/re/pie/decrypt.py`：

```bash
python3 work/re/pie/decrypt.py --film 10451 --out ./out      # 走接口查链接
python3 work/re/pie/decrypt.py --url '<encryption_url>' --out ./out --limit 3
vlc out/index.m3u8
```

## 六、spider 怎么写

文件：`work/android/app/src/test/resources/spiders/pie.js`（34.7KB），
生成脚本 `work/re/pie/build.sh`，源码拆成两块：

- `work/re/pie/crypto.js` —— 纯 JS 的 RSA/AES，22.8KB，**没有 Buffer/atob/TextEncoder**，
  只用 `BigInt`/`Uint8Array`/`Math`。RSA-2048 私钥解密（CRT）**6ms/次**，
  AES-CBC 解 1KB **0.164ms**。47 条对拍断言（和 node crypto 逐字节比）全过。
- `work/re/pie/site.js` —— 站点逻辑：信封封包/拆包、五个能力、域名池兜底。

为什么必须在 JS 里重写密码学：spider 运行时只有 `net`/`netAll`/`log`，
没有 `crypto`，而每个响应都得 RSA 解一次才能拿到 JSON。6ms 的开销对 90 秒预算
完全够（一次能力调用 = 1~2 个请求）。

能力映射：

| cap | 接口 | 备注 |
|---|---|---|
| `home` | `/v2_0/homePage` | 5 条/页 |
| `category` | `/v2_0/classificationContentDetails` | slug 就是 classification_id（1/2/5/6/7/8） |
| `search` | `/v2_0/searchV21List` | 少于 2 字直接返回空，不打请求 |
| `detail` | `/v2_0/getSingleItem` | `library_id` 传字符串；单集，`ref` 原样回 `library_id` |
| `play` | `/v2_0/filmDetails` | 有 `url` 就给，只有 `encryption_url` 就走 `reason:'encrypted'` |

域名兜底：15 个域名写进 `__spiderSite.hosts`，`api()` 里挨个试。**区分两类失败**——
HTTP/网络失败换下一个域名，信封解不开就直接抛（密钥问题换域名没用，别把 15 个域名
各跑一遍，实测那样一次 35 秒）。

配置：`docs/samples/spiders/pie.json`。`origin` 填当前域名池里的一个，
`cover.allowedHosts` 只有两个：`img.2ktdfje.top`（帖子封面）和
`qzpic.jxpolygon.com`（原片封面）。`net.proxy` 把 15 个 API 域名都列进去 —— 国内直连，
境外节点会被掐。

## 八、还没做的

1. **播放层解密**。密钥和算法都有了（AES-128-ECB / `saIZXc4yMvq0Iz56`），缺的是
   App 播放链路里那一段：拉 m3u8 → 解密 → 改相对段名为本地代理地址 → 段也解密。
   加完 `play` 才能给真地址。
2. **密钥的来源**。这轮只证明它恒定（两个不同视频通用），没找到它从哪来
   （不在 assets、不在字符串、不在 API 响应里；大概率在 `libkiwi.so` 里，那 so 是加密的）。
   换版本时 key 会不会变，取决于这一点。
3. **`libraryDetail` 的 `type` 取值**。它能把 library 映射到 film，省掉卡片 id 的歧义。
4. **`sliceVideo` 的签名算法**（`Server: Xcdn`，`{"code":-1,"message":"签名失败"}`）。
5. **`tags`/`tagList`**。`getUnionAllTag` 要参数（回「参数错误」），现在用 `web.categories` 兜底。

## 附：复现用的解密片段

```python
import json, base64
from cryptography.hazmat.primitives import serialization, padding as sympad
from cryptography.hazmat.primitives.asymmetric import padding as apad
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

priv = serialization.load_pem_private_key(open('client_private.key','rb').read(), password=None)

def open_envelope(env):                      # {"encrypt_key","encrypt_data"}
    meta = json.loads(priv.decrypt(base64.b64decode(env['encrypt_key']), apad.PKCS1v15()))
    key, iv = base64.b64decode(meta['key']), base64.b64decode(meta['iv'])
    dec = Cipher(algorithms.AES(key), modes.CBC(iv)).decryptor()
    pt = dec.update(base64.b64decode(env['encrypt_data'])) + dec.finalize()
    u = sympad.PKCS7(128).unpadder()
    return json.loads((u.update(pt) + u.finalize()).decode())
```

脚本都在 `work/re/pie/`：`api.py`（封包/拆包/调用）、`probe.py`、`enumep.py`（端点爆破）、
`crypto-test.js`（密码学对拍）。
