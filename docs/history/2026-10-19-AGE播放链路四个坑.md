# AGE动漫播放链路：从密文到解码器（2026-10-19）

这一轮把 AGE动漫 从「点了播不了」一路挖到「解码器出 1280x720」，中间穿过四个坑。
每个坑单独看都像别的层的问题，写下来免得下次重走。

起点：八家迁成 spider 之后，AGE 的 `play` 返回 `url:'' + alts:[密文]`。

---

## 一、这条链路总览

```
spider (agedm.js)         取 detail → playlists → 所有 age_ 密文 → alts
        ↓
model.js play()           保留密文、url 留空、reason:'encrypted'
        ↓
app.js episodeShapeOf()   从 lines 里捞出 agedm-wasm: 标记当 source
        ↓
app.js hgNativeResolve()  看见标记 → 交给主页面
        ↓
hxm/agedm-play.js         跑站点自己的 TinyGo wasm 算签名 → 请求解析站 → m3u8
        ↓
VlcRelay.wrap()           识破伪装后缀 → 绕中继 → 自判类型
        ↓
libvlc                    出帧
```

**关键分工**：spider 只负责「取到什么」，主页面负责「怎么解」。spider **不该**有能力
加载 wasm —— 宿主页 CSP 是 `connect-src 'none'`，那是刻意的。

---

## 二、坑 1：`resolveAny` 的接口形状对不上

### 症状

```
解析失败：1 条线路都试过了
```

### 根因

`agedm-play.js` 的 `resolveAny(lines)` 期望 `lines[i]` 是**二元数组**
`["xigua", "age_xxx"]` —— 那是旧 Java `AgedmAdapter` 交过来的格式。

八家迁成 spider 之后，`lines` 的来源换成了 `model.js` 的 `play()`，形状是
**对象数组** `[{line, name, url}]`。

于是：

```js
const name  = String(lines[i][0] || '');   // undefined
const token = String(lines[i][1] || '');   // ''  ← 空串
```

每条线路的 token 都是空串，`resolve('')` 必然失败。最后报「N 条线路都试过了」。

**这个错误信息会把人引向「线路全挂了」**，而真相是接口对不上。

### 修法

加 `pairOf()`：两种形状都收，顺带剥掉 `agedm-wasm:` 前缀（`resolve` 只吃 `age_` 开头的）。

```js
function pairOf(raw) {
  if (typeof raw === 'string') return [stripMarker(raw), stripMarker(raw)];
  if (Array.isArray(raw))     return [String(raw[0] || ''), stripMarker(String(raw[1] || ''))];
  return [String(raw.line || raw.name || ''), stripMarker(String(raw.url || raw.token || ''))];
}
```

### 教训

**数据结构换了、消费方没跟上，而且没有测试覆盖。** 这类 bug 的特征是：
报错信息准确描述了「发生了什么」，但完全没说「为什么」。

## 三、坑 2：`agedm.json` 漏了 `http.hosts`

### 症状

```
解析失败：当前源没有声明播放层出口（http.hosts），不放开任何域名：
jx.wuzhoupai.com；1 条线路都试过了
```

### 根因

`PlaybackHttpBridge` 和 spider 的 `net` 是**两个独立的出口**：

| 出口 | 白名单字段 | 谁在用 |
|---|---|---|
| spider 的 `net` | `__spiderSite.hosts` | 源自己抓页面 |
| 播放层解析 | 配置里的 `http.hosts` | 主页面里的 wasm 解析器 |

我写配置时只给了前者。wasm 算完签名要 POST 到 `jx.wuzhoupai.com`，被后者挡住了。

### 修法

配置里补 `http.hosts`：

```json
"http": { "hosts": ["jx.wuzhoupai.com", "xcdn.khfed.com"] }
```

### 教训

一个源有两种「能碰哪些域名」的声明，**它们在两个地方、用两种形状**。
写新源的时候必须两个都填 —— 这个坑只有真的点到播放才会暴露。

## 四、坑 3：`.jpg` 伪装后缀（本轮最硬的）

### 症状

```
libvlc demux: Failed to create demuxer 0x0 Unknown
```

黑屏，而且 VLC 每 2 秒换一条线路重试，8 条全试完也不报「格式不对」。

### 根因

AGE 解析站返回的地址长这样：

```
https://jx.wuzhoupai.com:8443/playurl/<hash>…&media_type=jpg
```

**但那个地址的真实内容是 m3u8**。日志证据（修好之后才看得到）：

```
[relay] 上游 200 http/1.1 https://jx.wuzhoupai.com:8443/playurl/7ace8647….m3u8
```

服务端把 `.m3u8` 说成 `.jpg`，`media_type=jpg` 再强调一遍。VLC 按 URL 后缀选
demuxer，直接判死。

### 为什么中继原来不接管

`VlcRelay.wrap()` 的放行条件是：

```java
if (AiiHttp.effectiveProxy().length() == 0) return null;   // 没开代理 → 直连
if (!NetRoute.mustProxy(host)) return null;                // 不在代理表 → 直连
```

当时 `mode=direct`，两条都不满足，所以返回 null，VLC 拿到裸地址。

### 修法（两处）

**① `VlcRelay.wrap()`：伪装后缀不管有没有代理都绕中继**

```java
boolean disguise = disguised(originalUrl);
if (!disguise && AiiHttp.effectiveProxy().length() == 0) return null;
// …代理表判断也跳过（绕中继是为了改类型判定，不是为了代理）
```

新增 `disguised()`：后缀命中 `.jpg/.png/.gif/.webp/.woff2/…` 或查询串含
`media_type=`，就判定为伪装。

**② 中继的 OkHttp 分支：读内容自己判类型**

原来只按 `.m3u8` 后缀或 `Content-Type: mpegurl` 判播放列表 —— 伪装地址两个都不命中，
于是照抄上游的 `image/jpeg`。

现在伪装地址走新分支：peek 前 1KB，

| 开头 | 判定 |
|---|---|
| `#EXTM3U` | 播放列表，整块读进来改写 |
| `0x47`（TS 同步字节） | `video/mp2t` |
| 其它 | `application/octet-stream` |

**必须边读边写**，不能 `readByteArray()` —— 这是视频流，一部片子几百 MB。
`peek` 不改读指针，所以已经 peek 过的字节还在，从头顺序搬就是完整内容。

### 结果

```
[relay] 播放列表改写 175 条
[relay] 伪装播放列表已改写
libvlc decoder: output: 1280x720     ← demux 过了，解码器起来了
```

### 教训

**服务端和扩展名可以同时骗人。唯一靠谱的证据是内容本身。**
这个修法顺带对 OpenList 那种「视频改名成 .jpg/.woff2」的站也生效。

## 五、坑 4：`Code=9` 不是 bug

### 症状

```
解析失败：这条线路服务端没受理（Code=9）
```

### 真相

解析站对**特定线路**不受理，客户端绕不过去。旧 Java 注释里就记着这个案例：

> 「萝球社！OAD」只有一条 `tt` 线路，那条回 Code=9，于是这部剧在 App 里彻底没救

我核实过《战×恋》（`20190213`）的真实数据：

```
playlists 的键: tt        ← 只有一条线
```

所以界面显示「1 条线路都试过了」是对的。

多线路的剧（《游戏人生》`20170207` 有 `qiyi`/`hnm3u8`/`lzm3u8` 三条）会一条条试，
碰到 `Code=9` 自动换下一条 —— 这正是 `resolveAny` 逐条重试存在的理由。

### 教训

**「报错」和「没救」是两件事。** 别把站点侧的拒绝当成自己的 bug 去修。

## 六、还没解决的：画面显示

解码器出帧了（`1280x720`），但屏幕上还是黑屏转圈：

```
libvlc window: request 0 not implemented
libvlc window: request 1 not implemented
libvlc decoder: output: 2130708361 unknown, 1280x720 stride 0 0
```

`2130708361` = `0x7F000001` = `127.0.0.1`。解码器在出帧，帧没落到 `SurfaceView` 上。

**这不是 AGE 的问题、不是 spider 的问题、也不是伪装后缀的问题** ——
是 `VlcPlayerActivity` 的 vout 绑定这一层。同样的黑屏在别的源上也可能出现，
只是之前没机会走到「demux 成功」这一步。
