# MissAV 过盾链路：修好了两处，还差最后一跳（2026-10-19 晚）

用户切到 MissAV，首页：

```
missav 请求失败 https://missav.live/dm539/cn/new：net 失败：
missav.live 在 Cloudflare 后面，okhttp 被挡（HTTP 103 @ …），
改用真浏览器内核也没过：界面还没起来，站点侧请求发不出去（稍等一下再试）。
```

一句报错里藏着两个独立的 bug，外加一条没打通的链路。

---

## 一、`界面还没起来` = 子进程拿不到 Activity

`SiteFetchWebView.fetchPage()` 第一句：

```java
MainActivity host = MainActivity.host;
if (host == null) throw new IOException("界面还没起来，站点侧请求发不出去…");
```

而 spider 的宿主 2026-10-19 搬进了 `:spider` 独立进程（`SpiderService`）。
`MainActivity.host` 是主进程的静态字段，**跨进程各是一份**，子进程里恒 null。

所以从搬进程那天起，任何「盾后站点」的过盾都必然走到这句。

修法：允许无窗口模式。headless WebView 本来就不需要 decorView（`SpiderRuntime`
一直是这么跑的：不 attach 也能 loadUrl / evaluateJavascript，只是不渲染像素）。

- `SiteFetchWebView` 加 `static void init(Context)`，`SpiderService.onCreate` 里调
- `ensureWebView()`：没有 Activity 时用 Application 上下文建页，**不 attach**
- `fetchPage/fetchBytes` 不再要求 `MainActivity.host != null`

改完日志从「界面还没起来」变成真的去加载页面了。

---

## 二、WebView 的 socks5 代理不可靠

有了页面之后仍然 20 秒超时。加两行日志（`onPageFinished` / `onReceivedError`）才看清：

```
[site-wv] WebView 走代理：SOCKS socks5://127.0.0.1:38599
[site-wv] WebView 代理已挂上
[site-wv] 过盾第 1 次超时，耗时 20278ms
```

**一句「页面加载完」都没有**。而同一个 socks 用 OkHttp 走是通的（能拿到 103）。

也就是说 `ProxyController.setProxyOverride` 回调说「已挂上」，实际页面根本没走代理。
设备 WebView 143，不是版本老的问题。

修法：在进程内起一个**只认 CONNECT 的 HTTP→SOCKS 桥**（`SiteFetchWebView.SocksBridge`）：
绑 127.0.0.1 随机端口，读到 `CONNECT host:port` 就做一次 SOCKS5 握手，回
`200 Connection Established`，然后双向管道。WebView 改成走 `http://127.0.0.1:<bridge>`。

桥起来了，也收到了连接：

```
[site-wv] WebView 走本地 HTTP→SOCKS 桥 127.0.0.1:39111 → 127.0.0.1:24117
[site-wv] 桥收到连接 /127.0.0.1:45834
```

## 三、还差的最后一跳

加了错误日志之后看到真正的原因：

```
[site-wv] 加载失败 https://missav.live/dm539/cn/new code=-8 net::ERR_TIMED_OUT
[site-wv] 页面加载完 https://missav.live/dm539/cn/new title/innerText="0|0"
```

桥收到 CONNECT，但转发到 socks 之后请求超时。三种可能，按可能性排序：

1. **桥的 SOCKS5 回复读死了 10 字节**。reply 的长度取决于 ATYP：IPv4 是 10，
   域名是 `7 + 长度`，IPv6 是 22。Xray 正常回 IPv4，但如果它回域名类型，
   这里会读多/读少，后续数据流错位。
2. 桥到 socks 的连接没走对（`127.0.0.1:24117` 是 `ProxyCore.port()`，
   但 `AiiHttp.effectiveJavaProxy()` 给的地址可能是外部 HTTP 代理而不是本地核心）。
3. Cloudflare 对无窗口 WebView 的挑战仍然不过（`title/innerText="0|0"` 说明页面是空的）。

`innerText=0` 是关键线索：如果桥通了、页面加载了，挑战页至少该有几千字节的正文。
0 意味着**页面根本没渲染出来**，所以问题在 1 或 2，不是 Cloudflare 那边。

---

## 四、封面：403 是另一条独立的坎

首页数据出来了，但封面全是灰块：

```
[http] GET fourhoi.com/dldss-562/cover-t.jpg
java.io.IOException: HTTP 403 @ https://fourhoi.com/dldss-562/cover-t.jpg
```

`fourhoi.com` 和站点页是同一套 Cloudflare 指纹判断，okhttp 取图一律 403。
已经加了回退：`SiteRepository.fetch()` 失败且域名命中 `SiteFetchWebView.handles()`
时，改用 `fetchBytes()` 借浏览器栈取字节（`handles` 里加了 `fourhoi.com`）。

回退被触发了（日志有「封面改走真 WebView：fourhoi.com」），但因为上面那最后一跳
没通，取回来的还是空 —— 等过盾链路修好，封面应该跟着好。
