# 类型页：全源可用（2026-10-19 晚）

真机上切到樱花动漫，点「日本动漫」：

```
加载失败
出了点小问题，重试一次；总不行就到设置里换个源。
这个源没有实现「类型列表」（spider 里没有 tagList 函数）
```

一句话里两个问题：**用户看到内部函数名**，而且这个源明明有分类，只是没实现`tagList`
这个能力名。

---

## 一、为什么只有 91porn 能用

上一轮只给 91porn 补了 `tags` / `tagList`，其余七家没动。而「全部类型」页对它们的
要求其实很轻：

- `tag-list` = 按分类列内容 —— 每家都有 `category`，语义一模一样，只是函数名不同。
- `tags` = 列出分类 —— 每家的分类**本来就写在配置里**（`web.categories`、
  `ui.categoryIds` / `ui.categoryLabels`）。

也就是说这不是「七个源各缺一个功能」，是壳少了一条退路。

---

## 二、壳的退路（一次修好五家）

`api()` 在源不支持某个能力时，先试 `contentFallback`：

```js
tag-list → category      // slug 就是 cateId，模型的 paged() 形状完全一致
tags     → siteTagFallback()   // 用 ui.categoryIds + categoryLabels 现拼
```

`siteTagFallback()` 的取名顺序：`categoryLabels` 的同位名字 → 一个 tab 对一个分类时
用 tab 标题 → 都没有就用 cateId 本身。没有任何配置分类的源（比如 cms）返回空，
让上层照常报错，不假装有内容。

**源自己实现了就优先用源的**：91porn 的标签是站点原文（「当前最热」「最近加精」），
配置里那份是旧名字。

效果：樱花动漫、每日大赛、MissAV、AGE、OpenList 立刻有可用的类型页，零请求。

## 三、值得单独实现的两家

### hanime1：240 个标签，7 个分区

它的 genre（10 个大方向）只是导航，真正决定「找不找得到」的是标签面板上那 240 个
细标签。面板在任意分类页的模态框里，DOM 是 `<h5>分区名</h5>` + 一串
`<label class="hentai-tags-wrapper"><input name="tags[]" value="無碼">`。

实现两件事：

- `tags()`：打一次分类页把面板抠出来，分区名映射到配置里 `ui.tagGroups` 的 id
  （站点是繁体，简繁两份都收，切语言时不会整页掉进 other）。
- `tagList()`：`/search?genre=…&tags%5B%5D=…&page=N`。

**两个坑原样还在**（2026-10-17 记过，今天复验）：

1. `tags[]` 的方括号必须编码成 `%5B%5D`，直接写会被中间层吃掉 —— 表现是「点了标签
   出来的还是默认列表」，不报错。
2. 必须带 `genre`，只给 `tags[]` 时站点回全站默认列表。所以挂 `GENRES[0]` 当 seed，
   那是兜底不是筛选意图。

真机（走代理）：

```
caps = home,category,tags,tagList,search,detail,play
全部类型 → 240 个标签 / 7 个分区（影片属性 / 人物关系 / 角色设定 / 外貌身材 /
           情境场所 / 故事剧情 / 性交体位）
点「巨乳」 → 41 张卡，nextPage=2
```

41 张这个数字和 2026-10-17 Java 版实测的「裏番 + 巨乳 = 41 张」一模一样，
说明过滤确实生效了（如果 tags[] 被吃掉，会回到 41 张那个「无标签」基线；
过滤生效的铁证是「拳交」从 41 掉到 35 —— 巨乳覆盖面太广看不出差别）。

### cms：苹果CMS 的 class[]

一个源覆盖几千个站，每个站的分类都不一样，不在配置里。所以 `tags()` 每次真请求
一次接口拿 `class[]`，摊成叶子（父类查不出内容，列出来只会让人点了个寂寞）。

## 五点五、顺手删了搜索页那排分类胶囊

搜索「爱」，结果下面挂着一排「全部 / 成人短剧 / 成人漫剧 / AI换脸 / AI魔改」。
那是 `renderSearch()` 里写死的：

```js
const filters = privateMode()
  ? [['all','全部'],['ai-duanju','成人短剧'],['ai-manju','成人漫剧'],['ai-huanlian','AI换脸'],['ai-mogai','AI魔改']]
  : [['all','全部'],['short','短剧'],['comic','漫剧']];
const items = state.filter === 'all' ? all : all.filter(item => {
  if (state.filter === 'ai-huanlian') return /AI\s*换脸/.test(title);   // ← 拿标题猜
  ...
});
```

两个问题，第二个比第一个严重：

1. 它跟搜索词毫无关系。搜「爱」也照样挂着，看起来像「你搜的结果被这几类分好了」。
2. 过滤是**拿标题正则猜的**。猜错的结果是「少了几个结果」，不报错 —— 用户只会觉得
   「搜索不全」，而不会想到是那排胶囊在作祟。

而且这套只对内置的黄果源有意义。用户自带的 spider 源每家分类都不一样，写死一份必然
对不上 —— 樱花动漫的分类是「日本 / 国产 / 欧美」，跟「成人短剧」半点关系没有。

现在整块删了：渲染、过滤、`data-filter` 事件、`state.filter` 三处读写全清（`grep
state.filter` 归零）。按分类找东西走「全部类型」，那里列的是源自己的分类。

真机：搜索「爱」→「爱 · 24 部作品」，标题下面直接是网格，没有胶囊。

## 六、还欠着的

- **`recommend` / `newest`（首页「更多」）** 还是没有源的实现，点了会报
  「这个源没有实现「精选推荐」」。可以按同样的思路降级到 `category`（不带 slug），
  但首页那两块本来就是 `home` 的切片，退化的价值不大，先留着。
- **cms 的 tags 每次真请求接口**（约 200KB）。可以按 api 地址缓存 10 分钟，但
  「分类变了要等发版」这件事比一次 200ms 更难受 —— 先不缓存。
