# 2026-10-19 晚：代理路由智能化（方案 B geosite 分流 + 方案 A 失败自愈）

> 一句话：路由从「静态表」升级成「作者显式声明 > geosite 自动分流 > 失败自愈学习」
> 三层；路上踩掉一个能把整个进程无声带走的坑（`go.Seq.setContext`）。

## 一、现在的路由全景（改完之后）

判定顺序（`AiiHttp.clientFor` / `routeAndSend`，OkHttp 出口）：

1. `NetRoute.directOnly(host)` → **强制直连**（白名单 / 声明源的直连域，失败也不换路）
2. 声明了 net 块且 `mustProxy(host)` → **强制代理**（同上）
3. `RouteMemory.opinion(host)` → 按记忆走（方案 A）
4. 未声明源的老兜底：全局代理开且非白名单 → 代理，否则直连
5. 连接层失败（超时 / reset / TLS / 解析失败；`HTTP <code>` 不算）→ 换另一条路重试一次
   → 成功 `RouteMemory.learn`，两条都败 `RouteMemory.forget` 回落规则层

核心层（`XrayConfig.routing()`，builtin 模式下进本地 SOCKS 的流量）：

```
① api inbound                    → direct
② 源 net.proxy 声明域 + origin    → proxy   （作者显式，压过 geo 判断）
③ geosite:cn                     → direct  （境内域名/CDN 全直连）
④ DirectHosts 手填白名单          → direct  （过渡保留，待退役）
⑤ 其余 tcp/udp                    → proxy   （冷门被墙域兜底）
```

`domainStrategy=AsIs`，只用域名规则；geoip:cn IP 规则 + xray dns 块是阶段 2（要配
IPIfNonMatch + DNS，暂不做）。

## 二、方案 B：geosite 分流

- `routing()` 之前只有 api 直连 + DirectHosts 域名直连。现在按上面 ①②③⑤ 重写。
- **dat 文件零工作量**：`libv2ray.aar` 的 assets 里自带 `geosite.dat`（11MB）+
  `geoip.dat`（17MB），核心经 AAssetManager 直接读 APK——不用内置第二份、不走热更。
- `NetRoute.declaredProxyHosts()` 新增读取口，`XrayConfig.build/buildString` 加带
  声明域的重载；`ProxyCore.probe` 的测速配置传空表（routing 不影响它）。
- `DirectHosts` 本次保留（老源 OkHttp 侧语义还在用），方案 A 稳定后单独退役。

## 三、踩坑实录：geosite 规则上线 → 点图标闪退（无崩溃栈）

**现象**：装上带 geosite 分流的包后，点图标秒退桌面；进程无声消失，**没有任何
Java 崩溃栈**。当时设备处于直连档，验证时核心从没带新配置启动过，所以这笔账
迟到了几个小时——用户开内置代理才第一次踩中。

**定位**（logcat 全量抓）：

```
19:20:26.479 核心就绪 Lib v31, V2fly-core v5.54.2
19:20:26.481 GoLog: Initializing core...
19:20:26.485 GoLog: asset: no current JVM
19:20:26.521 Zygote: Process 6828 exited cleanly (1)   ← 不是 crash，是 exit
```

**根因**：gomobile 的 asset 包读 `geosite.dat` 前需要注册 JVM context。
`go.Seq.setContext(appContext)` 我们从没调过——旧配置只用了字面域名规则
（`domain:xxx`），这条路径在 routing 引入 `geosite:cn` 之前**从未被走过**。
Go 侧拿不到 context 就 `os.Exit(1)`，整个主进程带走。

**修复**（一行）：`ProxyCore.ensureEnv` 里 `initCoreEnv` 之前
`go.Seq.setContext(appContext)`——v2rayNG 同款调用。

**教训**：核心配置里每引用一种新资源类型（geosite / geoip / DNS 出站），都要在
「核心真实启动」的档位下验一遍——**开关档位 × 代码路径**的组合要进验收清单，
「直连档下 app 正常」证明不了代理档没事。

## 四、方案 A：RouteMemory 失败自愈

- 新增 `RouteMemory`：`files/route-memory.json`，`{host: {route, at}}`，
  tmp+rename 原子写，mtime 检查跨进程重读（主 + :spider 天然共享），TTL 24h，
  上限 128 条丢最旧。
- `AiiHttp`：`getWith` / `rawWith` 两处重复的分流分支收拢成 `routeAndSend`；
  连接层失败换路重试一次，成功 `learn`，双败 `forget`。判定与翻转是包级纯函数
  （`isConnectFailure` / `flipRoute`），JVM 可测。
- `NetRoute.isDeclared()` 新增：声明源的直连域是作者显式决定，记忆不得覆盖。
- 单测 `RouteMemoryTest` 9 项 + `XrayConfigRoutingTest` 7 项；全套 201 项绿。

## 五、agedm「spider 跑不了 wasm」的说法：更正

现装 agedm spider 的 play 只回 `agedm-wasm:` 密文标记是事实，但 agedm.js 里
「CSP 没有 wasm 运行时/加载路径」的判断**是错的**：

- 运行时：WebView 内核（V8）自带 WebAssembly；spider 宿主页 CSP 的
  `script-src 'unsafe-inline' 'unsafe-eval'` 放行 wasm（主页面用同一族子句跑着
  同一个 410KB 的 TinyGo wasm，就是证据）。
- 加载路径：源文件是「可执行资产」——把 `hxm.wasm.js` 的 base64（~550KB，源上限
  2MB）连同 `hxm-exec.js`（Go 胶水 ~10KB）内嵌进 agedm.js，`net` 替代 `HG_HTTP`，
  play 即可直出 m3u8。**零发版**。

结论：agedm 的「点不了」是「还没把 wasm 塞进源文件」，不是架构限制，
不构成对「加源不发版」的反例。升级路径已明确，做的时候顺手把
`samples/spiders/agedm.json` 的 `_note` 和 `agedm.js` 的降级注释一起改掉。
