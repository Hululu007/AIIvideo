# MissAV 适配器：整站过盾、HLS 借道、七个静默失败

（2026-10-18，真机 7f8f5254 / Android 16。所有结论都是在这台机器上量出来的，
日志原样贴出来，改之前的推断一律标注「以为」。）

目标：让 App 能接入 <https://missav.live>，从加源到能播完整一集。

结果：**通了**，用户实测确认。加源 280~780ms，首页 12 张卡带封面，
详情页有选集，播放 2:18:10 的完整时长可拖进度、四档码率，
「全部类型」100 个分类，分类页能一直往下翻，
「无码影片」下面挂着 12 个站点（无码流出 / FC2 / HEYZO / 东京热 / 一本道 / …）。

---

## 一、整站挂在 Cloudflare 后面，okhttp 一律拿不到内容

第一件事就撞墙。`/cn/new`、`/api/*`、封面域 `fourhoi.com`、视频 CDN
`surrit.com` 全在盾后。用户加源时的日志：

```text
[api] /api/home FAIL 20004ms 过盾排队超时。
```

试过的、都不行的三条路：

| 做法 | 结果 |
| --- | --- |
| okhttp 直接请求 | 403（挑战页 HTML） |
| 从浏览器导出 `cf_clearance` 塞进 okhttp | 403，一样 |
| 换 UA / 补 Referer / 补 sec-ch-ua | 403，一样 |

`cf_clearance` 绑的是 **TLS 指纹（JA3/JA4）**，不是 cookie 本身。
OkHttp 层改不了这个，只能借浏览器。

所以有了 `SiteFetchWebView`：一个不可见的 WebView，正常导航到站点页面，
**让它自己过盾**，然后在页面上下文里发同源 `fetch`，把响应体带回 Java。

```text
[site-wv] 过盾第 1 次成功，耗时 277ms
[http] 预热完成 /api/home 6421 字节 510ms
```

### 过盾这条路踩的三个坑

**坑 1：UA 里的 `; wv)`。** WebView 默认 UA 带这个标记，CF 直接判非浏览器。
换成 Chrome 130 Mobile UA 之后 282ms 就过。

**坑 2：`setBlockNetworkImage(true)`。** 当初为了省流量开了它，结果 CF 的挑战
脚本靠「图片能不能加载」判断环境，图被拦 → 容器不插入 → 判据（`.grid`）永远
不出现，20 秒超时。去掉这个设置，判据改成 `html[lang], .grid`。

**坑 3：`evaluateJavascript` 的回包是 JSON 序列化的。** JS 里 `return '1'`，
Java 侧拿到的是 `"1"`（带引号）。`"1".equals(v)` 永远 false。剥引号之后才通。

### WebView 的网络是独立的

OkHttp 的 `proxy()` 对 WebView 完全无效 —— 它是另一个网络栈。
必须用 `androidx.webkit` 的 `ProxyController.setProxyOverride`：

```java
ProxyConfig config = new ProxyConfig(
        Collections.singletonList(new ProxyRule("http", "http://127.0.0.1:7897")),
        Collections.emptyList(), false);   // false = 不能绕过
ProxyController.getInstance().setProxyOverride(config, executor, callback);
```

没挂上之前的日志是 `[site-wv] 直连（当前没有生效的代理）`，然后过盾 20 秒超时。

## 二、HTML 解析：三个只有真页面才暴露的坑

### 卡片切分锚点

```java
// 错：真实卡片的 class 前面还有 Alpine.js 属性
"<div\\s+class=\"[^\"]*\\bthumbnail\\b"
// 对
"<div\\b[^>]*\\bclass\\s*=\\s*\"[^\"]*\\bthumbnail\\b"
```

第一版在真实页面上 0 命中，合成 fixture 上全绿。

### 封面判据是「src 是不是 data: URI」

站点用 lozad 懒加载，真封面的 `src` 是 `data:image/...` 占位，真实地址在
`data-src`。所以判据不能是「src 是否为空」。

### packed JS 解包：锚点是 `}('` 而不是 `})(`

播放地址（`surrit.com/.../playlist.m3u8`）写在详情页一段 Dean Edwards packer
里。解包踩了五轮：

1. 只抓了词典没抓载荷；
2. 正则试图匹配 packer 函数体（三层嵌套花括号）失败；
3. 锚点写成 `})(`，真实是内联形态 `}('`；
4. 索引按 1-based 算，实际 **0-based**；
5. 占位符按十进制算，实际 **base-36**（索引 14 写作 `'e'`）。

## 三、七个静默失败：数据都在，界面全空

共同特征：**接口 200、日志无异常、界面上什么都没有**。比报错难查十倍。

### 3.1 「无法拉到集数」—— `web.fields` 别名表

适配器返回的 `episodes:[{episodeNumber:1}]` 是对的，但前端
`pick(entry,'episodeNumber')` 走配置里的别名表，默认表里只有 `['ep_num']`
（AGE动漫/CMS 的字段名）。`episodeNumber` 不在候选里 → 取空 →
`openAt` 的 `episodes.filter(Boolean)` 把唯一那一集滤掉。

```java
fields.put("episodeNumber", arr("episodeNumber"));   // 必须同名声明
fields.put("source", fSrc);                          // ["source","playUrl","video_url"]
```

同一个坑在标签页又踩了一次：`adaptTags` 里
`name: pick(tag,'tagName') || pick(tag,'slug')`，默认别名表只有 `['name']`，
返回 `tagName` → 取空 → 「全部类型」页每个胶囊都写成 `dm96/高清`。

**适配器返回什么键名，别名表里就必须声明同名候选。** 这是契约的另一半。

### 3.2 「全部类型」空白 —— 要分组信封，不是平铺数组

`adaptTags` 认的是：

```json
{ "categories": [ { "code": "category", "tags": [ {"slug":"genres/dm96/高清","tagName":"高清","group":"category"} ] } ] }
```

第一版返回平铺的 `{items:[{id,name,count}]}`，`asArray(shapeValue(raw,'tags','categories'))`
拿到空 → 标题写着「35 个标签」，内容一片空白。

### 3.3 点了分类「已显示 0 部作品」—— 分类地址有三种形状

最贵的坑，因为它**不影响任何返回码**。真实形态（fixture 里每条链接都能对上）：

```text
genres/dm106/剧情   → https://missav.live/dm106/cn/genres/%E5%89%A7%E6%83%85
dm597/fc2           → https://missav.live/dm597/cn/fc2
new                 → https://missav.live/cn/new
                      ↑ 分类 id 永远在路径最前面
```

第一版把类型页拼成 `/cn/dm96/高清`（id 当成 `cn` 下面的一级），站点回的是
404 内容页，`parseList` 一张卡都认不出来。日志里却是
`[api] /api/category?slug=dm96%2F%E9%AB%98%E6%B8%85&page=1 ok 474ms` —— **200，成功**。

slug 的首段用来区分三种形态：`genres/…` 是类型页，`dm\d+/…` 是普通分类，
其余是固定导航。

### 3.4 「每个分类只有 12 部」—— pages 挂在 `pagination` 上

翻页这件事前端只认一个函数：

```js
function nextPageOf(raw) {
  const page  = Number(shapeValue(raw, 'list', 'page',  'pagination.page'))  || 1;
  const pages = Number(shapeValue(raw, 'list', 'pages', 'pagination.pages')) || 0;
  return page < pages ? page + 1 : null;
}
```

`shapeValue(raw,'list',X,Y)` 的意思是：配了 `web.shapes.list` 就读配置指定的路径，
**没配就退回 `pagination.X`**。我返回的是平铺的 `{items, page, hasMore}`，
两套都对不上 → `pages = 0` → `nextPage` 恒为 null → 界面直接写「已经到底了」。

修法是配 shapes：

```json
"shapes": { "list": { "items": "items", "page": "page", "pages": "pages" } }
```

站点不给总页数，用「这页满不满」推：满页就给 `pages = page + 1`。

改完日志：

```text
[api] /api/category?slug=dm817%2Funcensored-leak&page=6 ok 393ms
[api] /api/category?slug=dm817%2Funcensored-leak&page=7 ok 439ms
[api] /api/category?slug=dm817%2Funcensored-leak&page=8 ok 435ms
```

### 3.5 「类型」tab 点开是空的 —— 索引入口不能当列表入口

`/cn/genres` 是**分类索引页**（42 页 × 36 个），不是作品列表。第一版把它当成
底部导航里的一个列表 tab，点开必然是「类型作品 / 已显示 0 部」。

同样的错还有第二次：把「女优」也做成了 tab。`/cn/actresses` 列的也是女优，
不是片 —— 于是「女优作品 / 已显示 0 部」。

现在底部导航里**只有真正的作品列表**，索引类入口一律不进：

- 「选分类」归首页顶部那条「全部类型 >」（走 `tags` 动作 → `/api/genres` → 分类胶囊）；
- 「女优」「发行商」暂时不放进导航。要用起来得加一层（点女优 → `/cn/actress/{slug}`
  看她的作品），而前端目前只有「列表」和「影片详情」两种页面 —— 见第七节。

### 3.6 二级分类不显示 —— `categoryIds` 是数组，不是单值

站点自己的导航是**两级**的。「无码影片」下面挂着无码流出 / FC2 / HEYZO /
东京热 / 一本道 / Caribbeancom / Gachinco / XXX-AV / 人妻斩 / 顽皮…
一个 tab 只给一个总列表，等于把站点最好的那层结构扔了。

前端本来就支持子 tab，配置形状是：

```json
"ui": {
  "categoryIds":    { "uncensored": ["dm817/uncensored-leak", "dm597/fc2", "dm2208642/heyzo", …] },
  "categoryLabels": { "uncensored": ["无码流出", "FC2", "HEYZO", …] }
}
```

两个数组**必须等长**（前端按 `state.sub[tab]` 取同一位置）。

还有一张表容易漏：`web.categories` 是 `cateIdOf(slug)` 查的（slug → 站点 cateId），
而 `apiPathFor` 里是 `if (!cateId) return null` —— 查不到就**静默不请求**，
症状是「点了那个子标签，页面还停在上一页」。单测逮到过一次（`release` tab 漏填）。

### 3.7 `/api/reconcile` 必须应答

前端进每个网格页都会调 `detail` 带 `/api/reconcile?ids=a,b,c`（先铺网格图，
再拿详情盖真值）。missav 不实现就抛异常，一个页面 4~6 次，把真正的错误全淹了；
而前端拿到异常**什么都不记**，下次进来还会再问。

应答策略零网络：列表解析时把条目塞进一个 512 容量的 `LinkedHashMap`，
被问到的 id 命中就给真值、没命中给一个只带 `id` 的空壳 —— 前端会把它记进
`reconciledFixes`，之后不再问，而空壳让 `applyFixes` 的 touched 保持 0，
不会把卡片上的标题/封面改成空。

## 四、播放：surrit.com 的 403 和「借 WebView 取字节」

这一段是整件事里最硬的骨头。

### 现象

详情页、选集、播放地址全部正确，点播放一直转圈。日志：

```text
[api] /api/play/mfyd-196-uncensored-leak ok 44ms json
[relay] 中继已启动 127.0.0.1:38899
[relay] 上游 403 http/1.1 https://surrit.com/3076ed53-…/playlist.m3u8
[relay] 连接结束：sun.net.ConnectionResetException @https://surrit.com/… Connection reset
```

Mac 上 `curl`（走同一个出口）也是 403，页面标题
`Attention Required! | Cloudflare`，4545 字节。**同一个地址在站点 WebView 里
fetch 是 200。**

关键对照实验：

| 请求方 | 结果 |
| --- | --- |
| Mac curl（Chrome UA + Referer + Origin） | 403 Attention Required |
| 手机 okhttp（走代理、强制 HTTP/1.1、带 Referer） | 403 |
| **站点 WebView 里 fetch（跨源、不带 credentials）** | **200，m3u8 原文** |

挡的不是 IP、不是 Referer、不是 cookie —— 是浏览器栈那一层。

### 做法：取流也走那个已经过了盾的 WebView

`SiteFetchWebView.fetchBytes(url)`：

```js
fetch(url).then(r => {
  var rd = r.body.getReader();
  (function pump(){ rd.read().then(x => {
    if (x.done) { send('Z',''); return; }
    send('C', enc(x.value));       // enc = Uint8Array → base64（8KB 一块拼，防爆栈）
    pump();
  }); })();
});
```

Java 侧 `@JavascriptInterface bin(id, kind, payload)` 只往
`ByteArrayOutputStream` 里写，**立刻返回** —— 它在 WebView 的 Java 桥线程上
被调用，一阻塞就把渲染线程一起卡住。

**坑：`credentials:'include'` 会让整个请求 `TypeError: Failed to fetch`。**
surrit 的 CORS 回的是 `Access-Control-Allow-Origin: *`，浏览器规定带凭据的
跨源请求不接受通配。去掉 credentials 立刻 200 —— 也证明了这条路根本不需要
cookie，放行我们的是浏览器栈本身。

体积不是问题：720p 分片实测 **236316 字节 / 810ms**（服务器标
`Content-Type: image/jpeg`，伪装成图片；首字节 `0x47` 是 TS 同步字节）。

### 播放列表必须改写

`VlcRelay` 给 VLC 的地址是 `http://127.0.0.1:PORT/s?u=<base64>`。而 m3u8 里
全是相对路径：

```text
master:  #EXT-X-STREAM-INF:…,RESOLUTION=640x360,\r\n  360p/video.m3u8
media:   #EXTINF:4.004000,\n video0.jpeg
```

VLC 会相对**它拿到的那个地址**解析 —— 结果 `http://127.0.0.1:PORT/720p/video.m3u8`，
query 丢了，中继回 404。所以每一行 URI 都要换成「绝对地址再包一层中继」：

```text
[relay] 播放列表改写 4 条 @https://surrit.com/…/playlist.m3u8
[relay] 播放列表改写 1147 条 @https://surrit.com/…/1080p/video.m3u8
```

`#EXT-X-TOKEN` 这类站点自定义标签原样留着（VLC 会忽略，改了可能让分片对不上）。

Content-Type 自己判，不照抄服务器：文本以 `#EXTM3U` 开头就是
`application/vnd.apple.mpegurl`，其余按 `video/mp2t`。照抄 `image/jpeg` 的话
VLC 的 HLS 解复用器会去当图片处理。

改完的实测：

```text
VLC: decoder output: 1920x1088     ← 1080p 出画
播放器: 01:15 / 2:18:10            ← 完整时长，进度条可拖
取流失败次数: 0
```

## 五、配置生成抽成了纯函数

`MissavSite.probe` 里那段「拼 paths / fields / shapes / ui」没有任何网络依赖，
所以抽成了 `static JSONObject buildConfig(String base, String html)`。

好处很直接：`MissavConfigTest` 拿真实首页 fixture 直接调它，把整份形状钉住 ——

- 5 个 tab，没有「更多」（索引页不进导航）
- 「无码影片」12 个子分类，ids 和 labels 等长
- `web.categories` 覆盖每一个 slug（漏一个就点了没反应）
- `paths.tag-list` 落在 `/api/category`（不是 `/api/genres`）
- `fields` 里有 `episodeNumber` / `source` / `tagName`
- `shape.list` 的 page/pages 路径
- 封面白名单含 `fourhoi`

这七个坑里有五个是这个测试当场能拦下来的。改配置时少一个字段，编译期就能发现。

顺带：测试会把配置写到 `app/build/missav-config.json`，开发期往手机推配置时
不用再走一遍加源。

## 六、代理：手机到 Mac 的那一跳

missav 在这台机器的网络下直连不通。开发期用 `adb reverse` 把 Mac 的 Clash
（7897）映到手机的 `127.0.0.1:7897`，App 里网络代理设成「外部地址
`127.0.0.1:7897`」。

```bash
adb -s 7f8f5254 reverse tcp:7897 tcp:7897
```

**每次 adb 重连都要重做这一条**，否则症状是「过盾排队超时」，而 App 里
代理设置看着一切正常。

配置存在两个 SharedPreferences：`aii-net`（`proxy` 串）和 `aii-proxy-core`
（`mode=external`）。`pm clear` 会把这些连同源配置一起清掉 —— 开发期用
`run-as ... cp` 直接推这两个 XML 更快。

## 七、改了配置就要重新加源

站点配置是**加源时 probe 生成后存进 `user-source.json`** 的，不是每次启动从
代码读。所以：

> 改了 `MissavSite` 里的 `paths`、`fields`、`shapes`、`ui`，必须重新加源，
> 否则跑的还是旧配置 —— 表现是「代码明明改了，界面一点变化都没有」。

开发期绕过的办法（比重新加源快，但要知道自己在干什么）：

```bash
# 1) 生成配置
./gradlew :app:testDebugUnitTest --tests '*MissavConfigTest*'
# → app/build/missav-config.json（记得把原文件的 __url 合并进去）

adb push 配置.json /data/local/tmp/us.json
adb shell am force-stop com.huangguo.mobile
adb shell run-as com.huangguo.mobile cp /data/local/tmp/us.json files/user-source.json
adb shell monkey -p com.huangguo.mobile -c android.intent.category.LAUNCHER 1
```

（`run-as sh -c "cat > …"` 会因为权限被拒，`cp` 可以。）

## 八、留给下一轮的

- **女优 / 发行商**。它们是指引页而不是作品列表。要真正用起来，前端得再加一种
  页面：点女优 → `/cn/actress/{slug}` 看她的作品。适配器这边把
  `/cn/actresses` 解析成 `{slug, name, avatar}` 的列表不难，难的是前端没有
  落脚点。
- **类型只抓前 3 页**（100 个）。全量 42 页 ≈ 十几秒，加源和翻页体验都撑不住。
  要更多就调 `MissavAdapter.GENRE_PAGES`，或者给「全部类型」页做真正的分页。
- **分片每次一个 WebView fetch**。现在够用（4 秒一片、单片 810ms），但 1080p
  在弱网下可能追不上播放速度。真要治，得在 WebView 里做预取队列。
- **`_note` 里的四档清晰度是明文**，站点什么时候改成算签名就什么时候失效。
