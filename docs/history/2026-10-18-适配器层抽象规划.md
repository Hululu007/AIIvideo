接口 70 行，实现平均 800 行。比例 1:11。

**但「实现厚」不等于「实现错」。** 站点解析本来就该厚 —— 每个站 DOM 不同、
路由不同、播放器不同，这部分没有共性可抽，硬抽出来的「通用 HTML 解析器」
比八个正则更难维护。

真正的问题在**厚错了地方**。把小工具区单独量出来：

| Agedm | 586 | 93 | 16% |
| Cms | 519 | 63 | 12% |

合计约 **1200 行** —— **但这个数字是错的，要修正**。

我第一遍用「小工具区」整块量，那里面除了工具函数还有**正则常量和分类表**，
那两样是站点知识，删不得。按「纯管道函数」（stripHtml / unescape /
percentDecode / enc / param / page / base / get）逐个数，真实预算是：

| 适配器 | 纯管道行数 |
|---|---|
| Mrds66 | 117 |
| Porn91 | 71 |
| OpenList | 39 |
| Hanime1 | 15 |
| Missav | 7 |
| Yhdm | 103（迁移前） |

合计约 **360 行**，不是 1200。差了三倍多 —— 记一笔，免得下次又拿错数字
去论证一个正确的结论。

但**结论没变**，因为真正的代价不是行数：

```text
param() / page()    Porn91、Mrds66、Yhdm 三份逐字相同（md5 一致）
percentDecode()     Mrds66 与 Yhdm 只差注释和循环写法，行为一样
stripHtml()         5 个文件各写一遍
enc()               8 个文件各写一遍
get(url)            5 个文件各写一遍，都在做「带 UA 的 AiiHttp.getRaw」
```

这些不是「站点知识」，是**管道**。管道被复制八份，后果不是行数，是
**行为漂移**：`percentDecode` 在 Mrds66 里修过中文解码的 bug（`(char)` 拼字节
导致乱码），Yhdm 是后来照着抄对的 —— 如果抄错，症状和「站点改版」一模一样。

## 二、比重复更贵的：响应形状由每个适配器自己造

这是这次最该改的一条，比抽工具函数重要得多。

`SiteAdapter.fetch()` 的契约是「返回我们内部 JSON 形状的字节」。于是
**每个适配器都自己拼那份形状**：

```java
// Mrds66Adapter / YhdmAdapter
JSONObject out = new JSONObject();
out.put("items", items);
out.put("pagination", pagination(html, page, got));
JSONObject envelope = new JSONObject();
envelope.put("data", result);
```

```java
// MissavAdapter —— 同一件事，另一种拼法
out.put("items", items);
out.put("page", no);
out.put("hasMore", items.length() >= PAGE_SIZE);
return envelope;
```

前端的 `nextPageOf()` 只认 `pagination.page` / `pagination.pages`。所以
Missav 那套平铺形状**读不到翻页**，只能在配置里补：

```json
"shapes": { "list": { "page": "page", "pages": "pages" } }
```

也就是说：**形状不一致 → 每个适配器都要配一份 shapes → 配错就静默不翻页。**
`docs/2026-10-18-missav-适配器.md` 里那条「每个分类页只有第一页」就是这么来的。

同理还有 `web.fields` 别名表：它存在的唯一原因是「每个适配器返回的键名不同」。
如果形状由一份实现统一产出，别名表里一大半条目就没必要了。

**形状是对前端契约的那一半，只能有一份实现。** 各适配器交上来的应该只有
「一页有哪些条目」「这一页是第几页、共几页」这种**数据**，不是 JSON 结构。

## 三、改法

```text
HtmlKit.java        纯文本工具：stripHtml / unescape / text / percentDecode / enc
                    param / page / abs（相对地址拼接）/ firstMatch / allMatches
AdapterIo.java      取字节：base(profile) / get(url) / getJson(url)
AdapterShape.java   响应形状：envelope / listing / detail / play —— 唯一实现
```

适配器只剩三件事：

```java
final class XxxAdapter {
    // ① 这个站的页面/接口长什么样 → 解析成条目
    private static JSONArray cards(String html, String base) { ... }

    // ② 每个动作取哪一页
    private static JSONObject home(String base) { ... }

    // ③ 路由
    public static byte[] fetch(String path, SiteProfile profile) { ... }
}
```

目标：`YhdmAdapter` 1001 → 约 700；`Porn91Adapter` 1097 → 约 750。
省下来的都是管道，**站点知识一行不少**。

这说明省下来的确实是重复，不是功能。真正的收益在下面。

### 保留在各适配器里的（有意为之）

| 文件 | 保留的 | 为什么不能抽 |
|---|---|---|
| `AgedmAdapter` | `normalize()` | 是「去空白」不是 URL 归一化，同名字不同义 |
| `AgedmAdapter` | `get()` | 走 `api` 规则、返回 JSONObject、报错文案是站点专属 |
| `CmsAdapter` | `stripHtml()` | 不插空格的版本（`<b>a</b><b>b</b>` → `ab`） |
| `MissavAdapter` | `get()` | 走 `SiteFetchWebView` 过盾，不是 OkHttp |
| `Porn91Adapter` | `get()` | 要处理游客标记 cookie，同一个 URL 请求两次 |

「同名不同义」是这次最值得记的一课：`AgedmAdapter.normalize` 长得像
URL 归一化，其实是 `replaceAll("[\\s\u3000]+", "")`。批量替换脚本要是
按名字匹配，这里会静默改掉行为 —— 而症状是「标题里多了空格」，
没人会往这儿想。

**迁移时踩到的坑**（写下来免得重来）：第一遍我用「从函数签名往前找注释、
往后找 `    }`」的启发式批量删方法，把**正则常量块**整段吃掉了 ——
编译报十几个「找不到符号」。改用**精确签名匹配**（每个方法单独 `index(sig)`
再找配对的 `}`）才安全。八个适配器里有六个的常量块紧跟在工具函数后面，
用启发式一定会误伤。

已经迁完的 `Mrds66Adapter` 还顺带改了三条测试：`percentDecode` / `enc` /
`normalize` 原来用反射调适配器私有方法，现在这些函数的所有权归 `HtmlKit`，
用例跟着挪过去 —— 行为在哪，测试就在哪。

每步跑全量测试。`FieldsContractTest` 和 `AdaptersTest` 是安全网。

## 三点五、迁完两家的实测收益

```text
YhdmAdapter     1001 → 898   （-103 行）
Mrds66Adapter    995 → 892   （-103 行）
```

省掉的都是什么：

- `param` / `page` / `percentDecode` / `enc` / `stripHtml` / `unescape` / `normalize`
  → `HtmlKit` 一份
- `base(profile)` / `get(url)` → `AdapterIo` 一份
- 手拼 `{items, pagination:{…}}` → `AdapterShape.listing` 一份
- 手拼 `{source, url, videoUrl, quality, lines, episodeNumber}` → `AdapterShape.play`
- 本地 `pagination()` 兜底逻辑（两个适配器各写一遍）→ `AdapterShape.pagination`

**更有价值的是第三、四条**：形状统一之后，前端 `nextPageOf()` 只认
`pagination.page/pages` 这一套，适配器不用再各自配 `web.shapes.list`。
Missav 那次的「每个分类只有第一页」就是这么来的 —— 形状不一致被迫用配置补，
补漏了就静默失效。

行数只降 10%，但**接口面降了**：以前「一页数据」有八种装法，现在一种。

## 四、不做什么

- **不做通用 HTML 选择器引擎。** 八个站八个 DOM，正则比选择器短、比选择器快、
  也比选择器好调。抽象到这里就停。
- **不合并 `fetch()` 的路由分支。** 每个站的动作词汇不一样（OpenList 有 `dir`，
  Missav 有 `genres`），硬统一成一张表会变成「配置里写 Java」。
- **不动 `SiteAdapter` 接口本身。** 70 行是合适的：它回答的是「这是什么站」，
  不回答「怎么解析」。薄，但不该变厚。

# 附：VlcPlayerActivity 拆分（2026-10-18 晚）

## 问题

1990 行，一个 Activity 里挤三件事：libVLC 生命周期、RecyclerView 翻页、
以及**一整套自制 UI 框架**。

```text
buildUi()           651 → 920   270 行纯 UI 搭建
IconButton          内部类，Canvas 手绘播放/暂停/快进图标
makeIconButton      控件工厂
makeButton          ×2
styleSeekBar        LayerDrawable 手工拼进度条
scrim / rounded / animateBar
```

再加五个集合维护多实例状态（playingUrl / urlCache / resolving / failed / altTried）。

## 拆成三块

| 文件 | 行数 | 管什么 |
|---|---|---|
| `VlcPlayerActivity` | 1930 → 1592 | 编排和生命周期：起播、事件、翻页、JS 桥、进度落盘 |
| `VlcControlsView` | 528 | 顶栏/底栏/进度条/倍速面板/提示/错误块 + 手绘控件工厂 |
| `VlcSession` | 143 | 五个集合 + 换线游标 + 续播现场 |

边界用 `VlcControlsView.Host` 定死：控制层只回调「用户做了什么」
（`onPlayPause` / `onSeekBy` / `onSpeedToggle` / `onSeekTo`），不持有任何播放器状态。

## 为什么要拆 VlcSession（不只是为了行数）

那五个集合的生命周期规则互不相同，而它们以前和 UI 混在一起：

- `urlCache` 跨页保留（滑回来直接用）
- `failed` 滑回这一页要清掉（**不是黑名单**，上一次可能只是网络抖）
- `playingUrl` 跟着 player 实例走
- `altTried` 每集独立，到上限收手

这些全是纯逻辑，但以前**一条都测不了** —— 要验「滑回失败过的页会不会重新给机会」
得在真机上来回滑，时序一错就复现不了。现在 `VlcSessionTest` 8 条直接钉住。

## 重构时踩的坑（值得记）

第一版我用「函数签名往前找注释、往后找 `    }`」的启发式批量删方法，
**把翻页器的匿名 OnItemTouchListener 从中间切断了** —— 编译报
「进行语法分析时已到达文件结尾」，花括号少了三个。第二次同样的问题
（删 `IconButton` 内部类时匹配到内层方法的 `}`）。

最终改成**花括号配对**的删除函数（从 `{` 开始数深度，数到 0 才停），
一次过。这条对所有 Java 文件的批量删除都成立：**别用 `\n    }\n` 找方法尾**，
嵌套类和匿名内部类会让它永远找错。
