# 水果派（pie）播放改造方案

目标：让 pie 源在 App 里**真能播**。现在 `play` 只能降级成 `reason:'encrypted'`，因为
CDN 上 m3u8 和每个 `.ts` 都是整文件 AES-128-ECB 密文（key `saIZXc4yMvq0Iz56` 已拿到，
验证过两个视频的 m3u8 和分片）。播放器自己去拉地址，没人替它解。

---

## 一、现状（读代码确认过，不是推测）

播放链路只有一条：

```
VlcPlayerActivity.relayUrl(url)  →  VlcRelay.wrap(url)  →  new Media(libVLC, Uri.parse(...))
                                          │
VLC ──HTTP──> http://127.0.0.1:<port>/s?u=<base64 原始地址>
                    │
                    └─ OkHttp（带代理）──> 原站/CDN ──> 原样写回
```

两个关键事实决定了改法：

1. **中继已经在改写播放列表。** `rewriteM3u8()` 把每一条 URI 都换成
   `http://127.0.0.1:PORT/s?u=<b64 绝对地址>`，注释写得很清楚：「不能回头用 `wrap()`」。
   也就是说 pie 解出来的相对段名（`TFkN-00000.ts`）会被解析成
   `…/hls/decrypt/TFkN-00000.ts` 再包回中继 —— **分片天然会回流到中继**，不用另外做映射表。
2. **`MediaProxy` 是 WebView 那条路的**（`shouldInterceptRequest`），和 VLC 无关，别动它。

所以改造点只有一个：**在中继里，把「拿到密文 → 解密 → 交给 VLC」这一段插进去**。

---

## 二、改造后的数据流

```
VLC  GET /s?u=<b64 encryption_url>
 ├─ 中继 OkHttp 拉回 8336 字节密文
 ├─ MediaCipher.applies(url) == true
 ├─ 解密 → "#EXTM3U…TFkN-00000.ts…"（248 段）
 ├─ rewriteM3u8：每段 → /s?u=<b64 …/TFkN-00000.ts>
 └─ 200 application/vnd.apple.mpegurl + Accept-Ranges: none
VLC  GET /s?u=<b64 …/TFkN-00000.ts>
 ├─ 拉回 240832 字节密文
 ├─ 流式解密（64KB 一块，末块去 PKCS#7）
 └─ 200 video/mp2t（Accept-Ranges: none）
```

VLC、播放器、`VlcPlayerActivity` 全都不用改。

---

## 三、改动清单

### 1. 新增 `MediaCipher.java`（约 180 行）

| 方法 | 作用 |
|---|---|
| `configure(JSONObject media)` | 从站点配置装配；null / 缺 `decrypt` = 全关（默认行为不变） |
| `boolean applies(String url)` | 命中判定：`pathHas` 子串 + 可选 `hosts` 精确匹配 |
| `byte[] decryptAll(byte[] in, int cap)` | 播放列表用；`cap` 4MB 防呆 |
| `InputStream openDecrypted(InputStream in)` | 分片用；边读边解，64KB 缓冲，**最后一块才去 PKCS#7** |
| `String sniff(byte[] head)` | 自检：解出来应该是 `#EXTM3U` 或 `0x47` 开头 |

实现就是 `Cipher.getInstance("AES/ECB/NoPadding")` 逐块解；ECB 每块独立，所以
流式没问题。PKCS#7 的处理放在 `openDecrypted` 的收尾（推后一块，EOF 时才去 padding）。

### 2. `VlcRelay.java`（3 处，约 40 行）

- **`wrap()`**：`MediaCipher.applies(url)` 时**强制**回中继（现在「没代理就直连」）。
  这是必须的一条 —— pie 的 CDN 大概率直连更快，不加这条就绕过中继、密文直接喂给 VLC。
- **播放列表分支（`playlistByUrl`，第 411 行那一段）**：`bytes()` 之后先
  `MediaCipher.decryptAll()`，再 `new String(...)`、再 `rewritePlaylist()`。
- **分片分支（响应体透传那段）**：命中解密时
  - 丢掉请求里的 `Range`（ECB 的密文偏移和明文偏移一一对应，但 PKCS#7 只在末尾，
    一期不做偏移解密）；
  - 头里写 `Accept-Ranges: none`、`Content-Type: video/mp2t`、
    `Content-Length` = 上游长度 − pad（拿不到就省略，用 chunked）；
  - body 走 `openDecrypted(src)` 流式搬。
- **HEAD 探测**（第 313 行）：命中解密时直接回 `200 + Accept-Ranges: none`，不带长度。

### 3. `SiteProfile.java`（1 处，约 15 行）

在 `PlaybackHttpBridge.configure(...)` 旁边加 `MediaCipher.configure(object("media"))` ——
那是全 App 唯一「当前源长什么样」的装配点，别另开一处。

### 4. 配置 schema（`pie.json`）

```json
"media": {
  "decrypt": {
    "mode": "aes-ecb",
    "key": "saIZXc4yMvq0Iz56",
    "keyEncoding": "text",
    "padding": "pkcs7",
    "match": { "pathHas": "/encry/" }
  }
}
```

`pathHas` 比 `hosts` 稳：CDN 域名每个视频都不一样（`lvacm.fruit.tjfuxinjia.com`、
`gztp7fws01jv.shyunzhiyi.com`…），但路径里 `…/encry/vd/…/hls/decrypt/` 是固定的。
`hosts` 可留空。

### 5. 源侧 `pie.js`

`play` 从「降级」改成给真地址：

```js
var enc = film && str(film.encryption_url);
if (enc) return { url: enc, alts: [{ line: 'default', name: '默认线路', url: enc }], episodeNumber: 1 };
```

离线回归那条断言要跟着改（现在断言的是 `reason === 'encrypted'`）。

## 四、Range 与 seek（一期 / 二期）

| | 一期（建议） | 二期 |
|---|---|---|
| 做法 | 丢弃 Range，整段下发，`Accept-Ranges: none` | 起始偏移 16 对齐时按块解密，原样回 `Content-Range` |
| 代价 | 拖进度 = 从这一段开头重拉（10 秒 ~2MB） | 无 |
| 风险 | 无 | 末尾 padding 只对最后一块生效，`Content-Length` 要按块算，容易错 |

VLC 对没有 Range 的 HTTP 源能正常流式播（现在伪装后缀那条路就是 `Accept-Ranges: none`，
已经在跑）。先一期，播放稳定再说 seek。

---

## 五、失败模式与日志

这段逻辑最容易出的问题不是崩溃，是「静默出垃圾」，所以三处都要有明确日志：

| 情况 | 行为 |
|---|---|
| 长度不是 16 的倍数 | 不解密，原文透传，`[cipher] 长度不是 16 的倍数 8337 @ …` |
| 解出来不是 `#EXTM3U` / `0x47` | 判 key 不对，原文透传，`[cipher] 解密后不像 HLS（key 换过了？）` |
| 播放列表 > 4MB | 拒绝解密，报错，不读进内存 |
| 上游 4xx/5xx | 原样透传状态码，不解密 |

自检那一条是这次改造的保险丝：key 一换，日志里立刻能看到「不像 HLS」，而不是让用户
对着黑屏猜。

## 六、测试

- `MediaCipherTest`（新，约 120 行）：拿 `work/re/pie/` 那对真实密文/明文钉住
  - 1024 字节 m3u8 → 明文 1008 字节 + pad 16
  - 240832 字节 TS → 首包 `47 40 11 10`，0x47 落在 188 的整数倍
  - 输入长度 1/15/16/17/18 字节的边界（分块拼接不能错位）
  - `pathHas` 命中/不命中
- `VlcRelayTest` 增加两条：解密后的播放列表经过 `rewriteM3u8` 后每条都是 `/s?u=…`；
  `applies()` 命中时 `wrap()` 在无代理下也返回中继地址。
- 真机（模拟器）：播 `film 10451`（免费老片，248 段），日志里应出现
  `[cipher] decrypt …/index.m3u8 8336→8320` 和分片的 `→240828`，画面出帧。

---

## 七、不做的事

- 不改 VLC / 不加 native 模块（`libvlc` 的 demux 插件要另编，收益不抵成本）
- 不预下载整片（248 段 ≈ 500MB，还不能 seek）
- 不在 spider 里解（spider 只能返回字符串，没法把字节交给播放器）
- 不动 `MediaProxy`（那是 WebView 的媒体路径）

## 九、要你拍板的三件事

1. **key 放哪儿**：放源配置（`pie.json`，可热更、别的源也能复用，推荐）还是写进 Java 常量
   （隐蔽一点，但换 key 要发版）。
2. **spider ABI 升不升 2**：升了 `requires:'>=2'`，老 App 装不上这个源，语义干净；
   不升的话老 App 装了 pie 会黑屏（它会把密文地址直接交给播放器）。
3. **一期接受「拖进度重拉整段」吗**：接受就先上一期，seek 放到二期。
