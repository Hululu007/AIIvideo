**`app.js` 末尾新增 `fitFilmRows()`** — 卡片铺满

首页区块的 CSS 是「固定 2 行 + 横向滚动、每列 106px」。412px 宽的屏幕能排 3 列，但**「精选推荐」这个区块站点只返回 4 条数据**，于是只占 2 列，右侧空出 146px —— 观感上像"少放了一个"。

```
精选推荐: 4 条,  clientWidth=412, scrollWidth=412   ← 只有 2 列，右边空 146px
最近上新: 8 条,  clientWidth=412, scrollWidth=490   ← 3 列，正常横向滚动
```

判定规则：**只有"撑满后每格仍不小于 106px"时才铺开**。

```js
const columns = Math.ceil(row.children.length / 2);   // CSS 固定 2 行
const needed = columns * 106 + (columns - 1) * gap;
row.classList.toggle('is-fit', needed < available - 4);
```

实测两种数据量下的结果：

| 区块 | 条数 | 处理 | 卡片宽 | 总占宽 |
|---|---|---|---|---|
| 精选推荐 | 4 | `is-fit` | 114 → **183px** | 412 → 铺满 394px |
| 最近上新 | 8 | 不加 | 114px（不变） | 保持 490px 可滚动 |

用 `MutationObserver` 挂在 `#content` 上自动重算，**只监听 `childList` 不监听 `attributes`**——否则自己加的 class 会把回调再触发一遍形成循环。另外挂了 `resize` 应对横竖屏切换。

### 其它文件

**`app.html`** — ~~在 `app.js` 之前插入 `<script src="vendor/hls.min.js"></script>`~~ **已于 2026-10-16 移除**，见第十二节。

**`vendor/hls.min.js`** — ~~新增，hls.js 1.5.17，414KB。~~ **已删除。**

它**从头到尾没用上**。最终播放走的是 WebView 原生 HLS，原因见坑 4：CDN 按 `Origin` 分流，hls.js 走 XHR 必然带上 `appassets.androidplatform.net` 这个 Origin，会被判为套壳 APP 并返回宣传片；`<video src>` 的 media 请求不带 Origin，才能拿到正片。

当初留它是当备胎：万一某台设备不支持原生 HLS，把 `window.__feedUseHlsJs` 置 true 就切回去。但这个备胎充不上气——`__feedUseHlsJs` 全项目**只有 `feed-player.js` 一处在读，没有任何地方写**，而且真切过去也只会播到那支 54 秒宣传片。它唯一实际产生的作用是让 CSP 多开了三个口子，见第十二节。

`connect-src 'none'` 会让 hls.js 的 XHR 全军覆没。`frame-src` / `object-src` / `script-src` 的限制原样保留。

**`smali/com/huangguo/mobile/MainActivity.smali`** — 两处

## 三、八个坑（都是这轮踩的）

### 坑 1：CSP 是第一道门

改了 `app.js` 接上 hls.js 后，logcat 里是：

```
Refused to connect to 'https://yd-hls.hzjvlo.cn/...m3u8?...' because it violates
the following Content Security Policy directive: "connect-src 'none'"
```

原作者的策略是"所有网络访问必须走 Java 桥"，CSP 里 `connect-src 'none'`、`default-src 'self' data:`，只给图片开了 `https:` 的口子。所以**封面能显示，视频不能播**。

### 坑 2：autoplay 策略是第二道门

CSP 放开后视频仍不出画面。加诊断打点（原版会把 `console.log` 转发到 logcat 的 `D HuangGuo` 标签）才看清：

```
[feed] ep=1 Hls=true isSupported=true MSE=true canPlayHls=maybe url=...
[feed] hls error type=networkError details=manifestLoadError fatal=true
```

hls.js 本身没毛病，是请求层失败。CDN 的 `access-control-allow-origin: *` 也确认给了，CORS 不是原因。

### 坑 3：系统代理

用 CDP 连进 WebView 抓 `Network.loadingFailed`，拿到了准确错误：

```
net::ERR_PROXY_CONNECTION_FAILED
```

模拟器里残留着 `settings global http_proxy = 10.0.2.2:8080`（早前 MITM 留下的，服务早已不在）。

**关键区别**：Java 层的 `HttpURLConnection` 和 WebView 的 Chromium 网络栈是两个独立实现，前者不受这个代理影响，后者会读。所以同一台设备上，`SiteRepository` 抓站正常，WebView 里的 fetch 全挂。

```bash
adb shell settings put global http_proxy :0
adb shell settings delete global global_http_proxy_host
adb shell settings delete global global_http_proxy_port
```

### 坑 4：CDN 按 Origin 喂广告 —— 站点在反套壳（最隐蔽的一个）

代理清掉后视频能播了，**但播的不是正片，是一段 54 秒的宣传片**（画面带巨大金色条 + 二维码，写着"观看更多黄果原创短剧"）。当时误判成"能播就行"收工了，实测后才发现内容不对。

排查链条：

1. 页面 `#videoInitialData` 里的 `videoSrc` → `/video/5860/ep-10/` 给的是 `33289a62…`
2. 拿这个 m3u8 算时长 = **441.5 秒**，86 个分片同源，crypt.key 也是自己 → 正片，没插片
3. 但 APP 里 `video.duration` = **54 秒**
4. CDP 抓网络请求，发现有个 `crypt.key` 的路径是 `853acaba…` —— **这个 hash 不在这部剧的任何一集里**

拿同一个 m3u8 URL、只换请求头测：

| 请求头 | 返回内容 |
|---|---|
| 裸请求 | `33289a62` — **441.5 秒正片** |
| `Origin: https://huangguoai.com` | `33289a62` — 正片 |
| `Origin: https://huangguoai.ai` | `33289a62` — 正片 |
| `Origin: null` / 任意其他站 | `33289a62` — 正片 |
| **`Origin: https://appassets.androidplatform.net`** | **`853acaba` — 54 秒宣传片** |

**全表只有这一个 Origin 被喂广告。** 而 `appassets.androidplatform.net` 正是 Android `WebViewAssetLoader` 的默认域名——**站点专门把"WebView 套壳 APP"列进了黑名单**。

原版作者用原生 ExoPlayer 播放（`open-player` → `PlayerActivity`），ExoPlayer 不发 Origin 头，所以一直是好的。**改成 WebView 内播放反而踩中了这条规则。**

**解法**：不用 hls.js，改用 `<video src>` 走原生 HLS。

```js
// hls.js 走 XHR，必然带 Origin: https://appassets.androidplatform.net → 拿到广告
// <video src> 的 media 请求不带 Origin → 拿到正片
if (window.__feedUseHlsJs) { /* hls.js 分支，保留备用 */ }
else { video.src = url; video.load(); }
```

实测 Android WebView 原生支持 HLS（`canPlayType('application/vnd.apple.mpegurl')` → `maybe`），AES-128 解密由底层 MediaPlayer 处理。改完后 ep1 = 218s、ep2 = 407s、ep3 = 251s，与页面数据逐个吻合。

`hls.js` 仍留在 `assets/vendor/` 里，把 `window.__feedUseHlsJs` 置 true 就能切回去（比如某天站点换了防护策略）。

### 坑 5：原生 HLS 的能力边界（先测再做，省一轮返工）

换成原生播放后，倍速和拖拽进度能不能用是未知的——Android WebView 的原生 HLS 走 `MediaPlayer`，不是 MSE，行为不一定和桌面 Chrome 一致。动手写功能前先用 CDP 在页面里建了个临时 video 实测：

```
dur: 441, ready: 4, buffered: 441
rate1x: 4.00   (4 秒里推进 4 秒)
rate2x: 7.45   (4 秒里推进 7.45 秒，ratio 1.86)
rateWorks: true
seekWorks: true   (跳到 200 秒后实际停在 202)
```

两项都可用，于是按「长按加速 + 可拖拽进度条」来设计。**第一次测时因为没等缓冲稳定跑出了假阴性（`ratio≈1.08`），第二次加了「连续两次采样 currentTime 都在前进」的稳定判据才拿到真实结果**——测性能类能力时，样本本身的准备状态比断言更重要。

### 坑 6：返回键踩不到播放层（用户实测发现）

**现象**：看剧时按系统返回，画面纹丝不动，还停在播放页；连按几次才退出到桌面。

**根因**：播放层 `.feed` 是 `position:fixed; z-index:80` 的**独立图层**，挂在 `#app` 上，不属于 `#content`。而原版的 `hgBack()` 对未知路由只做一件事：

```js
if (state.route !== 'home') { goHome(); return true; }
```

`goHome()` 确实跑了、`#content` 也换成了首页——**但那层播放器还盖在上面**，视觉上毫无变化，用户自然以为"返回没反应"。

**改动**（三处）：

1. 抽出 `feedClose()`，让返回键和左上角按钮走同一条路径
2. `hgBack()` 里在判断根视图**之前**加分支：
   ```js
   if (state.route === 'feed' || document.querySelector('.feed')) return feedClose();
   ```
   双条件是兜底——即使路由已被别的路径改走，只要图层还在就收掉
3. `updateBackEnabled()` 里加同样的兜底，保证任何路由切换都不会把播放层留在屏幕上

顺带修了 `feedCleanup()` 的空值隐患：`feed?.querySelectorAll(...).forEach(...)` 在 `.feed` 不存在时会抛 `TypeError`——可选链只保护了前半段。

**验证**（实测三级链路）：

| 位置 | 按返回 | 结果 |
|---|---|---|
| feed | → `route:"detail"` | 回详情页，选集可见 |
| 详情页 | → `route:"home"` | 回首页 |
| 首页 | → `NexusLauncherActivity` | 正常退出 |

**教训**：往别人的路由体系里插新界面时，不能只做到"渲染出来"，还得接进它的返回栈。原版有 `setBackEnabled` / `hgBack` / `isRootColumn` 一整套约定，我第一版只顾着把 feed 画出来，没接进去。这种问题自己测不容易发现——因为开发时都在用界面上的返回键，很少按系统返回键。

### 坑 7：封面是 AES 加密的，而且接口给的是相对路径

接口化之后首页所有封面变成了**占位字**（标题首字：神、女、高、少）。logcat 里刷屏：

```
E HuangGuo: cover failed
E HuangGuo: java.lang.IllegalArgumentException: 无效封面地址
    at com.huangguo.mobile.SiteProfile.coverUrl(SiteProfile.java:122)
    at com.huangguo.mobile.SiteRepository.coverData(SiteRepository.java:312)
```

我第一轮判断成了"接口给的是明文 jpg，Java 那套解密是多余的"，于是在前端加了个 `plainCovers` 白名单放行明文地址。**这个判断是错的。**

`SiteProfile.coverUrl()` 的真实逻辑（jadx 反编译 `work/rev_cz/`）：

```java
URI uri = new URI(str);
String host = uri.getHost();
if (!"https".equals(uri.getScheme()) || host == null || uri.getUserInfo() != null)
    throw new IllegalArgumentException("无效封面地址");
// host 还必须在 cover.allowedHosts 白名单里，否则 "无效封面域名"
```

而 `/api/home` 返回的封面是**裸相对路径** `/upload_01/upload/xxx.jpg`，`getScheme()` 是 `null`，第一关就抛。`plainCovers` 之所以没生效，是因为 `new URL('/upload_01/...')` 本身在 JS 里就抛异常，被 `catch` 吞了，白名单永远是空的。

**封面到底是不是加密的**——看字节：

```
$ curl -s .../2026092411162272798.jpg | head -c 16 | xxd -p
093de3b1fc4af46ff223ac4c8bdb076a
$ curl -s .../2026101116034363882.jpg | head -c 16 | xxd -p
093de3b1fc4af46ff223ac4c8bdb076a     ← 三张不同的图，前 16 字节完全一样
```

三张不同图片的头 16 字节一模一样，这是 AES-CBC **固定 IV** 的指纹：JPEG 头 `FFD8FFE000104A464946000101...` 每个文件都相同，同 key 同 IV 就编出同一个密文块。明文 `Content-Type: binary/octet-stream` 也在暗示这一点。

`site-default.json` 里配置齐全：

```json
"cover": {
  "allowedHosts": ["pic.fisawck.cn", "pic.tkzdds.cn", "pic.wirqed.cn", "pic.drleao.cn"],
  "mode": "aes-cbc",
  "transformation": "AES/CBC/NoPadding",
  "key": "f5d965df75336270",
  "iv": "97b60374abc2fbe1",
  "keyEncoding": "text",
  "headerRepair": "legacy-xor"
}
```

`pic.drleao.cn` 本来就在白名单里。本地用 Python 复现整条链，确认解密出来就是正片封面：

```python
raw = fetch(url)                                  # 174816 字节
out = AES_CBC_decrypt(raw, key=b'f5d965df75336270', iv=b'97b60374abc2fbe1')
# out[:16] = ffd8ffe0001044464946000101000001     ← 注意 byte[6] 是 0x44 ('D')
out[6] ^= 0x0E                                    # 'D' → 'J'
# out[:16] = ffd8ffe000104a464946000101000001     ← 标准 JFIF，1086x1448
```

`repairCoverHeader` 干的就是最后那步 `bArr[6] ^= 0x0E`（`Ascii.SO`）。原版加密时把 JPEG 头里的 `J`(0x4A) 异或成 `D`(0x44)，解密后要再异或回来。

**正确改法**：把相对路径补成绝对 https URL，然后照旧交给 Java 的 `cover` 动作，让它走 `coverData()` 的「抓图 → AES-CBC 解密 → 修头 → `data:image/jpeg;base64`」全流程。我那个 `plainCovers` 白名单整个删掉了。

```js
const IMG_ORIGIN = 'https://pic.drleao.cn';
function coverImageUrl(raw) {
  let url = String(raw || '').trim();
  if (/^\/\//.test(url)) url = 'https:' + url;
  else if (!/^https?:\/\//i.test(url)) url = IMG_ORIGIN + (url[0] === '/' ? url : '/' + url);
  // 顺手剥掉 auth_key
  return url;
}
```

**顺带发现的**：图片 CDN 根本不校验 `auth_key`。`/api/videos` 返回的封面尾上挂了个带过期时间的签名（`auth_key=1792086154-0-0-<md5>`，约 2 小时后失效），但拿伪造的过期签名去请求照样 200、字节数一致：

```
$ curl -o /dev/null -w '%{http_code} %{size_download}' \
    "...jpg?auth_key=1000000000-0-0-00000000000000000000000000000000"
200 174816
```

所以统一把 `auth_key` 剥掉（只在该参数是唯一 query 时），换成永久地址，省得两小时后封面集体 403。

**教训**：看到「解密失败」先怀疑数据形态，别急着怀疑解密逻辑本身。我上一轮把"地址不合法"误读成"不需要解密"，代价是一次完整的错误实现 + 一次全量回归。

### 坑 8：`/api/videos` 的 tag 参数是假的

## 六、缓存：什么会存，什么每次都要重新拉

| 内容 | 有没有缓存 | 存在哪 | 策略 |
|---|---|---|---|
| 首页 `home` | 有 | SharedPreferences `cache:home` | 先渲染缓存再后台刷新，保留 80 条 |
| 分类 `category:<id>:<page>` | 有 | 同上 | 同上，保留 79 条 |
| 详情 `detail:<id>` | 有 | 同上 | 同上 |
| 搜索 `search:<kw>` | 有 | 同上 | 同上 |
| 标签 `tag:<slug>:<page>` | 有 | 同上 | 同上 |
| 封面图 | 有 | Java 侧解密缓存 + WebView HTTP 缓存 | |
| 轮播取色 | 有 | localStorage `banner-palettes` | |
| **观看进度** | 有 | localStorage `hgpref:progress` | 改造时加的，每 5 秒记一次 |
| **播放地址** | 有 | localStorage `hgpref:epurl` | 改造时加的，8 分钟窗口 |
| **视频分片** | **部分** | WebView 的 Chromium HTTP 缓存 | 同一个 URL 8 分钟内命中；换集或过期则重拉 |

数据层是原版就有的设计，前端用的是 **stale-while-revalidate**——先拿缓存把界面渲染出来，再在后台拉新的覆盖。所以打开 APP 基本是秒出内容，不会白屏等网络。

### 进播放页时不再重复拉一次选集

原版 `goDetail()` 已经是缓存优先的：先 `api('cached', {key:'detail:<id>'})` 渲染，网络回来再覆盖，实测第二次进详情页不会出现 loading。

**但 `renderFeed()` 是后来我加的，第一版直接 `await api('detail')` 打网络**——而用户是刚从详情页点「立即播放」进来的，那份数据 `goDetail` 才刚拿到手。等于同一份数据连拉两次，中间白等一个往返。

改成三级取用：

```js
// 1. 内存里刚拿到的详情（最快，几乎 0 耗时）
let detail = (state.detail && String(state.detail.id) === String(videoId) && asArray(state.detail.episodes).length)
  ? state.detail : null;
// 2. 持久缓存
if (!detail) {
  const cached = await api('cached', { key: `detail:${videoId}` }).catch(() => null);
  if (cached?.data && asArray(cached.data.episodes).length) detail = cached.data;
}
// 3. 兜底才走网络
if (!detail) { content.innerHTML = '<div class="feed-boot">正在加载…</div>'; detail = await api('detail', {id: videoId}); }
```

**只有真的要等网络时才显示「正在加载…」**。实测：

```json
{"ms":8, "bootSeen":false, "epCount":13}
```

从 810ms（一次网络往返）降到 **8ms**，且「正在加载…」不再出现。

顺带把播放地址的复用窗口从 4 分钟放宽到 8 分钟（`auth_key` 是签发时间，实测 +600 秒仍有效，留了余量），并给 `video` 加了 `error` 监听：**复用的地址万一过期，就丢掉它让下次重新签发**，不会一直卡在错误上。

### 为什么视频只有"部分"缓存

原版其实有一个不错的视频缓存：`VideoPlaybackCache` 用 Media3 的 `SimpleCache`，**128MB 磁盘 LRU**，落在 `cache/video-segments`。但它只挂在 `PlayerActivity`（原生 ExoPlayer）的 `setMediaSourceFactory` 上：

```java
ExoPlayer.Builder(this).setMediaSourceFactory(VideoPlaybackCache.sources(this)).build();
```

**改造后播放搬到了 WebView 的 `<video>`，走 Chromium 自己的网络栈，够不到这个 SimpleCache。** 这是竖屏 feed 的代价。

### 补的那一层：URL 复用

播放地址是带 `auth_key` 的签名链接，**每次请求 `episode` 都签发一个新的**。URL 一变，Chromium 的 HTTP 缓存就永远命不中——滑走再滑回来都要重拉整条流。

所以在 `app.js` 里加了一层 URL 复用：签名后 8 分钟内复用同一个 URL（CDN 给的 `cache-control` 是 `max-age=300`，`auth_key` 本身实测 +600 秒仍有效，留了余量）。URL 稳定了，m3u8 和分片就能吃到 Chromium 自己的缓存。

实测重新进入同一集：`readyState:4, buffered:218, seekable:218`——整集 218 秒已在缓冲里，秒开。

**要做"永久离线缓存"**（看过一次就存下来，断网也能看），得在 Java 层写：拦 `WebViewClient.shouldInterceptRequest`，把 CDN 请求按"URL 去掉 auth_key"做 key 存进磁盘。工作量不小，但路子是通的。

## 七、国内直连线路（重要）

原版 `site-default.json` 的 `origin` 是 `https://huangguoai.com`。这个域名**在国内被 DNS 污染**——用阿里 DoH 查它的真实解析结果是：

```
huangguoai.com  →  108.160.169.185
```

`108.160.169.185` 属于 **Dropbox 的 IP 段**，不是这个站点自己的。GFW 对墙外域名返回这种垃圾 IP，所以国内手机解析出来直接连不上，表现就是 APP 打开一片空白。

站点自己在维护一份「备用地址（直连无需代理）」列表，格式是随机子域 + 基础域，例如：

```
yjcy94.lq41d53z.cc
dn9d.lq41d53z.cc
a037a0.lq41d53z.cc
```

用 DoH 查它们的真实解析：

| 域名 | 真实 IP | 说明 |
|---|---|---|
| `yjcy94.lq41d53z.cc` | 43.229.39.227 / 103.41.185.230 等 | Cloudflare，**未被污染** |
| `cab3f.nt17g20k.cc` | 同上（三个入口都 301 跳到这里） | 同上 |
| `yd-hls.hzjvlo.cn` | 119.188.11.61 | **国内**（山东联通）—— m3u8 所在 |
| `tp1.drleao.cn` | 101.28.255.94 / 218.24.83.103 等 | **国内**，`Server: Lego Server` |
| `pic.drleao.cn` | 42.236.90.50 / 157.119.252.59 | **国内**（河南联通）—— 封面图 |

**结论：视频和图片 CDN 本来就是国内节点，唯一被卡住的就是站点入口。** 所以只需要把 `origin` 换成新入口即可，`site-default.json` 改一行：

```json
"origin": "https://yjcy94.lq41d53z.cc"
```

`Referer` 用的是 `{origin}/` 占位符，会自动跟着变，不用动。

三个入口都是 301 跳到 `cab3f.nt17g20k.cc`，`HttpURLConnection` 默认跟随重定向，所以直接用入口域即可——**选入口不选跳转目标，是因为入口域是站点对外公布并维护的，跳转目标变了入口会跟着走**。

**如果哪天这个线路也连不上**：从站点页面拿一个新的备用地址，改 `site-default.json` 第一行，按第五节重新打包。判断新地址是否可用，用 DoH 查一下别解析成 `108.160.x.x` 这类不相干的 IP 就行：

```bash
curl -s "https://dns.alidns.com/resolve?name=新地址&type=A"
```

### 真机冷启动慢、最后弹「网络走丢了」的原因与修复

用户把 APP 从后台彻底划掉再打开时，旧链路是：WebView `fetch()` 最多等 20 秒 → 失败后回退 `bridgeCall('home')` → Java 仍访问 `huangguoai.com` → Android 解析到不可达的 IPv6 地址 → 站点抓 HTML 再超时。真机日志记录到：

```text
[api] home 接口失败，回退桥接：The user aborted a request. @52
SocketTimeoutException: failed to connect to huangguoai.com/2a03:2880:... after 15000ms
```

改了三件事，每一件都有真机数据支撑。

**一、REST 请求改走 Java 原生桥。** WebView 的 `fetch()` 会自动带 `Origin: https://appassets.androidplatform.net`，这个头会让 API 入口连接超时；Java 的 `HttpURLConnection` 不带。实现上借用现有 `detail` action 传受控的 `/api/...` 路径，`SiteRepository.detail()` 检测 `/api/` 前缀后复用已有 `fetch()` 返回 JSON —— 不新增方法，因为原包 DEX 已经贴着 65,536 的 method-id 上限，加了 `apktool` 直接打不出包。

**二、失败不再回退 HTML。** REST 失败就进页面错误态 + 自动退避重试（2s / 5s / 12s），绝不退回那条要等 40～50 秒的旧抓取路径。

**三、首屏请求瘦身（效果最大的一条）。** 分类页原来一次要 20 条，响应约 20KB：

```text
/api/videos?cate_id=24&page=1&size=20      →  28480ms（另有 40s 只收到 5.7KB 的记录）
/api/videos?cate_id=24&page=1&size=8       →   1268ms
/api/videos?cate_id=25&page=1&size=8       →   1676ms
/api/videos?cate_id=24&page=2&size=20      →   4328ms（翻页，用户已在看内容）
```

首屏从 28 秒降到 1.3 秒。一屏是 3 列 × 2 行 = 6 张卡片，8 条够铺满还有余量；翻页仍按 20 条走。**没有字段裁剪能力**，响应体积和条数严格成正比（实测 20 条 19.9KB / 10 条 10.3KB / 5 条 5.4KB），所以只能靠减少条数。

### 顺带修掉的一个回归：内容缓存失效了

原版把内容缓存写在 Java 的 `AppStore.saveCache()`，而那是 `dispatch()` 在**桥调用返回之后**执行的。数据层改成 REST 之后 `home`/`detail`/`category` 不再经过 `dispatch()`，`saveCache` 的调用点全部失效 —— `cache:home` 永远是空的，冷启动必然无数据可画。

改成前端 localStorage 自管（`hgcache:` 前缀，key 沿用原命名），顺带拿到两个好处：`localStorage` 是同步读的，首屏不用等任何网络往返；接口挂了也能拿旧内容兜底。

真机验证（**关掉 Wi-Fi 和移动数据**后冷启动）：

```text
[api] /api/home FAIL 31ms 站点连接失败      ← 断网时 31ms 快速失败，不再干等 20 秒
```

首页 hero、精选推荐、热门漫剧全部正常渲染，封面来自 Java 磁盘缓存。**完全离线可用。**

### 一条重要的现场结论：这条链路是「慢」，不是「坏」

同一个接口连续三次，结果可以完全不同：

```text
/api/videos?cate_id=24&page=1&size=20   第1次: 连接失败
                                        第2次: 2.18s / 19937B
                                        第3次: 40.0s / 5739B（超时截断）
```

TCP 握手通常 0.3 秒就成，但握手之后传输会被压到每秒几百字节然后断流。同时测同一台手机上的国内节点：

| 目标 | 线路 | 结果 |
|---|---|---|
| `cab3f.nt17g20k.cc` | Cloudflare | 时通时断，2s ~ 40s |
| `pic.drleao.cn` | 国内（河南联通） | **0.10 秒收完 174KB**，三次全稳 |
| `yd-hls.hzjvlo.cn` | 国内（山东联通） | **0.13 秒**，三次全稳 |

所以图片和视频一直很流畅，卡的只有 API。**站点的所有入口域名（`cab3f.nt17g20k.cc`、`hgai5.com`、`yjcy94.lq41d53z.cc`、`zsharex.com` 等）解析到完全相同的 5 个 IP**，换域名没有意义；直连 IP 也不行（Cloudflare 要 SNI）。`pic.drleao.cn` 虽是国内节点但只是静态 CDN，`/api/*` 一律返回空 200。

结论：**这个 app 的体验上限被这条链路卡住了。** 想彻底解决只能自建反代（把 API 转到国内节点），那是另一个工程。

## 十、倍速与横屏是怎么做的

### 倍速

右下角一个按钮展开面板，五档：0.75× / 1× / 1.25× / 1.5× / 2×。选中值存 `hgpref:feedrate`，切集、重新进入都保持。

和已有的「长按临时 2×」是两套逻辑，靠 `video.dataset.tempSpeed` 区分：长按开始时打这个标记并写 `playbackRate = 2`，松手时清标记并**恢复用户选定的档位**（不是硬写 1，否则长按一次就把选的 1.5× 冲掉了）。`applyRate()` 遍历所有集时跳过带这个标记的 video，避免把长按中的那集改回去。

### 播放时收起外壳

播放中，进度条、集数、时间、倍速与横屏按钮全部隐去；点一下屏幕暂停才出现。沉浸播放时画面是干净的，这符合播放器的常规预期。

用 `.feed.is-playing` 驱动，`opacity` 和 `pointer-events` 一起切：

```css
.feed.is-playing .feed-hud,
.feed.is-playing .feed-bar,
.feed.is-playing .feed-times,
.feed.is-playing .feed-controls{opacity:0;pointer-events:none}
```

**只切 `opacity` 是不够的** —— 淡出之后元素还在原地，仍然能被点到，进度条会被误拖。必须同时把 `pointer-events` 关掉。

关键点：**只有当前可见那一集的播放状态算数**。相邻集会预热和回收，它们同样会触发 `play` / `pause` 事件；拿任意一集的 `video.paused` 去决定整层显隐，会出现「滑到下一集时外壳莫名闪一下」或者「明明在播、外壳却不消失」。所以 `feed-player.js` 里维护了一个 `activePage`，由 `IntersectionObserver` 判定当前集时**先赋值再起播**，`play` / `pause` 事件里只在这个集上才同步外壳。

返回键不参与收起。它是导航而不是播放信息，留着省一次点击——想退出时不必先暂停。

一个附带处理：收起时顺手把倍速面板关掉，否则下次暂停会看到一个上次留着展开的面板。

### 横屏：不能走 Fullscreen API

第一版写的是 `feed.requestFullscreen()` + `screen.orientation.lock('landscape')`，**在这个包里全是空转**。两条硬约束：

```xml
<!-- AndroidManifest.xml -->
<activity android:name="com.huangguo.mobile.MainActivity"
          android:screenOrientation="portrait" ... />
```

```text
MainActivity$2  (WebChromeClient) 只有 onConsoleMessage / onJsConfirm
→ 没有 onShowCustomView / onHideCustomView
```

Manifest 锁死竖屏，WebChromeClient 又没实现全屏回调，所以 `requestFullscreen()` 找不到出口，`orientation.lock()` 也被系统拒绝。Java 桥只有 `request` / `setBackEnabled` / `setDetailMode` 三个方法，加不了旋转（原包 method-id 已接近 65536 上限，加方法有风险）。

**改用纯 CSS 旋转**：把每一集的内容舞台转 90°，用户把手机横过来就是满屏正片。

### 为什么转「舞台」而不是转滚动容器

这是第一版踩的坑，也是整块改动里唯一会直接导致功能坏掉的地方。

我最初旋转的是整个 `.feed`（滚动容器），再让它横向滚动。但**触摸滚动是按手指在屏幕坐标系里的位移判定的**——容器转了之后，它的滚动轴仍在自己的局部坐标系里，手指竖滑对不上轴，横屏下根本切不了集。

所以结构上拆成两层：

```html
<div class="feed">                    <!-- 滚动容器：始终竖向，永远不转 -->
  <div class="feed-overlay">…</div>   <!-- 返回键 + 控件：fixed，跟着转 -->
  <section class="feed-page">         <!-- 一屏一集，height:100vh -->
    <div class="feed-stage">          <!-- 只有它被旋转 90° -->
      <video>…</video>
      <div class="feed-bar">…</div>
    </div>
  </section>
</div>
```

滚动容器、每页高度、`IntersectionObserver` 的可见性判定、`scroll-snap` 吸附全部沿用原来那套已验证的路径，一个字没动。

### 坐标映射

舞台尺寸取 `100vh × 100vw`（即「横过来的视口」），`transform-origin: 0 0`：

```css
/* 非翻转：手机逆时针横过来 */
transform: translateX(100vw) rotate(90deg);   /* 局部 (x,y) → 视口 (W−y, x) */
/* 翻转：手机顺时针横过来 */
transform: translateY(100vh) rotate(-90deg);  /* 局部 (x,y) → 视口 (y, H−x) */
```

两种情况下**局部左上角都落在使用者视角的左上角、局部右下角都落在右下角**，所以舞台内的 `right` / `bottom` 定位仍然指向使用者的右下角，控件不需要单独换算。

翻转方向不做传感器自动判断——WebView 里 `deviceorientation` 不一定可用，而且会抖。给一个「翻转」按钮，存 `hgpref:feedflip`，只在横屏下显示。

### 进度条拖拽要跟着改

舞台转了，进度条在**屏幕上变成一条竖线**，原来那套按 `clientX` 算比例的逻辑会乱跳。按上面的映射反解：

```js
const span = landscape ? rect.height : rect.width;
const offset = landscape
  ? (flip ? rect.bottom - point.clientY : point.clientY - rect.top)  // 横屏：纵向取比例
  : point.clientX - rect.left;                                       // 竖屏：横向取比例
```

### 验证方式

没有连接设备，横屏又是纯几何变换，光看代码不算数。搭了一个探针页（把 `app.css` 和一个手搓的 feed DOM 丢进无头 Chrome），用 `getBoundingClientRect()` 量真实屏幕坐标。视口 412×915：

| 元素 | 竖屏 | 横屏（非翻转） | 横屏（翻转） | 判定 |
|---|---|---|---|---|
| 舞台 | 0,0 → 412,915 | 0,0 → 412,915 | 0,0 → 412,915 | 精确覆盖视口 |
| 第 2 集舞台 | 0,915 → 412,1830 | 同左 | 同左 | 落在视口外，不串页 |
| 控件组 | 右下角 | 屏幕左上→(48,847) | 屏幕右上→(236,38) | 换算后都是使用者右下角 |
| 进度条 | 横条 412×24 | 竖条 24×859 | 竖条 24×859 | 旋转正确 |
| 转圈 | 居中 (189,440) | 居中 | 居中 | 居中未被破坏 |
| 比例 0→1 | left→right | top→bottom | bottom→top | 方向正确 |

三条结论都有实测坐标支撑，不是推演：舞台精确铺满、别的集不串进来、控件落在使用者右下角。

### 这一轮新增的坑

**坑 9：旋转滚动容器 = 切集失效。** 见上文。触摸滚动的方向判定发生在客户端坐标系，转容器必然对不上轴。**转内容，不转容器。**

**坑 10：spinner 和 error 的居中会跟着丢。** 它们原本靠 `.feed-page` 的 `display:flex` 居中；把舞台从 flex 容器改成普通定位块之后，`position:absolute` 且不带偏移的 spinner 会掉到左上角。改成显式 `top:50%;left:50%;margin:-17px 0 0 -17px`（spinner）和 `translate(-50%,-50%)`（error）。

**坑 11：返回键和控件得从滚动流里拿出来。** 它们原本是 `.feed` 的直接子元素，`position:fixed` 所以不随滚动移动。横屏后舞台要整体旋转，控件如果继续留在滚动流里、或者各自单独写一遍变换，很容易漏掉某个元素。收进一个 `.feed-overlay` 里，只给这一层写旋转，里面的元素继续用 `absolute` + `right/bottom` 定位即可。

## 十二、工具链：补丁集、复现比对、CSP 收口（2026-10-16）

这一轮没动功能。起因是想改一处 CSP，然后发现**没有任何办法证明改完之后打出来的包，和我之前测过的那个是同一个东西**。先把这件事解决掉。

### 一、改动面只有 9 个文件

拿原始样本重新解包，与 `cz_repack/` 做文件级 diff：改 8 个、新增 1 个。

| 类型 | 文件 |
|---|---|
| 改 | `assets/app.css`、`assets/app.html`、`assets/app.js`、`assets/site-default.json` |
| 改 | `smali/com/huangguo/mobile/` 下的 `HotUpdateManager`、`MainActivity`、`SiteProfile`、`SiteRepository` |
| 新 | `assets/feed-player.js` |

补丁集 584KB。

**之前算成 11 个，多了两个。** `AndroidManifest.xml` 和 `DualContentRepository.smali` 的 mtime 确实变了，但内容与原始样本**逐字节相同**——是 apktool 解包时重新序列化写入的，不是我们改的。

### 二、mtime 会骗人

第一版补丁集按 `find -newermt` 推导，结果漏了 `assets/vendor/hls.min.js`：它的 mtime 是解包那一分钟，因为当初是用 `cp -p` 拷进去的，时间戳被一并保留，看起来像原版文件。

这个漏洞是 `verify` 抓出来的，不是眼睛看出来的。所以 `sync-patches` 改成拿**基准解包 vs 完整工作树**做文件级 diff，mtime 完全不参与判断。

### 三、两条路径打出来的包，逐条目一致

```text
fast  路径：cz_repack/                      → cz-mod.apk
clean 路径：chengzi-v0.3.15.apk + patches/  → cz-mod.apk
```

两个产物都是 8919034 字节。`unzip -v` 逐条目 CRC32 比对 —— **全部相同**。整体 sha256 不同只来自 zip 条目的时间戳，内容没有差异。

也就是说：`patches/` 是完整的，没有漏，也没有多余。这条链现在能对上账。

### 四、删掉 hls.js 退路，CSP 收回三处

`vendor/hls.min.js` 414KB 随包发布，但 `window.__feedUseHlsJs` 全项目只有 `feed-player.js` 一处在读、**没有任何地方写**，是条死路；而且真切过去也只会播到坑 4 里那支 54 秒宣传片。

删完之后 CSP 有三个口子可以收。全量搜过 `fetch(` / `XMLHttpRequest` / `WebSocket` / `sendBeacon` / `EventSource` / `createObjectURL` / `MediaSource` / `new Worker` / `@import`，**非 vendor 代码里一处都没有**——数据层全部走 Java 桥的 `HttpURLConnection`，不受 CSP 管。

拿原始样本的值一对照，发现那三个口子**本来就是原版没有的，是当初为 hls.js 试错时我们自己开的**。所以这次等于把欠的还回去，只剩一处真正必要的新增：

| 指令 | 原版 | hls.js 试错期 | 现在 | 说明 |
|---|---|---|---|---|
| `connect-src` | `'none'` | `https:` | `'none'` | 回到原版 |
| `img-src` | `'self' data: https:` | `+ blob:` | `'self' data: https:` | 回到原版 |

### 但域名不在它手里

上游 `site.json` 的 `origin` 写的是 `https://huangguoai.com`。真机上解这个域名：

两个都是 `cab3f.nt17g20k.cc` 的 IP（阿里/腾讯 DoH 一致给出的五个地址之二）。

**原因是 `SiteProfile.smali` 里我们早就钉死了。** 上游的写法是「从 merge 后的规则里读 origin」——也就是热更新包说了算；改造版在那个位置之后插了一行 `const-string p1, "https://cab3f.nt17g20k.cc"`，把前面算出来的值整个覆盖：

```smali
invoke-virtual {p1, p2}, Lorg/json/JSONObject;->getString(Ljava/lang/String;)Ljava/lang/String;  # 上游：读远端 origin
move-result-object p1
const-string p2, "/+$"
const-string v0, ""
invoke-virtual {p1, p2, v0}, Ljava/lang/String;->replaceAll(...)                                 # 上游：去尾斜杠
move-result-object p1
const-string p1, "https://cab3f.nt17g20k.cc"     # ← 改造版加的，覆盖上面全部
iput-object p1, p0, ...->origin:Ljava/lang/String;
```

**这一段现在带注释了**，把上面 6 条死代码的来历写清楚——读到「算完又覆盖」不是笔误。之所以删指令而不是留注释：本方法 `.locals 4`，v0/v1/v2 在后面还有复用，删任何一条都要连带核对整段寄存器，收益不抵风险。

所以我上一轮写「远端 origin 会盖掉本地」是错的，实测推翻了。**结论反过来：域名一直握在我们手里。**

### 前端也不在它手里

`HotUpdateManager.resource()` 做热替换时，只放行三类路径：


而 `app.html` 里 `<script src="...">` 一共六个，全是 `vendor/` 和根路径，**一个字都不引用 `ui/`**。原版 app.html 也一样。`ui/` 不是相对 `assets/` 的前缀，热替换接管不到 `app.html` 本身，而 `app.html` 决定了谁被加载。

所以 `copyUi()`、`"ui/"` 常量、`release.json` 的 `resetUi` 字段在代码里躺着，**但没有出口**。上游推不动我们的界面。

这个切分是想要的。上游在做站点适配——r16 的说明就是「修复黄果封面 CDN 变更导致的图片加载失败，以及 AI 单条作品提示『未找到选集列表』的问题」——那正是我们不愿意自己跟的部分。而把包发给别人之后，别人的界面由我们定，不受上游主题推送影响。

## 十五、摘掉原生播放器 + 站点规则瘦身（2026-10-16）

上一节末尾留的那句话做了。

### 一、原生播放器：63 个文件 660KB

`PlayerActivity` 不是一个类，是**59 个文件**：

```text
PlayerActivity.smali                          370 KB
PlayerActivity$1..7.smali                      45 KB
PlayerActivity$Selection.smali                  1 KB
PlayerActivity$$ExternalSyntheticLambda9..56    48 KB   ← D8 为 40+ 个 lambda 生成的合成类
```

加上只被它引用的 `VideoPlaybackCache`（3 个文件 20KB）和 `EpisodeLoadControl`（1 个），**合计 63 个文件 660KB**。

**删之前先量的引用面**，结果很干净：

| 引用方 | 内容 |
|---|---|
| `AndroidManifest.xml` | 一个 `<activity>` 声明 |
| `MainActivity.smali:2472` | `const-class ... PlayerActivity`，在 `dispatch` 的 `open-player` 分支里 |
| `MainActivity$$ExternalSyntheticApiModelOutline0.smali` | D8 生成的 backport 代理，其中一个方法专门签 PlayerActivity 的 `getOnBackInvokedDispatcher()` |

**两个原以为能一起摘掉、实际不能的**：

- **`androidx/media3`（2872 个文件 30MB）摘不掉。** 看起来它只被播放器用，但 `okio`、`bouncycastle`、`okhttp3`、`androidx/webkit`、`com/parse` 都在引用 media3 的类——那是 **D8 的共享 backport 合成类**（比如 `AsynchronousMediaCodecBufferEnqueuer$$ExternalSyntheticBackportWithForwarding0`），命名挂在 media3 名下但被多个库共用。删了会连累它们。

### 二、`dispatch` 的 switch 没动一个字节

`open-player` 走的是 `dispatch` 里的 **packed-switch**：先由 `sparse-switch` 按字符串哈希选出编号，再由 `packed-switch` 按编号跳分支。这张表和索引是耦合的，删一个分支要同时改两张表。

所以做法是**只换 `:pswitch_24` 的 body**：原来构造 `Intent` 打 `PlayerActivity`、包进 `MainActivity$$ExternalSyntheticLambda41` 里 `runOnUiThread` 启动；改成「塞完 `source` 就原样返回」。返回值类型和数量都没变，switch 结构零改动。

配套三处：Manifest 的 `<activity>` 删掉、`ApiModelOutline0` 里那个 PlayerActivity 方法删掉（`.method`/`.end method` 删完仍是 30 对 30）、孤儿 `MainActivity$$ExternalSyntheticLambda41` 删掉。前端 `app.js` 的 `openPlayer()` 一并删——它本来就是留着备用的，没有任何调用点。

**真机验证**：冷启动正常，进详情点播放，`c2.qti.avc.decoder` 在跑，`BufferQueueCore` 两秒 76 帧，`/api/videos/117/play?ep=1 ok 483ms`，零 PlayerActivity 相关报错，crash 0 条。

**收益**：补丁集 **1.1M → 708K**（-36%），APK 8094014 → 8065342 字节。

### 三、`site-default.json`：踩了一个坑

原文件 11 个顶层块 3329 字节。先按「哪些块有出口」筛了一遍：

| 块 | 谁读 | 可达 |
|---|---|---|
| `origin` | `SiteProfile` 构造 + 钉死 | 是 |
| `headers` | `SiteRepository.fetch` 的 `setRequestProperty` | 是 |

| `selectors` / `routes` / `patterns` / `attributes` / `fields` | 全在抓 HTML 的分支里 | 否 |
| `categories` / `categoryMap` / `sectionNames` | 同上 | 否 |

并确认了抓 HTML 那条路**没有任何入口**：`apiPathFor()` 覆盖全部内容类 action，落到桥的 19 个 action 都不碰 `SiteRepository` 的抓取器；`api('detail')` 三个调用点都带 `id`，`api('category')` 的 id 全部来自 `categoryIds`，四个都在 `CATE_IDS` 里。

```text
Caused by: java.lang.NullPointerException: Attempt to invoke virtual method
'java.util.Iterator org.json.JSONObject.keys()' on a null object reference
	at com.huangguo.mobile.SiteProfile.<init>(SiteProfile.java:28)
	at com.huangguo.mobile.HotUpdateManager.load(HotUpdateManager.java:83)
	at com.huangguo.mobile.HotUpdateManager.beginSession(HotUpdateManager.java:120)
```

**`SiteProfile` 的构造函数在启动时会遍历校验 `routes` / `selectors` / `patterns`**——对每条路径查 `//`、`..` 之类，非法就抛「无效站点路径」；缺键则直接对 null 调 `keys()`。

「不可达」指的是**运行时不会被读**，而构造函数是**启动期**跑的，这两件事不是一回事。这是我的漏判，好在冒烟脚本第一秒就抓住了。

## 十六、前端拆模块（2026-10-16）

`app.js` 从 2174 行降到 1875 行，拆出 `cover.js`（217 行）和 `adapters.js`（202 行）。做法沿用 `feed-player.js` 那套：挂在 `window.HGxxx` 上，`create(deps)` 显式传依赖，不靠全局变量。

### 先量依赖，别凭感觉切

原本打算拆的是「封面」和「轮播」两块。量完外部依赖之后，轮播那簇**放弃**了：

| 候选簇 | 行数 | 外部依赖 | 结论 |
|---|---|---|---|

| 封面图片 | 138 | 5 个 | 拆 |

量法是逐行扫出每个候选区间引用了哪些**区间外**的顶层符号。这一步把「看着内聚」和「真的能独立」区分开了——轮播在文件里是连续的一段，读起来像一个模块，但它对外伸手 16 次，搬出去只会把依赖关系从隐式变显式，代码量还多了。

另外 `renderTags` 一度被判成适配层的依赖，实际只出现在一句注释里。**正则扫注释会误报**，所以量完还得看一眼。

### `cover.js`

封装四件事：URL 归一 → 拉取解密 → 解码上屏 → 失败重试。对外只要三样依赖：`api` / `content` / `scroll`。

导出 8 个：`resolveUrl` / `get` / `loadInto` / `retry` / `hydrate` / `hydrateList` / `observe` / `applyPalette`。

**顺手修了一个泄漏**：原来 `app.js` 里有两处直接写 `observer.observe(image)`——`observer` 是封面模块的内部状态变量，却被外面的列表渲染摸到了。现在收敛成一个 `hydrateList(images, eager)`，语义是「前 eager 张立刻加载，其余交给观察器」，把「模块内部有个 IntersectionObserver」这个事实关回模块里。

首次真机验证只看了「页面起来了」，不够。封面模块的全部意义就是封面，所以补了 CDP 断言：

```text

coverImageUrl('/abc/def.jpg?auth_key=1') → https://pic.drleao.cn/abc/def.jpg
```

以及 hero 取色那条支线——`banner-palettes` 缓存里可能有上一轮留下的记录，会把「没跑」误判成「跑了」。所以**先清空缓存再冷启动**，确认重新入缓存 9 条、hero 的 `--hero-tint-light` 有值。

### `adapters.js`

两层纯逻辑，都不碰 DOM 也不发请求：

- `apiPathFor(action, args)` —— 内部动作名翻成站点 REST 路径
- `adapt*()` —— 站点 JSON 翻成 App 内部结构

`CATE_IDS` / `FIRST_PAGE_SIZE` / `PAGE_SIZE` 三个常量跟着搬过去了（确认过只被 `apiPathFor` 用）。唯一依赖是封面地址归一函数，从 `cover.js` 传进去。

留了一个坑：`apiPathFor` 同时也是「这个动作走不走 REST」的判据——`api()` 里那句 `if (shape.apiPathFor(action, args))`。返回 null 就落到 Java 桥。所以这个函数不是纯辅助，它是数据层的路由开关。

拆完验证：`apiPathFor` 九个动作的路径逐条比对、未知动作返回 null、`adaptTags` 的分组映射、剧场页「已显示 8 部」（`FIRST_PAGE_SIZE` 穿过模块生效）、22 张封面照常解码。

## 十七、左右滑动拖进度（2026-10-16）

进度条只有 24px 高、贴在屏幕最下沿，播放中还被外壳收起来，指头够不着。补一条手势：在画面上横向划，右划快进、左划后退。

### 手势占哪条轴，是这一轮唯一需要想清楚的事

滚动容器 `.feed` 永远是竖向的（横屏也只转 `.feed-stage`，见第十节），所以**屏幕横向这条轴是空的**。拿它做 seek，与上下滑切集互不干扰——这大概是唯一一处不需要权衡的选择：纵向留给内容，横向留给进度。

判定阈值：横向位移先过 14px 死区，且大于纵向位移的 1.2 倍，才算拖进度；不满足就还给原生滚动。

配套把 `.feed` 的 `touch-action` 定成 `pan-y`。默认 `auto` 时浏览器的手势识别会把横向也一起消费掉，判定为 pan 之后不再发 `pointermove`、改发 `pointercancel`，拖到一半就断。`pan-y` 等于明确告诉浏览器「只有纵向归你」。

### 映射与反馈

一屏宽 = 120 秒，线性，不做加速度。1080px 的屏划 100px 约 11 秒。

拖动中**不动播放头**：先把当前集 `pause()`，进度条、左下时间、中央提示都按目标位置画，松手才写 `currentTime`。不暂停的话会出现「手停着不动、播放头自己往前跑」的错位，松手一瞬间还要跳回去。

松手按原状态恢复：拖动前在播就继续播，本来就是暂停的就停在目标位置（`drag.wasPlaying`）。拖动那一下的 `click` 被 400ms 窗口吞掉，否则松手会顺手把视频暂停。

中央提示 `.feed-seek` 与 2× 徽标同位置，两者互斥：进入 seek 时 `endHold()` 掉长按计时器；长按计时器醒来时也先看 `drag.active` 有没有被占。

### 横屏下的取舍

横屏把画面转了 90°，手指位移还在屏幕坐标系里，所以 seek 取的仍是屏幕横向。这在横屏下的含义是：**物理上竖着划屏幕 = 拖进度，物理上横着划 = 切集**（后者的手感是上一轮验证过的）。

反过来做不到：横屏时「画面的横向」落在屏幕纵向上，那条轴被滚动容器占着。二选一，保切集。

> **同一天晚上这条改了。** YG 的预期是「横屏：上下划 = 亮度、左右划 = 进度」——
> 就是系统播放器那套手感。现在按**内容坐标**判轴，横屏时那两条轴的含义对调，
> 代价是横屏下不能滑动切集，所以在控件里补了「上一集 / 下一集」。
> 见[第二部分第十八节](#十八横屏手势亮度--清晰度2026-10-16-晚)。
> 竖屏没动：横向还是进度，纵向还是滚动切集。

## 十八、横屏手势：亮度 / 清晰度（2026-10-16 晚）

YG 提了三条关于播放器的：横屏上下划应该是亮度（不是现在的拖进度）、播放器里选不了清晰度。
这一节记这两件，顺带记第 3 条（内容源备注 / 换源缓存）落在播放器之外，见
[用户自带源那一篇](2026-10-16-用户自带源与适配层.md) 的「七、源管理」。

### 手势：屏幕坐标 → 内容坐标

第十七节说得很清楚：seek 取的是**屏幕横向**，而在横屏下这句话的物理含义是
「竖着划 = 拖进度、横着划 = 切集」。这一晚把它对调成用户预期的那套：

```text
横屏（画面转了 90°）
  物理左右划  →  拖进度      ← 原来这条轴归滚动容器（切集）
  物理上下划  →  亮度        ← 原来这条轴归 seek

竖屏（没动）
  左右划 → 拖进度    上下划 → 滚动切集
```

做法是先把视口位移换算成**内容坐标**位移，再在内容坐标系里判主导轴。
翻转开关会让映射取反，所以换算要带上它：

```text
非翻转  stage(x, y) → 视口(100vw − y, x)     用户向右 = +dy，用户向下 = −dx
翻转    stage(x, y) → 视口(y, 100vh − x)     用户向右 = −dy，用户向下 = +dx
```

换成内容坐标之后，「过死区 + 压过另一轴的 1.2 倍」那套判定原样复用，两种模式
（seek / 亮度）互斥且**一次只认一次**，判定之后不再改。

**横屏那条竖向轴是抢来的**：它本来归滚动容器。抢的办法是横屏时给 `.feed` 上
`touch-action: none`（CSS 里跟着 `data-orientation` 走，不能等 `pointerdown` 再改——
手势识别在那之前就开始了）。代价写在明面上：**横屏下不能滑动切集**，所以控件里补了
「上一集 / 下一集」两个按钮，只在横屏显示（`.feed-ep-prev` / `.feed-ep-next`）。

### 亮度：为什么不蒙一层黑

WebView 里改不了屏幕亮度，常见的取巧是盖一层半透明黑。那只能变暗，而用户滑到顶时
期待的是**变亮**。所以走原生窗口属性：

```text
__player:brightness?value=0.42    0~1 的窗口亮度
__player:brightness?value=-1      交回系统（退出播放器时调）
__player:brightness               读当前值
```

读的时候分两层：窗口上没覆盖过（`screenBrightness < 0`）就用系统亮度估一个
（`Settings.System.SCREEN_BRIGHTNESS` ÷ 255，读它不需要权限）。不这么做的话，
用户第一次上下滑会从我们瞎猜的 50% 起跳，屏幕先闪一下。

改窗口属性必须回主线程（`Handler(Looper.getMainLooper())`）—— 在桥的工作线程上直接改，
Android 会抛，而且抛在用户手指正划着的时候。

### 清晰度：先把「有哪些」问出来

片源给的播放地址是**主列表**（`#EXT-X-STREAM-INF`）还是**媒体列表**（`#EXTINF` + `.ts`），
只有把文本取回来看才知道，而页面 CSP 的 `connect-src` 是 `'none'`。所以又多一条桥指令：

```text
__player:variants?url=<编码过的 m3u8>
 → {ok, items:[{name, note, url}]}
```

`name` 取 `RESOLUTION` 的宽（`1080x608` → `1080P`），`note` 把两个原始数都摊开
（`1080x608 · 800 kbps`）—— **标签是 CDN 自己写的，我们只负责照抄并把它说明白**。
相对地址按主列表所在目录展开（实测给的是 `2000k/hls/mixed.m3u8` 这种相对路径）。

实测这一家（量子/暴风系，`v.lzcdn27.com`、`lzv34.com`、`v.lzcdn28.com`）：

```text
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:6
#EXT-X-PLAYLIST-TYPE:VOD
...
```

**混着来。** 同一批片子里有的给主列表（1 档：`RESOLUTION=1080x608` + `BANDWIDTH=800000`），
有的直接给媒体列表（没有档位可列）。所以面板的行为分三种：

| 探测结果 | 按钮 | 面板 |
|---|---|---|
| ≥2 档 | 显示当前档位（如 `1080P`） | 可选列表，当前档高亮 |
| 1 档 | 显示那一档 | 一行，标成「当前」并置灰 + 「这个源只有这一路清晰度」 |
| 0 档（媒体列表 / 探测失败） | 不出现 | —— |

**0 档不是错误**：那说明这个站只有一路清晰度。给一个点不动的选择器，或者编一个
「高清/超清」出来，都比不显示更糟。所以只有一路时如实写清楚 —— 这一条是 YG
那句「无法选择清晰度」最可能的真相：他用的那个源本来就只有一路。

换档 = 换地址重挂（`video.src` + `load()`），位置、倍速、播放状态都带过去，
选中的地址会写进 `hgpref:epurl` 的那份记忆里，下次进这一集直接用。
