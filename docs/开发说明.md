## 发版清单  ⚠ 已过时（用 work/android/scripts/build.sh）

```bash
cd work/shells
./build.sh release           # 刷补丁 → verify → 打包 → 报 sha256
cp cz-final.apk ../../AIIvideo-<版本>.apk
shasum -a 256 ../../AIIvideo-<版本>.apk
```

然后在 GitHub 建一个 Release，把 APK 传上去，Release notes 里贴 sha256。

**仓库里不放 APK。** 两个原因：二进制进了 git 历史就删不掉（每版 8MB）；
APK 里烧着账号服务器的实际地址和 appId，放 Releases 至少是个显式动作。

**没有 CI。** 构建需要原始样本 APK，而它不是这个仓库的东西。
押在 GitHub Actions 上只会得到一个每次必红的 workflow。

发版前对着打勾：

- [ ] `./build.sh verify` 通过（补丁集 == 工作树）
- [ ] 真机装上跑一遍：冷启动 / 换源 / 播放 / 收藏 / 观看历史
- [ ] 三条源各测一次：苹果CMS 站、AGE动漫、普通 REST 源
- [ ] 账号后端 `curl https://<你的域名>/api/healthz` 有响应
- [ ] 版本号有变（`AndroidManifest.xml` 的 versionCode / versionName）
- [ ] Release notes 里写了 sha256
- [ ] **前端热更新同时发一版**，`HOT_MIN_VERSION_CODE` 设成本次 versionCode
      （带新桥指令的界面不能发给没有那个桥的旧 APK，否则点下去没反应）
- [ ] `./build.sh hot-check` 通过（`release` 里已经内置这一步，红着就发不出去）
- [ ] 内置播放器在真机上播一条 HEVC 流（见「内置播放器（libVLC）」）

### 前端和 APK 是两条时间线

`assets/` 里改一行 JS，只有跑过 `publish-hot.sh` 才算真的上线。APK 里那份是「出厂默认」，
设备上跑的一般是热更目录里那份 —— 所以改了 JS 只重装 APK，看到的还是旧逻辑，
而且不会报任何错。

2026-10-17 踩过一次：内置播放器要播放地址的那个 hook 在设备上是旧的 `async` 版，
`evaluateJavascript` 收到的是 `"{}"`，第 2 集永远取不到地址。本地源码早就是同步版，
改了三遍都没效果，因为每次装完 APK，热更又把旧 JS 盖回去了。

`./build.sh release` 现在会在出包前拉线上 `hot-update.json` + zip，和当前 `assets/`
算一份指纹对比，对不上直接报错退出。没网的时候只警告，不拦。


### 补丁集为什么不用 mtime 推导

`cp -p` 会把新文件的 mtime 伪装成解包时间。上一版按 mtime 找改动，漏掉了 `assets/vendor/hls.min.js`——它的 mtime 是解包那一分钟，看起来像原版的。文件级 diff 是唯一可信来源，所以 `sync-patches` 拿基准解包和完整工作树对。

## 内置播放器（libVLC）

**2026-10-17 起全应用只用内置播放器。** 网页 `<video>` 那条路已经移除，不是开关关掉——
`feedPlayer.open()` 直接解析地址、把 `{eps,index,url}` 递给 `VlcPlayerActivity`，页面这边
只剩一屏「正在打开播放器…」。竖滑切集、左右滑拖进度、单击出控件、倍速面板全在 Activity 里，
WebView 里不再套第二层。退出播放器后 `hgResume` 读 `__player:last` 收进度，然后落回详情页
（原来落回 feed 页，那页没了）。

`feed-player.js` 里 `render()/attach()/bindVideo()` 保留着但**已经没有任何调用点**——
将来要恢复网页兜底时是现成的，别当成活代码读。

1.0.18 起，APK 里带了一个原生播放器 `VlcPlayerActivity`，用 libVLC 3.7.7。目的只有一个：WebView 的 `<video>` 用哪个解码器由系统 WebView 决定，页面拿不到任何旋钮，于是同一部片在 A 机能放、B 机 `MediaError 4`（SRC_NOT_SUPPORTED）。libVLC 自带 FFmpeg，HEVC、10bit、AV1、AC3/E-AC3 都能软解，和设备硬解能力脱钩。

**这是本轮唯一加进 APK 的原生依赖**，其余一切仍走 `java-src → classes5.dex`：

| 部件 | 位置 | 说明 |
|---|---|---|
| Java 绑定 | `.build/vlc/classes.jar` | d8 合并进 `classes5.dex`（libvlc 约 1250 个方法，装得下） |
| so | `cz_repack/lib/arm64-v8a/{libvlc,libvlcjni,libc++_shared}.so` | 45MB + 95KB + 9MB |
| 播放页 | `java-src/com/huangguo/mobile/VlcPlayerActivity.java` | SurfaceView + 手势 + 进度回传 |
| 桥 | `__player:native` / `__player:last` / `__player:capability` | 走 detail 桥，不加 dispatch 动作 |

`build.sh` 里两处与之相关：`fetch_libvlc()` 从 Maven 拉 AAR 到 `.build/vlc/`（缓存在本地，不进仓库），`install_vlc_libs()` 把 so 铺进工作树的 `lib/<abi>/`。`lib/` 和 `classes5.dex`、`site-web.js` 一样是**构建产物**，`sync-patches` 的 `diff` 里显式排除——否则补丁集会变成 53MB 的二进制。

体积是这条路线的固定成本：8MB → 61MB。只打 `arm64-v8a`；32 位机器上 `LibVLC.loadLibraries()` 直接抛，`available()` 返回 false，页面退回网页播放器，不闪退。

### 三个非显然的坑

**① 不能靠 `nativeLibraryDir` 判断 so 在不在。** 本包是 `android:extractNativeLibs="false"`，so 不解压到磁盘，那个目录永远是空的，链接器直接从 APK 里 mmap。唯一的判据是「试着加载一次」：`LibVLC.loadLibraries()` 成功即可用，结果缓存在静态字段里（45MB 的映射，别反复试）。

**② `IVLCVout.setWindowSize()` 不调，画面会缩在左下角。** 不设窗口尺寸时 `android_window` 按视频原始分辨率（比如 320×192）铺在原点。要在 `surfaceChanged` 和 `onConfigurationChanged` 里把 SurfaceView 的像素尺寸喂给它。踩到时表现为「有声音、右下角一小块画面」，很容易误判成解码失败。

**③ 进度回传不要用 `startActivityForResult`。** `MainActivity.onActivityResult` 在 smali 的 dispatch 区里，动它风险不成比例。做法是：退出时把 `{id, episode, position, duration, finished}` 写进 `SharedPreferences(hg_player/last)`，页面回到前台读 `__player:last` 取走（读即清）。"回到前台"认 `window.hgResume`（原生 `onResume` 里有 `evaluateJavascript("window.hgResume && window.hgResume()")`），**不能只听 `visibilitychange`**——WebView 被 Activity 盖住时 `document.hidden` 经常一直是 false，那条事件根本不发。

顺带一个细节：`onPause` 和 `onDestroy` 都会落盘，两次都写的话页面收走第一条、prefs 里还剩一条一模一样的，下次回前台会把更新的进度盖回旧的。所以 1.5 秒内不重复写。

### 怎么验

真机上最快的一条：`adb reverse tcp:8000 tcp:8000`，本地 `python3 -m http.server` 起一个 HEVC 的 HLS 目录（`ffmpeg -i in.mp4 -c copy -f hls ...`），然后从播放页点「内置」。本机验证过的结果：`1896×1064 H264`、`720×1280 HEVC (H.265)` 都能满屏播，进度写回 `hgpref:progress`，`__player:last` 取到 `{position, duration}`。

## 改造要点

| 原版 | 改造后 |
|---|---|
| 默认进红果源，依赖本地 `:8080` 服务 | 冷启动直接进黄果源 |
| 进黄果要点版本号、输密码、确认年龄 | 启动自动完成 |
| 播放打开原生 `PlayerActivity` | WebView 竖屏沉浸 feed |
| 手动返回、手动选下一集 | 上下滑切集，结束自动连播 |
| 部分页面抓 HTML，国内网络容易慢或空白 | REST 数据层 + 前端缓存 + 失败自动重试 |
| release 关闭 WebView 调试 | 调试常开 |

播放器逻辑已从 `app.js` 拆到 [`feed-player.js`](work/shells/cz_repack/assets/feed-player.js)。竖屏 feed 已实现：上下滑切集、自动连播、右下角倍速选择、横屏/竖屏切换、横屏翻转、长按临时 2× 加速、单击暂停/继续、底部进度条拖拽、左右滑动拖进度、时间显示、进度记忆、前后集预加载、滑远释放解码器、失败重试、海报图。

左右滑动拖进度走**屏幕横向**那条轴（右划快进、左划后退，一屏宽约 120 秒，拖动中中央显示目标位置），纵向留给上下滑切集，两条轴不抢。横屏下同样可用，取舍见[改造说明第十四节](docs/2026-10-15-橙子短剧改造-说明.md)。

倍速五档（0.75× / 1× / 1.25× / 1.5× / 2×）存 `hgpref:feedrate`。横屏不走 Fullscreen API——Manifest 锁死 `screenOrientation="portrait"`，且 WebChromeClient 没实现 `onShowCustomView`，所以改成纯 CSS 旋转内容舞台，详见[改造说明第十节](docs/2026-10-15-橙子短剧改造-说明.md)。

播放中不显示任何播放器外壳（进度条、集数、时间、倍速与横屏按钮），点一下屏幕暂停才会全部出现，沉浸播放时画面是干净的。返回键不参与收起——它是导航，不是播放信息。

## 注意事项

- 根目录 APK 与 [`work/shells/cz-final.apk`](work/shells/cz-final.apk) 是同一产物；打包以 `work/shells/` 为源头。
- 播放走 WebView `<video>` 原生 HLS。hls.js 的 XHR 会带 `Origin: https://appassets.androidplatform.net`，CDN 据此返回宣传片；`<video src>` 的媒体请求不带这个 Origin。**那条 hls.js 退路已经删掉**，连带把 CSP 的 `connect-src` 从 `https:` 收回 `'none'`、去掉三处 `blob:`（全应用无 `fetch` / `XMLHttpRequest` / `WebSocket`，网络一律走 Java 桥的 `HttpURLConnection`）。
- 站点入口走 Cloudflare，国内移动网络下时通时断（同一个接口实测 1.3s ~ 28s 都有）。图片和视频走国内节点所以一直流畅。这是当前体验的主要瓶颈。
- 站点域名会漂移，[`work/drama_api.py`](work/drama_api.py) 里有域名发现逻辑，可移植进 App。

### 前端热更新：自建签名通道（2026-10-17 重启）

原来的 GitHub 订阅已经切断，现在前端资源走自己的服务器：

```text
HotUpdateManager.INDEX
→ https://149.104.21.177.sslip.io/hot/hot-update.json
```

改 `app.html` / `app.css` / `app.js` 之后不需要再发 APK：

```bash
cd work/shells

```

服务端文件落在 Caddy 的 `/srv/cfg/hot/`，结构和完整流程见
[`docs/热更新说明.md`](docs/热更新说明.md)。要点：

- 包名固定为 `ui/**` + 根部 `site.json` / `theme.json`；`resource()` 会把
  `appassets` 的请求优先映射到当前 session 的 `ui/`。
- ECDSA 私钥在 `work/shells/.build/brandkey/`，APK 只放公钥
  `assets/hot-update-public.pem`；服务端即使被改包也过不了验签。
- 检查在 `onResume` 触发，30 分钟内不重复；设置页「检查更新」强制检查。
- 新包先进入 `pending`，下次冷启动作为 trial 加载；首页渲染成功后调
  `hot-ready` 才转正，启动失败会自动回退并在设置页标出 `blocked`。
- **发完要两次冷启动才看得到效果**：第一次只是把包拉下来写进 `pending`
  （几十到上百 KB，还要验签），第二次启动才把它当 trial 加载。少了第二次，
  页面跑的仍是旧 JS，看起来就像热更没发成功。
  在页面上核对：`hotStatus.revision` 是线上 revision，且
  `window.__hgNativeEpisode.toString()` 是新实现，就说明生效了。
- `HotUpdateManager.resource()` 不要动。它其实是整个 `shouldInterceptRequest`
  的处理体，stub 掉会让 WebView 去 DNS 解析虚拟域名，直接白屏。

### APK 自更新：GitHub Releases + 镜像（2026-10-17 改）

清单和包都在 `zhaoruizhe81/AIIvideo` 的 Releases 上，本地不存副本：

```text
https://github.com/zhaoruizhe81/AIIvideo/releases/latest/download/android-update.json
```

清单里的 `urls[]` 是一组下载地址（GitHub 原始 + gh-proxy + ghfast），
`UpdateMirror.pick()` 并发下每个源的前 256KB，按真实耗时挑最快的。
**不要退回 HEAD 探速**：GitHub 的 release asset 在边缘节点回 302 只要 30ms，
但实际下行被限得厉害，只探头会把最慢的那条选出来。

两个必踩的坑，都写进代码注释了：

- `HttpURLConnection.setInstanceFollowRedirects(true)` **只跟同主机**跳转。
  GitHub 会 302 到 `objects.githubusercontent.com`，gh 镜像 302 到自己的 CDN，
  自动重定向在这里不生效——拿到的是空 302 响应。`UpdateMirror.open()` 手动
  跟 `Location`，检查更新和下载都走它。
- 国内两个平台（Gitee / GitCode）都不能做匿名大文件直链：Gitee 的 raw 和发行版
  附件一律 403（2020 年后强制登录）；GitCode 的 raw 回「暂不支持预览」，
  uploads API 对 60MB 直接 413。这两个平台不要浪费时间。

下载本身在 `UpdateMirror.download()`（Java）：64KB buffer、边下边算 sha256、
进度用反射调回 `UpdateManager$Progress.onPercent`（那个接口在 smali 里，
Java 编译期看不到）。

**二、APK 自更新**

```text
UpdateManager.MANIFEST_URL
→ github.com/MrSsg/HuangguoAPP-for-Andriod/releases/latest/download/android-update.json
```

这个仓库**已经 404**，所以 App 里那个「检查更新」从来就没成功过，只是每次冷启动白打一次外网。切了四处：

| 位置 | 动作 |
|---|---|
| `UpdateManager.check(Z)` | 直接返回 `cached()`（纯本地读缓存），不发网络 |
| `UpdateManager.download(Progress)` | 直接返回 `null`，封掉 `download-update` 这个桥动作的口子 |
| 前端启动自检 | 去掉 `setTimeout(checkUpdate, 3000)` |
| 更新面板整块 | `#update-overlay`（app.html）+ `setAvailableUpdate` / `showUpdate` / `checkUpdate` / `hgUpdateProgress` / `hgUpdateInstallPermissionDenied` / `hgUpdateInstallError` 加两个按钮监听（app.js）+ `#update-overlay` / `.update-panel` / `.update-track` / `.update-buttons` / 四个 `.has-update` 选择器（app.css），全删 |

设置页那一栏保留成纯展示（版本号 + 说明），因为它挂着 `data-secret-entry`——连点五次版本号是隐藏入口。顺带说明：当前构建里这个入口**不会触发**，因为 `handleVersionTap()` 开头是 `if (privateMode()) return;`，而 `privateMode()` 就是 `contentSource === 'huangguo'`，bootstrap 恰好把 contentSource 钉死成 huangguo。代码路径保留，行为是原样。

**验证方式**：冷启动后 25 秒、每 0.25 秒采样一次 `/proc/net/tcp{,6}` 里 uid `10332` 的远端地址，只出现两类——`cab3f.nt17g20k.cc` 的五个 IP（接口）和 `172.217.x.x` / `2001:4860::/32`（WebView 组件更新，跑在应用进程内的 Google 那套，与业务无关）。**GitHub 零连接。**

`window.HotRuntime` 现在读出来是 `{"revision":0,"version":"内置","theme":{}}`，不再对外声称跑着谁的 revision。

上游主仓库 `MrSsg/HuangguoAPP-for-Andriod` 已 404。`HuangguoAPP-HotUpdates` 仍在维护，但与本包无关了。
