# 2026-10-19：卡片过渡动画「顿一下再跳」排查记录

**现象**：真机（23113RKC6C，Android 16）上点卡片进详情，动画偶尔冻在起跳阶段
约 1.7~2.4 秒，然后直接变到全屏。退出动画一直流畅。

**这轮改动**（app.js + card-transition.js）：

1. `CARD_TRANSITION_ENABLED` 开关重新打开（用户要求恢复动画），并且 `capture()`
   跟着开关走 —— 之前开关关了 capture 照跑，白做两趟 cloneNode，还把缓存渲染
   挡死了（`hasDetailData && !entrySource` 永远不成立）。
2. 缓存命中无条件先渲染（不再要求 `!entrySource`）。
3. 「过场盖加载」：动画进行中不重建 `#content`，缓存/网络/收藏三种渲染全部排队到
   `onOpened`（spring 落定）之后执行。动画中途的 innerHTML 重建 + 封面 hydrate
   就是第一版「顿一下」的直接原因之一，已消除。
4. **帧停顿看门狗**：`settle()` 里 onUpdate 超 150ms 没推进 → 直接画到终态收场，
   打 `[card-transition] 帧停顿，跳到终态`。这是兜底，不是根治。

**排查证据**（全部真机 CDP 实测，工具链见 `2026-10-18-真机WebView调试.md`）：

| 实验 | 结果 |
|---|---|
| 页面内插桩 prepare/draw | prepare 20ms，draw 每帧 0.1~0.5ms，无长任务 |
| rAF 间隔监测 | 停顿时 rAF 断流 1.7~2.4s，之后 120fps 满帧跑完 |
| PerformanceObserver longtask | 停顿期间**零长任务** —— 渲染进程 JS 空闲 |
| 摘掉舞台背景快照层 | 仍停顿 |
| 摘掉全屏封面层 | 仍停顿 |
| 摘掉阴影层 | 仍停顿 |
| 冻结 borderRadius/clipPath 每帧更新 | （数据被污染，未定论） |
| 无过渡动画进详情（capture 返回 null） | 从不停顿 |
| spring 启动推迟 600ms | 停顿跟着 spring 起跳时刻走，不跟着 prepare 走 |
| gfxinfo（某一次点击） | 370 帧 / 0.54% janky / p95 16ms —— 有时又完全流畅 |

**结论**：停顿与动画页面自身的 DOM/样式无关（图层逐个摘除无效），是渲染主线程
被页面外的东西间歇性抢占。头号嫌疑：**Android WebView 全 app 共享一个渲染进程
主线程**，spider 宿主 WebView（SpiderRuntime 的隐藏宿主页）在同一线程上跑抓取与
解析时，主页面 rAF 被饿死。尚未实锤：spider 调用 pending 期间单独观察未引发停顿
（可能调用本身没真正跑起来），停顿与桥回调时刻的相关性也没抓到。

**下一步（架构级，另开一轮）**：
- 复现时抓 `console.warn '[card-transition]'` 确认看门狗触发频率；
- 在 spider 抓取进行中主动给渲染线程加压（busy loop 探针）验证共享线程假说；
- 若实锤，考虑 spider 宿主降频（把解析搬去 `setTimeout` 分片）或挪出 WebView
  （牺牲部分 TLS 指纹能力，需权衡）。

## 根治（同日晚）：spider 宿主迁入 `:spider` 独立进程

**实锤**：CDP 探针直接调 `bridgeCall('spider', {op:'call', cap:'detail', …})`：

```
spider detail 调用：1781ms（yhdm.one 抓取 + 解析）
主页面 rAF 断流：62ms → 1730ms（1717ms）—— 完全重合
```

根因坐实：**Android WebView 全 app 共享一个渲染进程主线程**，spider 宿主页
跑源码时主页面帧调度被饿死。同进程内无解，唯一根治是进程隔离。

**改动**：

| 文件 | 内容 |
|---|---|
| `ISpiderChannel.aidl` | 新增。同步 `String call(String)`，一次往返 = 一次能力调用 |
| `SpiderService.java` | 新增。跑在 `:spider` 进程，收 JSON → 钉代理快照 → 调 SpiderRuntime |
| `SpiderClient.java` | 新增。主进程侧客户端，原 CALL_LOCK + GENERATION 语义原样搬来 |
| `SpiderRuntime.java` | 去掉 Activity/decorView 依赖：WebView 免窗口 headless（Service 里没有 window） |
| `SpiderStore.java` | `call` 改走 SpiderClient，契约不变 |
| `AiiHttp.java` | 新增 `applyProcessProxyOverride`：内置核心的本地 SOCKS 地址是主进程内存值，:spider 读不到，主进程每次调用带快照 |
| `AndroidManifest.xml` | 注册 service，`android:process=":spider"` |
| `MainActivity` | onDestroy 的 `SpiderRuntime.shutdown()` → `SpiderClient.shutdown()`（解绑 + 停服务，进程随之回收） |

**踩到的坑（必须记住）**：WebView 数据目录锁 —— 同一 app 只允许一个进程用
同一数据目录的 WebView，否则 `RuntimeException: Using WebView from more than
one process`。解法是官方指定的 `WebView.setDataDirectorySuffix("spider")`，
在 SpiderService.onCreate（进程内最早时机）调用。spider 宿主页本来就关了
DOM storage，两套数据目录互不可见无影响。

**真机验证（23113RKC6C）**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| spider detail（真实网络） | rAF 断流 1717ms | 调用 2090ms，**rAF 断流 0** |
| cap=play（进播放器） | — | `cap=play ok ms=1712`，VLC 正常起 |
| 播放器返回 → 详情 → 首页 | — | 路由干净，无残页 |
| 单测 335 + model-check | 绿 | 绿 |

**已知代价**：多一个进程的内存（约一个空 WebView 渲染进程）；spider 抓取的
cookie 与主 WebView 的 cookie 天然隔离（各进程独立数据目录）—— 目前所有源
都是无登录抓取，不受影响；若未来出现「需要登录态的 spider 源」，要在 AIDL
载荷里显式传 cookie。

**回归**：`scripts/spider-check.js`、`scripts/model-check.js` 照跑；真机点卡片/
返回/连点多次无死锁（watchdog 任何分支都保证 `finish()` 恰好执行一次，`stop()`
会清掉 interval，不泄漏）。

## 追记（同日晚）：方案 B/A 落地与一次闪退

进程隔离之后，代理路由智能化（geosite 分流 + 失败自愈）随后落地，完整记录见
[`2026-10-19-代理路由智能化.md`](2026-10-19-代理路由智能化.md)。与本主题相关的一次
事故：geosite 规则让核心第一次去读 geo 文件，而 libv2ray 的 gomobile asset 路径
需要 `go.Seq.setContext(appContext)`（从没调过），Go 侧 `os.Exit(1)` 把主进程无声
带走——现象是点图标闪退且无 Java 崩溃栈。修复一行，教训（新核心配置资源类型要在
「核心真实启动」的档位下验收）已写入路由文档 §三。
